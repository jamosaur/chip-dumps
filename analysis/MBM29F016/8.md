This chip is one byte lane of a 32-bit-wide flash bank. In a 32-bit bank, four 8-bit chips sit side by side and each chip stores every fourth byte of the data. The first 1.05 MB is uniformly random data, so it is compressed or encrypted. After it come about 36 KB of ASCII text in four records, each with a short binary header, and the rest of the chip is erased (`FFh`). The text cannot be read as it stands, but it has clear structure. In the hex-dump sections, the bytes fall into identical 65-byte patterns, and these keep the same internal layout wherever they start in the chip. The patterns fit one rule exactly: chip byte *i* is character 4*i* of a stream of 65-character lines. Each line is `XXXXXXXX: XXXXXXXX ×6` plus CR LF, so the text was written across four chips, one byte per chip. The chip's data bits D0 and D2 are also swapped relative to the CPU. Hex digits and record names only make sense after swapping those two bits back. None of the other MBM29F016 dumps contains the other three lanes, so neither the text nor the compressed block can be rebuilt from this chip.

## Layout

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x10B896 | High-entropy data (7.96–8.00 bits/byte per sector), no header in this lane. A short constant-fill island sits at 0x106E6E–0x106F6E |
| 0x10B896 | 0x000020 | Tail of the block: mostly `00` with a few small values (`7A 63 75 29`, `31 45 4B 03`, `FB 46 4F 56 56 FA`) |
| 0x10B8B6 | 0x000010 | Record header 1: `BA 00 79 00`, name `cho0009` (raw `fho000<`), `FF` padding |
| 0x10B8C6 | 0x003EDE | Text lane, record 1 (hex dumps, `r=` tables, `=====` banners) |
| 0x10F7A4 | 0x000010 | Record header 2: `BA 00 AB 00 47 00`, then 10 × `FF` |
| 0x10F7B4 | 0x0000F1 | Text lane, record 2 (short) |
| 0x10F8A5 | 0x000010 | Record header 3: `BA 00 D5 00`, name `cho0017` (raw `fho0047`), `00` padding |
| 0x10F8B5 | 0x002818 | Text lane, record 3 |
| 0x1120CD | 0x000010 | Record header 4: `BA 00 0C 00`, name `cho0009`, `FF` padding |
| 0x1120DD | 0x002486 | Text lane, record 4 (starts with the same preamble as record 3) |
| 0x114563 | 0x0EBA9D | Erased (`FFh`) |

## Findings

- **Fill and entropy.** Sectors 0x00–0x0F hold 7.96–8.00 bits/byte. Lag-1 to lag-1024 byte differences average 85, which is what random data gives, so there is no image-like or code-like structure. Every bit position is 1 with probability 0.52, so bytes with seven 1-bits occur about 26% more often than expected. The cause of this small, even bias is unknown (see open questions). At 0x10B8C6 the content switches to 100% printable ASCII, and it ends at 0x114562. Everything from 0x114563 to the end is `FFh`.
- **Text is one lane of four (stride 4).** The text in 0x1103E1–0x1105E8 splits at CR into 65-byte pieces that always have the same layout: 56 hex digits, 6 spaces, one `:`, one LF and one CR. The pieces start at 0x1103E1, 0x110422, 0x110463 … (offsets mod 16 = 1, 2, 3, …), so an address-line scramble on the board cannot explain them. Mapping position *i* inside a piece to text position (4*i* + c) mod 65 is the only affine mapping that matches the expected separator columns. In other words, the chip holds every fourth character of a stream of `%08X: %08X %08X %08X %08X %08X %08X` lines terminated by CR LF. Spreading the bytes out four apart lines up `:` at column 9 and spaces at columns 10, 19, 28, 37, 46 and 55 across groups of four lines, as the figure shows. Elsewhere, a 15-byte repeating unit (`:00a 00200, 00` LF) is the same effect on 60-character lines. A brute-force search over low address-bit permutations gave no clean improvement, which confirms the scramble is a lane split and not address wiring.
- **Data bits D0 and D2 are swapped.** If CR, LF, space, `0` and `=` keep their values, the only possible bit permutation is identity or a D0↔D2 swap. With the swap, the text uses only hex digits `0–9 A–F` (raw data holds 229 `<`, which the swap turns into `9`). Letter frequencies also become plausible: raw `q` 597 and `t` near zero become `t` 597 and `q` near zero, and raw `k` 588 becomes `n`. The record names read `cho0009` / `cho0017` and not `fho000<` / `fho0047`. The other dumps of this chip, read on the same reader, decode with no swap, so the swap is probably in the board's wiring to this chip.
- **Record headers.** Four 16-byte headers start with `BA 00`, then one byte (0x79, 0xAB, 0xD5, 0x0C), then `00`. They differ from the text in one way: the 7-character names inside them read straight through in this one chip, with no striping. Either the header was copied to every lane or it was written with byte-wide accesses. Records 3 and 4 begin with the same preamble (lane text `Co4R0rs vox h1/4y mr` after the bit swap), so they are probably two instances of the same report. Record 2 has type byte `G` (0x47) and no name.
- **Text content.** Only a quarter of each line is present, so no sentence can be read. The structures are recognisable: blocks of `========` with title fragments between them (`==h laCkers=====`, `==Rs oD ====`, `==MonrTe=====`), 6-word hex dumps of memory or registers, `r=` value tables, and lines with `0x`-style fields. This looks like a diagnostic report or crash log written by the firmware.
- **Constant island in the block.** 0x106E6E holds 127 × `F9`, followed by runs of `F8`, `88`, `C1` and `3F`. Over a 32-bit stream this is about 500 bytes of fill, which is unusual inside compressed data. It may be an uncompressed or stored region of the original object.
- **No known signatures.** `binwalk` finds nothing in either the raw or the bit-swapped image. zlib, raw deflate and gzip decoders all fail at offset 0. Decompression could not succeed anyway, because this chip holds only every fourth byte of the stream.

## Device

Unknown, **low** confidence on the device itself. The evidence supports more about the board than about the product. It had a 32-bit data bus with four 5 V MBM29F016 chips forming an 8 MB bank, probably from the second half of the 1990s or the early 2000s. This lane's D0 and D2 were cross-wired. The firmware used the bank as storage, not to execute code in place: about 4.3 MB of compressed or encrypted data across the bank, followed by headed text records that look like diagnostic or crash reports. The record names `cho0009` and `cho0017` match nothing known. None of the other MBM29F016 dumps shares this layout, so the chip does not belong with the NS-2482 lanes (dumps 3, 4, 5), the Hitachi microcode (dump 1) or the font flash (dump 2).

## Open questions

- **Which lane, and the other three chips.** It is not known whether this chip is the most or the least significant byte. Dumping the other three chips from the same board and interleaving them would recover the text and the compressed object. The phase of record 1 relative to the header would then show the lane number.
- **What the 1 MB block is.** It has no visible header in this lane. With all four lanes, the next step is to check the first 16 bytes for gzip, ZIP or LZ headers and to try decompression.
- **Bit bias of 0.52.** This could be retention loss (programmed 0 bits drifting to erased 1) or a property of the encoding. If it is decay, the text should contain single-bit 0→1 errors. Comparing repeated hex-dump lines across records 3 and 4 for one-bit differences would test this.
- **Header fields.** The meaning of byte 2 (0x79/0xAB/0xD5/0x0C) and of the `FF` versus `00` padding is unknown. A sequence number or checksum is likely. Testing that needs the other lanes' copies of the header.

## Method

Python (run with `-I`) for the sector and 4 KB entropy maps, byte and bit statistics, and lag-difference tests. The bit permutation was derived from fixed-point characters and checked against hex-digit and letter frequencies. The stride-4 lane split was found by an exhaustive affine-mapping fit of separator columns over the 65-byte hex-dump pieces, after a hill-climb over address-bit permutations failed. `binwalk`, `strings` and zlib trial decompression were run on both the raw and the bit-swapped image. Siblings were compared by fill extent, entropy profile and a search for the `BA 00 .. 00 cho` header. The figure was rendered with Pillow.
