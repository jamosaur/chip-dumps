This image contains no code, only fonts and lookup tables. It holds a complete GBK 16×16 Chinese bitmap font, eight-pixel-wide 8×16 character sets of the kind used by VT100/VT220 and PC-ANSI terminals, a 24-row font that is only partly here, and a table that maps traditional characters to simplified GB2312 codes. The strongest evidence is that glyphs rendered from the image line up exactly with GBK code positions. Glyph number `(lead−0x80)×191 + (trail−0x40)` gives the right character at every place checked: `一`, `啊`, `阿`, `中`, `国`, `电`, `话`, `齄`, `丂`, `龥`, full-width `ＡＢ１` and `あ`. The 8×16 sets include VT220-style control-character pictures (`NU`, `SH`, `SX`, ...), DEC Special Graphics line-drawing glyphs and a full CP437 set. That points to a Chinese-market text terminal. The whole image fills about 1.9 MB of the 2 MB chip. Entropy is 4.6 bits/byte, there are no `FFh` regions, and unused space is zero-filled.

## Findings

- **No code or headers.** `binwalk` finds no signatures. Every `strings` hit is bitmap noise. No region looks like a vector table or instructions for any CPU.
- **8×16 sets (0x000000, 0x080000).** Each 4 KB block is 256 glyphs × 16 bytes, one byte per row. The four sets are:
  - A0 has two-letter control-character pictures (`NU`, `SH`, `SX`, `EX`, ...), as shown by a VT220 in "display controls" mode.
  - A1 and B0 carry DEC Special Graphics: `◆ ▒ ␉ ␌ ␍ ␊ ° ± ␤ ␋ ┘ ┐ ┌ └ ┼ ⎺ ⎻ ─ ⎼ ⎽ ├ ┤ ┴ ┬ │ ≤ ≥ π ≠ £ ·`.
  - A1 also has box and technical pieces plus Latin-1 accented letters.
  - B1 is a full CP437 set, as used for ANSI/SCO console emulation.
- **The 16×16 GBK font is split into halves.** Plane 0x000000–0x07FFFF holds the left 8 columns of each glyph and plane 0x080000–0x0FFFFF the right 8 columns. The same glyph index is used in both, so address bit A19 selects the half. Pairing `0x002BF0 + 16·i` with `0x082BF0 + 16·i` gives clean characters. The first ones are `丂 丄 丅 丆 丏 丒 丗 丟 丠 両 丣 並`, which are GBK 8140–814B.
- **GBK indexing.** Each lead byte gets 191 slots (trail 0x40–0xFE, with 0x7F kept but always blank). The table starts with an empty placeholder row for lead 0x80, so the font begins 0x2000 (512 glyphs) into each plane. The last glyph is FEA0, at 0x060620 and 0x0E0620. 22,660 left-half slots are non-empty. Because the ×191 step is not a power of two, glyph addresses must be computed by a CPU, not by a hardware character generator.
- **The user-defined area is filled.** GBK A140–A7A0 is normally empty, but all 672 slots here hold glyphs. They are runs of traditional characters grouped by radical (王/玉, 瓦, 田, 疒, 鳥 radicals), apparently copied from elsewhere in the code space. The 1-byte rows A1–A9 hold the standard GB2312 symbols (`、。·ˉˇ…【】±×÷∶∧∨∑∏ … ※→←↑↓〓`).
- **The 24-dot font is incomplete.** At 0x100000–0x1C0C4F the image uses the same GBK index, but each slot is 32 bytes. Rows 26–31 are zero in 100 % of slots, and the 0x17E0 (= 191 × 32) period of zero gaps confirms the indexing. Each slot holds only 8 pixel columns: `中` shows a 24-row vertical stroke with stubs of the box, `一` shows only its right-hand serif. The other columns are not in this image. The ASCII slots at 0x100000 likewise show only fragments, such as two stems of `H` with no crossbar. Which columns this slice covers could not be determined.
- **Traditional-to-simplified table (0x1F0000).** It has 9,728 big-endian GB2312 codes. They start `2020 D2BB B6A1 C6DF D5C9 …` = blank, `一丁七丈三上下不丐丑且丕世丙丞丢并 … 了予事二于云互五井`. The entries follow Unicode/KangXi radical-stroke order and run up to the `鳥` and `魚` radicals (`鲻 鳇 鳆 鳄 鲢 鳢 鲚 鸵`). Traditional source characters appear as their simplified equivalents (`並→并`, `丟→丢`, `亂→乱`, `個→个`). 3,171 entries are `2020h` (no GB2312 equivalent), and offset 0x1F0342 holds an odd `A0A0`. The ordering matches neither Big5 code order nor a plain Unicode-indexed array: there are 9,728 entries, but U+4E00..U+9FA5 has 20,902 code points. Some stray entries (`锕 锿 砹 桉 苯 吡 醭`) sit between unrelated characters. This is probably a Big5- or Unicode-to-GB conversion table indexed through a mapping that is not in this image.
- **Records at 0x1F4F00, 0x1F5000 and 0x1F5150.** These are byte streams such as `03 2F00 A6A4 A6AF A6CF | 11 3E00 A6A3 | 21 5A00 A6A9 | 31 7A00 A6AB …`. A control byte appears to give a count of following GB codes in its low bits. When bit 3 is clear, a 16-bit little-endian value follows, and these values increase steadily. The three tables contain 56 unique codes (mostly row A6, Greek), 78 (row A7, Cyrillic) and 177 (rows A4/A5, kana). The meaning of the 16-bit field is not decoded; the tables are probably input-method data for the key-cap sets described below.
- **Keyboard-mapped Cyrillic and kana sets (0x1FA5E0).** Three 94-glyph 8×16 sets sit in ASCII code positions, at 0x1FA5E0, 0x1FADE0 and 0x1FB5E0. In the Cyrillic set the glyph under each Latin letter is the Russian ЙЦУКЕН keyboard letter on the same key: A–Z give `Ф И С В У А П Р Ш О Л Д Ь Т Щ З Й К Ы Е Г М Ц Ч Н Я`. The hiragana and katakana sets run in gojūon order from `@`/`A` onwards. These sets are therefore probably soft-keyboard or input-method key caps, not character-set designations. The record tables at 0x1F4F00 list the matching GB2312 codes and are probably the same input-method data. The 32-byte 24-row slices just before the sets (0x1F5800–0x1FA39F) appear to be 24-dot versions of those symbol rows.

## Device

**Chinese-market text terminal (VT100/VT220/ANSI-compatible 汉字终端), font flash. Medium confidence.** For the device class:

- The VT220 control-picture glyphs, DEC Special Graphics and CP437 are the character sets such a terminal needs to emulate DEC VT and SCO/ANSI consoles.
- A full GBK 16×16 font, Cyrillic and kana key-cap sets for symbol input, and a traditional-to-simplified table fit a terminal sold into Chinese banking, post-office or retail systems. Typical makers were Start/实达, Great Wall, Inspur and Newland.

This chip is a dedicated font store, with firmware held elsewhere on the board:

- The 24-dot font is present as one 8-pixel slice only, so the board probably held at least two more font chips of the same type.
- The image contains no firmware.

None of dumps 1 and 3–9 is a matching slice. A Chinese dot-matrix printer is a less likely alternative: 24-dot fonts are typical there, but the VT control pictures and CP437 sets are not.

## Open questions

- **Which columns the 24-dot slice covers, and where the rest is.** Look for sibling font chips from the same board. A dump with the same 0x17E0 zero-gap period at 0x104000 could then be interleaved with this one, column by column.
- **How the 9,728-entry table is indexed.** Generate candidate orderings (Big5 by radical/stroke, CNS 11643 planes, GB 12345) and score the alignment of identity mappings with this table.
- **What the 16-bit fields in the 0x1F4F00 records mean.** Test whether they are Unicode or keyboard/input-method codes, or offsets into the 0x1F5800 glyph blocks, by comparing them with the glyph order in those blocks.
- **Why the A140–A7A0 user area holds radical-grouped characters.** Compare those glyphs with GBK/4 (AA40–FEA0) slots to see whether they were copied from there.

## Method

I used Python (`python3 -I`) for per-sector entropy and zero/`FF` maps and for runs of zero bytes. I rendered glyph sheets to PNG with PIL in several layouts (row-major, column-major, paired halves) and confirmed the GBK index by rendering known characters. The traditional-to-simplified table was decoded with Python's `gb2312`/`gbk` codecs and compared with `big5` code sets. I also ran `binwalk` and `strings`, and compared fixed-offset features against sibling dumps 1 and 3–9 (none matched). All scratch work was kept in a `mktemp -d` directory outside the repo.
