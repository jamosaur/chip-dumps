This chip is one of four MBM29F016 parts that make up an 8 MB, 32-bit-wide flash bank in a Seiko Instruments (SII) NS-2482 "Multi Access Server". The board ran a 68040-family CPU under NS-OS 3.1. Dump 3 is byte lane 0, the most significant byte on a big-endian bus. Dumps 5 and 4 are lanes 1 and 2. Lane 3 is not among the dumps. Interleaving 3/5/4 byte by byte makes the boot-loader text readable (`Bus error`, `Address error`, `2nd Boot version 1.2 start`, `load 3rd Boot from %s`). The NS-2482 identity comes from the sibling lanes: `SysDescr "SII Multi Access Server NS-2482."` and `Communication Server NS-2482 System Software 1998.08.31 (Ver 3.1)` are in dump 4, at 0x11d9fe and 0x149000. This chip holds `NS-OS version 3.1 start.` at 0x12f200. Every 64 KB sector begins with its own flash-management unit header (magic `24 11`). Apart from the boot area, each sector holds 127 × 512-byte blocks of one logical unit, stored linearly in this chip alone.

## Findings

- **Byte lane 0 of a 32-bit bank.** The boot area at 0x000400–0x003876 reads as text and 68k code only when interleaved with dumps 5 and 4 as `3,5,4,?`. Examples are the 68000 exception names at CPU 0x3630 (`Bus error`, `Illegal instruction`, `Zero-divide trap`) and `Memory card` / `Flash Rom` / `/boot.3rd` / `bootconf` messages. With lane 3 missing, every fourth byte is unknown.
- **The file-system units are stored per chip, not interleaved.** Unit 0x42 at 0x020200 is linear 68k code in this chip alone, for example `48E7 001C 2A6F 0010 … 4CDF 3800 4E75` (movem/movea/movem/rts). The flash manager treats each byte lane as an independent array of 64 KB erase units: 4 lanes × 32 sectors = 128 units = the "8M byte" in the descriptor.
- **Unit header** (0x30 bytes at the start of every sector). It starts with constant words `2411 0080 0000 0080 0001 0080 0001 0200 0040 0020`: magic 0x2411, probably 0x80 blocks per unit, block size 0x200. The big-endian word at +0x24 is the logical unit number. +0x2C and +0x2E hold the same counter twice, probably an erase or write count (1 for never-rewritten units, up to 9). The meaning of +0x26 is unknown. Block 0 of each unit holds only the header. The data is the remaining 127 blocks (0x200–0xFFFF), with no per-block map.
- **Logical numbering.** Untouched units carry number 4×sector+lane: this chip has 0x00, 0x04, 0x0C, 0x60, 0x64 … 0x7C, while dumps 5 and 4 have +1 and +2. Rewritten units have moved: sector 2 holds unit 0x42. The end of unit 0x42 (`7E12 2014 C086 4A80` at 0x02FFF0) runs straight into unit 0x43 at 0x100200 (`6500 00CA … 7E13 2014 C086 4A80`), which confirms that the logical order is right.
- **Partition descriptor.** At 0x0001FF there is a 0x78 byte, then the ASCII text, then longwords at 0x280: `7F, 0, 1, 7F, 200, 3F8, 0, 3F01, 0, 1D45, 194D, 9EC, 1F41, 1FC0`. The first values look like unit ranges and the block size. The later ones are not decoded.
- **The boot loaders are 68040 code.** Interleaved, the 2nd boot at CPU 0x1010 does `movec cacr`, `move.l #$8000,d0`, `movec d0,cacr` and `F498` (CINVA IC). These cache instructions exist only on the 68040/68060, and bit 15 of CACR is the 68040 instruction-cache enable. Other strings mention `CICR`, `SI-ram SETUP`, `QMC`, `SCC1`/`SCC2` and `TDMa`/`TDMb`, which point to a Motorola MC68360 QUICC as the communications controller, probably running in companion mode beside the 68040.
- **The file system** (rebuilt from lanes 0–2) has 32-byte directory entries: a 4-byte inode plus a 28-byte name. The root directory, held in unit 0x0E on the sibling chips, lists `admin`, `bin`, `boot.3rd`, `bootconf`, `driver`, `etc`, `init`, `init.root`, `mnt`, `nsx.sys`, `pocvup`, `save` and more. This chip holds parts of utilities, libraries, PPP, SNMP, IP, scripts written in the device's `$FUNC[...]` scripting language, and a fragment of the NS-OS kernel.
- **The configuration is factory default.** The text in unit 0x4A (0x080000) describes "High Super Digital" (HSD, an NTT leased-line service), 1536 kbit/s PRI time slots, LAPD SAPI0/SAPI16 and LAPB timers. No IP addresses, host names or credentials were found in this chip.
- Units 0x04, 0x0C, 0x25 and 0x60–0x7C have valid headers but zero-filled bodies. The flash manager apparently zero-fills free units rather than leaving them erased.

## Device

Seiko Instruments (SII) NS-2482 Multi Access / Communication Server, system software Ver 3.1 dated 1998-08-31: a Japanese ISDN BRI/PRI and leased-line (HSD, frame relay) access router. Confidence: **high**. The model string and date are in sibling lanes 4 and 5, which share this chip's per-sector header format and slot into the same 32-bit interleave. This chip carries `NS-OS version 3.1 start.` and the matching boot loaders. The CPU is very likely a 68040-family part with an MC68360 QUICC (medium confidence, from the cache instructions and the QUICC register names).

## Open questions

- **Lane 3 is missing.** None of dumps 1, 2, 6–9 has the `2411` unit header, so the fourth chip was not dumped or is not in this set. Without it the boot loaders cannot be disassembled completely, and about a quarter of the logical units are absent. If a matching chip turns up, interleave it as the last byte of each word.
- **Duplicate logical units.** Units 0x0E, 0x49 and 0x4E appear on two lanes with identical bodies. Units 0x42, 0x48 and 0x54 appear twice with different bodies. The higher +0x26 value does not consistently mark the live copy. Next step: check which copy chains correctly into its logical neighbours, as done for 0x42 → 0x43.
- **File-system metadata.** The superblock and inode table were not located. They probably sit in units 0x08–0x0B, which are missing or on lane 3. Next step: find the inode format from the directory's inode numbers (for example `boot.3rd` = 0x1B8) and the code in `boot.3rd`.
- The partition-descriptor longwords at 0x280 and the unit-header fields +0x26 and +0x04–+0x13 are not fully decoded.
- The magic values `2BF?` (CPU 0x1000) and `HPO?` (CPU 0x4000) lose their fourth byte to the missing lane.

## Method

Python scripts computed per-sector entropy and erased/zero ratios, printed the 0x30-byte header of every sector in dumps 3, 4 and 5, and built a logical-unit map from the word at +0x24. Byte-interleaving dumps 3/5/4 with a placeholder for lane 3 recovered the boot-area text, and the file-system units were joined in logical order to find directory entries. `strings` and `grep` identified each unit's contents. No disassembler was usable (r2 was broken, and rizin and capstone were not installed), so the 68k and 68040 opcodes (`4E75`, `48E7`, `4CDF`, `61FF`, `4E7A`/`4E7B`, `F498`) were decoded by hand.
