This chip holds only one byte of every 16-bit word. It is the low byte lane (D7–D0, odd addresses on a big-endian bus) of a two-chip, 4 MB flash bank that ran Hitachi SuperH (SH) code. The partner chip with the high bytes is not among the dumps. The SH identification comes from instruction low bytes that stay adjacent in this lane. The standard SH epilogue `lds.l @r15+,pr` / `rts` / `nop` (`4F26 000B 0009`) leaves `26 0B 09` here, and that sequence occurs 7,664 times. Register pushes `mov.l r14…r11,@-r15` (`2FE6 2FD6 2FC6 2FB6`) leave `E6 D6 C6 B6` (1,128 times), and `sts.l pr,@-r15` followed by `add #-4,r15` (`4F22 7FFC`) leaves `22 FC` (1,056 times). Text supports the halving. C strings appear with every second character missing, for example RCS keywords that read `Hae:da_a., . 61/52:33 riuiEp$`, which is the odd-position characters of `$Header: …da_a.c,v 1.x 96/… Exp $`. Tables of 16-bit characters, whose high byte is 00h or 82h, appear in full. They include the menu labels `NAVIGATION`, `NAVI`, `ﾅﾋﾞｹﾞｰｼｮﾝ` ("navigation" in half-width katakana) and `ﾅﾋﾞ`, plus version tags `APL 0101` and `BASE0101`. This points to a Japanese car-navigation unit of about 1996–97.

## Layout

Offsets are chip offsets. CPU address ≈ 2 × chip offset + 1 within the 4 MB bank.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x000040 | Image header: `AA AA AA AA AA AA AA AA`, fields, then `AA AA BB BB CC CC DD DD` marker twice (32-bit `AAAAAAAA BBBBBBBB CCCCCCCC DDDDDDDD` in the CPU view) |
| 0x000040 | 0x000200 | 256-entry table of 32-bit pointers (vector-table shape), mostly to consecutive 4-byte stubs |
| 0x000240 | 0x000060 | Small constant tables |
| 0x0002A0 | 0x000220 | Table of 8-byte (16 CPU bytes) records: id 0x01–0x43, pointer, length |
| 0x0004C0 | 0x1A0B40 | SH program code with literal pools and embedded constants (about 3.3 MB in CPU terms) |
| 0x1A1000 | 0x04F000 | Constant data: UI label tables, tile/character maps, lookup tables, RCS strings |
| 0x1F0000 | 0x002000 | Tables (sorted 16-bit index pairs and similar) |
| 0x1F2000 | 0x001F49 | Second, smaller block of SH code ending in its own `$Header$` string at 0x1F3F2A |
| 0x1F3F49 | 0x00C09F | Erased (FFh) |
| 0x1FFFE8 | 0x000018 | Footer: `00 00 2D 2D 2D 2D 7C 71` twice, then `AA` ×8 (matches the header marker) |

## Findings

- **Byte lane, not byte-wide code.** Byte histograms of even and odd chip offsets are the same, so the chip is not two interleaved lanes itself. Adjacent instruction low bytes (`22 FC`, `26 0B 09`, `0B F6`, `E6 D6 C6 B6`) show that consecutive 16-bit SH instructions put their low bytes in consecutive bytes of this chip. That requires a 16-bit bus with two ×8 chips, where this one supplies D7–D0. A 32-bit, four-chip bank would split these pairs across two chips.
- **CPU family.** The surviving low bytes match SH-1/2/3 encodings throughout 0x0004C0–0x1A1000: 29,361 × `0B 09` (`rts`/`nop`), 1,681 × `26 0B F6` (`lds.l @r15+,pr`/`rts`/`mov.l @r15+,rN` in the delay slot), and stack frames of `-4`/`-8` (`22 FC`, `22 F8`). The 256-entry pointer table at 0x000040 is shaped like an SH-1/SH-2 exception vector table. SH-3/SH-4 have no vector table, so SH-1 or SH-2 is more likely. Without the high bytes this cannot be confirmed by disassembly.
- **Vector/stub table at 0x000040.** Most entries are `80 xx`, where `xx` rises by 4 per entry (C8, CC, D0, …), wrapping through 00h. That pattern fits a table of 4-byte default-handler stubs. About 30 entries differ (indices 8, 57–68, 73, 81, 109–145). These are probably the interrupts that have real handlers. Four entries have 00h as the 23–16 byte, so they point to a different memory region.
- **Link address.** Pointers in the record table at 0x0002A0 have bits 23–16 in the range 0x80–0xB1. The image is about 0x3E8000 CPU bytes, so bits 23–16 of 0x80–0xBE would cover it. The firmware was therefore probably linked to run at a base whose bits 23–16 are 0x80 (for example `0x…80_0000`). The image may be copied to RAM or the flash may be mapped there. The high byte of the address is in the missing lane.
- **Header and footer.** The CPU-view markers `AAAAAAAA`, `AAAAAAAA BBBBBBBB CCCCCCCC DDDDDDDD` (twice, at chip 0x18 and 0x32) and the `AA…` run at the very end of the chip bracket the image. Fields between them (`34 78`, `10 FF`, `FF A0`, `FF D0`, `B4 50 AB 0F 00 A0 7D 6D 00 F0 3B E6 00 EA 99 15`) are probably sizes, addresses and checksums. The footer pair `2D 2D 2D 2D 7C 71` repeated twice is probably a stored checksum. Simple 8- and 16-bit sums of this lane alone do not match it, as expected if it covers both lanes.
- **16-bit character tables (full text visible).** At 0x1A1880 are `08 "APL 0101"` and `08 "BASE0101"`. At 0x1A1920 and again at 0x020372 are `0A "NAVIGATION    "`, `04 "NAVI"`, `09 "ﾅﾋﾞｹﾞｰｼｮﾝ"` and `03 "ﾅﾋﾞ"`. These are length-prefixed strings of 16-bit characters with the high byte (00h) in the other chip. At 0x1A1C07 a table lists half-width small kana `ｧｨｩｪｫｬｭｮｯ` followed by `9F A1 A3 A5 A7 C1 E1 E3 E5 EC`. Those are the low bytes of Shift-JIS small hiragana ぁぃぅぇぉっゃゅょゎ (`829F`…`82EC`), most likely a kana-input or text-conversion table.
- **RCS `$Header$` stamps.** More than 60 halved `$Header: … Exp $` strings, at 0x01003C–0x02DE2E, 0x1A1CEE, 0x1A748E, 0x1B56F0–0x1B589E, 0x1D4D3C, 0x1DA9F2–0x1E818C and 0x1F3F2A. They name source modules by prefix: `da_*`, `c_r_*`, `mh_*`, `nh_*`, `sh_*`, `cg*`, `ii*`, `po*`. Reconstructed date fields use two-digit years `94`–`97`, for example `1.12 96/07/1x` at 0x02DC0A. The code was therefore built from RCS-managed C sources in about 1997. Author fields are only half present and are not reconstructed here.
- **Tile and character maps.** From about 0x1A4500 there are rectangular runs of consecutive codes (`FGHIJK`, `LMNOPQ`, `/0123456789`, `ｰｱｲｳｴｵｶｷｸ`…) at a stride of 0x15 bytes. These are probably screen layouts that place consecutive character or tile cells in a grid, with attributes in the other lane.
- **No compression or filesystem.** binwalk (85 signatures) finds nothing, and the byte statistics are those of uncompressed code, not packed data. Long FFh runs appear only at 0x1A2B03, 0x1A30B3, 0x1A6582, 0x1E7621 (a few hundred bytes each) and from 0x1F3F49 to the footer.

## Device

Low confidence on the exact make and model. Medium confidence that this is the program flash of a Japanese car-navigation unit, or the navigation computer of a car AV system, from about 1997. The evidence is the `NAVIGATION`/`ﾅﾋﾞｹﾞｰｼｮﾝ` labels, half-width katakana and Shift-JIS tables, `APL`/`BASE` version tags, and roughly 3.3 MB of SH code. That code size is far beyond a simple head unit and in line with map-display firmware of the period. High confidence that it is a Hitachi SH CPU on a 16-bit bus, with this chip as the low byte lane of a two-chip bank. No manufacturer name survives in this lane. Searches for halved forms of likely vendor names (Pioneer, Alpine, Clarion, Kenwood, Xanavi, Zexel, Denso, Aisin, Panasonic, Sony, Zenrin) found no convincing matches.

## Open questions

- **Missing high byte lane.** The partner MBM29F016 holding D15–D8 is not among the dumps. With it, the image could be interleaved (partner byte first) and disassembled as big-endian SH, and the full `$Header$` paths, author names and any copyright string would become readable. Dumps 1–6, 8 and 9 do not start with the `AA AA AA AA` marker, so none of them is the partner.
- **CPU variant and memory map.** SH-1 versus SH-2 and the link base (bits 31–24) cannot be settled from one lane. With the partner lane, check the literal-pool constants for on-chip register addresses: `0x05FFFxxx` for SH7032/7034 or `0xFFFFFExx` for SH7604.
- **Header and footer fields.** The meaning of the fields between the `AAAA…DDDD` markers, and of `2D2D 2D2D 7C71`, needs both lanes. Then try a 16- or 32-bit sum over the image.
- **Second code block at 0x1F2000.** It is probably a loader or flash-update routine, but this cannot be verified without the high bytes.

## Method

I took per-sector and per-4 KB entropy, FFh and zero ratios, then hex-dumped the header, the tables and the tail. binwalk and `strings` gave almost no plain text. That, together with byte-pair statistics (`0B 09`, `26 0B`, `F6 F6` dominant), suggested instruction low bytes. Matching the patterns to SH prologue and epilogue encodings confirmed it. I searched for halved strings by taking every second character of candidate words (`Version` → `eso`, `$Header:` → `Hae:`) and reconstructed the RCS keyword strings by hand. Full-width 16-bit character tables were found by scanning for katakana and ASCII runs. The block map was rendered with a short Python/PIL script. All scratch work was done in a temp directory with `python3 -I`.
