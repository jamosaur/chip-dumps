This 2 MB image is the "FM" (flash memory) microcode load for a microprocessor board in a Hitachi enterprise disk subsystem. A small directory (`DIRDIRT` / `OBJDIRT` tables) indexes 49 compressed Intel i960 COFF objects, built with GCC 2 for VxWorks. They decompress to about 5 MB of controller microcode: RAID, cache, remote copy, error recovery, the SVP (service processor) link, and a patch module. The strongest evidence is in the modules themselves: `S66 0927.1 Copyright(C)1997,2000,Hitachi,Ltd.`, `DKC200 system`, `RAID300 A+++++++ !!`, `FM data is RAID300 DATA!!`, the Hitachi-specific terms SVP, DKC, CHA/DKA, LDEV/PDEV, HORC/HRC, and the version record `5247710300` (microcode 52-47-71-03/00).

## Findings

- **Directory format.** The table at 0x000000 starts with `DIRDIRT\0` and gives the offsets of four sub-records. Each `OBJDIRT\0` record holds a type (6, 2 or 3), four size/address words, an entry count, a second count, and then (offset, length) pairs. The pairs are contiguous and account for every byte from 0x000AA8 to 0x1A73B5.
- **Directory size fields.** In the type 6 and type 3 records the first two words are the text and data sizes rounded up to 1 KB: `0x25400`/`0x3800` against 0x25390/0x3678 in the type 6 module, and `0xE400`/`0x400` against 0xE038/0x4 in the type 3 module. The third word (`0x7400`, `0x2000`) is unknown and may be a stack or work-area size. The type 2 record holds `0x80400000`, which is the 0x400000 load base with bit 31 set. Its next words are `0x51B400` and `0x424000`. The first matches the total text plus data of all `.abs` modules, rounded up. The second probably matches the large `.bss` (0x423D70) declared by `ZSCLOADD.abs`. Its counts are 47 and 14, and 14 is the number of entries from `ACMLOADSD.abs` to `ZZPTH1D`.
- **Checksum.** The third of the six check values in `MPVRT`, `0x0DB32D55` at 0x00003C, equals the 32-bit byte sum of 0x000AA8–0x1A73B4 (all object data). This is verified. The loader module contains the message `SUM CHECK ERROR`. The other five values did not match simple byte, word or CRC-32 sums over the compressed or unpacked groups.
- **CPU is Intel i960.** The COFF magic is `0x0160` (I960ROMAGIC), stored little-endian. Section headers are 44 bytes and symbol entries 24 bytes, as in i960 COFF; `file` misreports the files as MIPS COFF. In the instruction words, opcode bytes for `lda`, `ldob`/`stob`, `mov`, `addo`, `callx` and `b` dominate. The loader references `vxIMRClear` and `vxIPNDClear`, which access the i960 Cx/Jx/Hx interrupt-mask and interrupt-pending registers.
- **Operating system is VxWorks.** The modules import `semTake`, `semGive`, `taskSpawn`, `taskDelay`, `msgQCreate`, `msgQSend`, `socket`, `connectWithTimeout`, `etherAddrResolve` and `hostAdd`. The VxWorks kernel itself is not in this image, so it probably sits in a separate boot ROM.
- **Compiler and build paths.** The modules carry `gcc2_compiled.` markers. Static symbols include source paths: `/project/iosk360h/local94/src/` for the main build and `/project/iosim20g/local66/src/` for the patch. Source names include `erra00.c`, `svp1is01.c`, `zcum04.s` and `rootsvpver_drot.c`. The symbol tables are intact, with about 6,600 distinct global names such as `_radh_chkdrv_xor`, `_stgn_spar_slot`, `_mrcs_extblrecover` and `_rcfi_ChkHdvSwaped`.
- **Loader module (0x000AA8).** This module is relocatable and links to address 0. It contains a COFF loader of its own, with messages `zldcoffOpen`, `zldcoffMod`, `zldcoffSymAdd` and `Undefined external - %s`. It also contains a gzip inflater (`invalid compressed data -- crc unmatch.`), the load-mode names `PATCHLOAD%02d` and `BUNKATSULOAD%02d` (Japanese *bunkatsu* = split), and the messages `FM loading normal end !!`, `SM valid !!` and `FM/SM both invalid`. It reads this flash (FM) or shared memory (SM), inflates each module, and links it into RAM.
- **Main microcode, first group.** The 32 `xxxLOADD.abs` modules are absolute-linked back to back from 0x41AD10 to 0x81EA30. The three-letter module prefixes match function areas in the symbols. RAD covers RAID and parity. RCF covers configuration (`FM data is RAID200 DATA!!`). MRC and HAS cover remote copy (`AHORCMNG`, `hrclmini`). ERR covers error recovery and includes a dump tool, `Errt Dump Tool Version1.0-00` and `Copy Rights(c) Honma Products 1997`. SVP covers the service-processor interface, and STG covers spare-slot handling (`_stgn_free_spar_slot`).
- **Main microcode, second group.** The 13 `xxxLOADSD.abs` modules are linked from 0x10000000 to 0x100FC440, a second memory region.
- **Version strings.** `COMLOADD.abs` contains `S66 0927.1`, which matches the 2000-09-27 build timestamps. It also contains `52475100` and `52460101`, probably compatible or previous microcode levels. The `MPVRT` record at 0x000028 gives `5247710300`, read as microcode 52-47-71-03/00.
- **Patch module.** `ZZPTH1D` (0x19808D) is relocatable and built from `acmpatch.c` … `zcupatch.c`. It overrides functions in the MRC, RCH and RSM areas, such as `_mrcs_ipairchk` and `_rchc_rscbseglayout`.
- **SVP network module (0x19C159).** This relocatable module talks to the SVP over TCP/IP sockets (`svpSend`, `svpReceive`, `SYSTEM TRACE AREA DUMP`, `<conn close>`).
- **Stale tail (0x1B0000–0x1FFFFF).** These five sectors start mid-stream. They contain .Z streams at 0x1B79D8, 0x1BC578, 0x1BC5C7, 0x1C109F, 0x1CE3E7 and 0x1F6EAF. They unpack to i960 COFF modules dated 1998-11-12 and linked at 0x1001xxxx and higher. Their symbols identify them as older DRR, ERR (156 bytes, the same size as the current `ERRLOADSD.abs`), JMA, PRO, RAD and RCH second-group modules. The last one is cut off at the end of the chip. The current image was written over sectors 0x00–0x1A only, so the tail of an older, larger microcode load survived.
- **Bus layout.** Text, gzip CRCs and COFF headers are all intact in this single byte-wide image. It does not need interleaving with any other dump.

## Device

**Hitachi enterprise disk subsystem, probably the Freedom Storage 7700E family (internal name RAID300) or an OEM version such as the HP SureStore E XP256. Medium-high confidence.** Hitachi as the maker is certain from the copyright string, and the SVP/DKC/CHA/DKA/LDEV/HORC vocabulary is specific to Hitachi's enterprise arrays. Three clues point to the RAID300 generation: `RAID300 A+++++++ !!` in the loader, `FM data is RAID200 DATA!!` / `RAID300 DATA!!` in RCF, and `DKC200 system`. The September 2000 build dates also fit the late life of the 7700E. That RAID300 means the 7700E comes from general knowledge of Hitachi's internal names (Lightning 9900 = RAID400), not from anything in the dump. The chip probably comes from a CHA (channel adapter) or DKA (disk adapter) microprocessor board. The image holds code for both the channel (`CHP`) and disk (`DKP`) processors, so it cannot tell which.

## Open questions

- Five of the six `MPVRT` check values are unexplained. Next: try sums over the unpacked text and data only, and sums per directory and per module. Alternatively, disassemble the loader's `inir_ldchk1` routine, which prints `inir_ldchk1 %08x`.
- The meaning of the third size word in the type 6 and type 3 directory records (`0x7400`, `0x2000`) is not known. Next: find where the loader parses `OBJDIRT` and trace that field.
- The difference between the `LOADD` and `LOADSD` module groups, and why the second group is based at 0x10000000, is unclear. Next: check how the loader treats each group, and find the i960 memory map of the MP board.
- Which board, CHA or DKA, the chip came from is unknown. Next: compare with a dump from a known board, or look for a board-type check in `INILOADD.abs`.
- The microcode version needs checking against a public Hitachi or HP release list for 7700E/XP256 levels around 52-47-xx.

## Method

Sector entropy and fill statistics with Python, then hex dumps of the header. I parsed the `DIRDIRT`/`OBJDIRT` tables with a short Python script, carved each entry, and unpacked them with `gzip -dc`, which handles both gzip and .Z. COFF headers, sections and symbol tables were decoded with a custom i960 COFF parser (44-byte section headers, 24-byte symbols). The architecture was confirmed from an opcode-byte histogram, since no i960 disassembler was installed and radare2 was broken. Identification came from `strings` and symbol names. The checksum was tested by summing image regions. The stale tail was found by scanning for .Z signatures beyond the directory's end, and was unpacked the same way.
