This is one of four 8-bit flash chips that make up the 8 MB flash store of a Seiko Instruments (SII) **NS-2482 Multi Access Server**, a Japanese WAN access router from 1998. The SNMP setup file inside it sets `SysDescr "SII Multi Access Server NS-2482."`, and a shell script carries the banner `Communication Server NS-2482 System Software 1998.08.31 (Ver 3.1)`. Each 64 KB sector starts with the same 48-byte unit header. A unit-number field shows that dumps 3, 5 and this one are physical lanes 0, 1 and 2 of one bank. In sector 0 the four chips hold a 68040 boot loader striped one byte per chip (`POC-IDL Ver 3.0`). Every other sector is a whole 64 KB unit of a flash file system holding 68k executables, drivers and setup scripts for a STREAMS-based, Unix-like real-time OS.

## Layout

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x30 | Unit header (unit number 2) |
| 0x000030 | 0x3D0 | Zero |
| 0x000400 | 0x3476 | Byte lane 2 of the striped boot loader `POC-IDL Ver 3.0` (needs dumps 3, 5 and a missing fourth chip) |
| 0x003876 | 0xC78A | Zero |
| 0x010000 | 0x20000 | 2 empty units (header only, unit numbers 6 and 10), zero-filled |
| 0x030000 | 0x150000 | 21 file-system units (headers plus 512-byte data blocks): 68k code, string tables, directories, scripts |
| 0x180000 | 0x80000 | 8 empty units (header only, unit numbers 98 to 126 in steps of 4), zero-filled |

## Findings

- **Unit header.** Every sector starts with `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`, then zeros up to 0x23. After that come a big-endian 16-bit unit number at +0x24, a 16-bit value at +0x26 (0 to 14), and the same 16-bit counter twice at +0x2C and +0x2E (1 to 9, possibly an erase or write count). The constants `0x0200` and `0x0080` match the layout seen in the data: 128 blocks of 512 bytes per 64 KB unit, with block 0 holding the header.
- **Lane order.** In empty and boot units, the unit number equals 4 × sector + lane. For sector 0 that gives dump 3 → 0, dump 5 → 1, this dump → 2, and for sector 31 it gives 0x7C, 0x7D, 0x7E. Unit numbers ending in 3 (0x03, 0x07 … 0x7F) appear in none of the three dumps, so a fourth chip (lane 3) existed and has not been dumped. None of dumps 1, 2 or 6 to 9 contains the header magic.
- **Striped boot loader.** Interleaving sector 0 of dumps 3, 5 and 4 one byte at a time, with a gap for lane 3, gives readable text with every fourth character missing, for example `TRA. #3.ins.ruc.ion.Vec.or` and `.POC.IDL.Ver.3.0.`. Lane 0 holds the most significant byte (big-endian). The code includes `4E7A`/`4E7B` (MOVEC) and `F498` (CINVA IC, only on the 68040 and 68060), so the main CPU is a 68040-class part. The striped image starts at chip offset 0x400 (bank offset 0x1000) with a probable header (`32 42 46 ?? 03 F6 7A ?? 00 00 2A ?? 00 00 40 ??`) and ends at chip offset 0x3875. Its strings are an exception-frame dumper (`Vector Offset`, `Effective Address`, `Format`) and boot messages (`boot parameter NG`, `not card boot`). The CPU cannot reset straight from these chips because offset 0 holds the unit header, so this is probably a second-stage loader started by a separate boot ROM. Elsewhere the file system contains `3rd Boot version 1.2 start.` and `check 2nd Boot version number NG.` at 0x162C71, which supports a boot ROM → 2nd boot → 3rd boot chain.
- **File-system units are not striped.** From 0x030200 the data is plain big-endian 68k code (`4E75` rts, `48E7` movem, `61FF` bsr.l, `4FEF` lea), so each unit sits whole on one chip. The OS reaches the bank through 8-bit accesses per chip, which puts consecutive 64 KB units on alternating chips.
- **Two programming histories.** In units the factory programmed (for example 0x040000, 0x0B0000, 0x0C0000, with +0x26 = 0 and count 1), the rest of block 0 is `00`. In units rewritten later (count 2 to 5), offsets 0x40 to 0x1FF are `FF`. Unused space and empty units are zero-filled rather than erased (`FF`), so the file system or programmer writes zeros to unused blocks.
- **Repeated unit numbers.** The same unit number sometimes appears on two chips. Unit 0x0E (0x160000 here and in dump 5) and unit 0x49 (0x110000 here, 0x0F0000 in dump 5) have identical data and differ only in the +0x26 field. Unit 0x4E (0x100000 here, 0x020000 in dump 5) is also identical. Unit 0x42 (0x0F0000 here, 0x020000 in dump 3) has different data. The +0x26 field is probably a generation number that marks which copy is current, but this is not confirmed.
- **Directory format.** Directory blocks use 32-byte entries: a 32-bit inode number followed by a 28-byte NUL-padded name. One example at 0x050C00: `traceroute` (inode 0x1B6), `vupstat`, `who`, `frstat`, `help`, `pstat`, `subifstat`. Deleted entries have inode 0, the first character cleared and a `#` appended (`\0etstat#`, `\0spfroute#`). Just before the directory, at 0x050B80, are 20-byte records that look like extent or inode entries.
- **Files seen.** Drivers `tcp.drv`, `tn.drv`, `tty.drv`, `e2prom.drv`, `en.drv`, `en960.drv`, `fr.drv`, `frnet.drv`, `ip.drv` (directory at 0x164EC2 / 0x071602). Commands `reload`, `restart`, `setupgw`, `setupif`, `show`, `telsetup`, `trace`, `tstat`, `ospfifstat`, `ospfroute`, `overrunstat` (0x098602, 0x1606C2).
- **OS.** A Unix-like kernel with STREAMS (`M_PROTO`, `M_IOCTL`, `getmsg`, TLI library `libtli`), VFS and mounts (`fs:root initialize`, `mount:%s can't read fs table`), processes and signals, and a debugger called `ddx` (`display 68000-registers`, breakpoints, symbol loader), all around 0x038900 to 0x048500. Boot-time device setup strings (`open-flash 0`, `flash-pt-push`, `open-ramd`, `open-mc 0`) show the root file system sits on the flash with a RAM disk and a memory card (`MCard`). The flash devices are named `FLASH1`/`FLASH2`, with `SRAM` and an `e2prom` (0x092DF2).
- **Second CPU.** Interrupt and DMA dumps for `CICR`, `CIPR`, `CIMR`, `CISR`, plus `SDMA bus error`, `QMC BD memory get` and `<spiParameterRAM>`, are the CPM registers and QMC microcode of a Motorola MC68360 QUICC. Combined with the 68040 code, this is probably a 68040 with a 68EN360 in companion mode.
- **Network functions.** ISDN layer 1/2: S/T interface states `F0(POWER OFF)`, `F3(LOST-SIG)`, `INFO0/2/4`, LAPD/LAPB statistics, `l2stat`. Also frame relay with LMI (`<< LMI message information >>`, `frstat`, DLCI), PPP (LCP/NCP status), IP with OSPF (a large `OSPF:[...]` debug table at 0x064E22), ARP, SNMP MIB-II plus private `nse*` objects (`nseSysCpuLdTLoad`), telnet and traceroute. WAN port names run `P1-1` to `P3-8` plus `P1-WAN` to `P3-WAN` (0x1712AE), which suggests 3 line-card slots of 8 ports. `RSR-B8ZSD` and `OptionA 0.6dB/1.2dB/1.8dB` point to a T1 (B8ZS) framer with line build-out settings.
- **Script language.** Setup and shell scripts are written in a proprietary Pascal-like language with `$`-builtins (`$PR[$STDERR[];"OK\n"]`, `$PUSH["pt";4;"";-1]`, `SYMLINK["/usr/etc";"/tmp/etc"]`, `FUNCTION main[]`). The interpreter's symbol table is at 0x0AA170 and 0x0B56E6. The scripts mention `/usr/setup/common/hostname`, `/usr/setup/common/pw` and a version-up server `/share/vupd`. One comment is dated `obsolete 1998.3.11`.
- **No site data found.** No IP addresses or host names other than `127.0.0.1` appeared in this chip's portion.

## Device

**Seiko Instruments (SII) NS-2482 Multi Access Server**, system software Ver 3.1 dated 1998-08-31. Confidence: **high** for the product, from the `SysDescr` string and the version banner. It belongs to SII's NS-series communication servers, a line SII Network Systems still sells as the SmartCS range. The hardware details are **medium** confidence and come from the code: a 68040-class main CPU, an MC68360 QUICC companion, four MBM29F016 chips (8 MB) as a byte-striped bank holding the boot loader and file system, an EEPROM, SRAM, a memory-card slot, Ethernet, and ISDN, T1 and frame-relay WAN ports.

## Open questions

- **Fourth chip.** Lane 3 (unit numbers ≡ 3 mod 4) is missing. Without it the boot loader is three-quarters complete and a quarter of the file-system units are absent. Next step: check whether another dump of this chip type, possibly from a different seller lot, has the `24 11 00 80` header with unit number 3 in sector 0.
- **Header fields.** The meanings of +0x26 and +0x2C/+0x2E are guesses. Next step: disassemble the flash driver (near the `FlashEEPROM: No Memory.` and `[ERASE TO]` strings at 0x039300) to find the code that reads these fields.
- **File-system reconstruction.** The inode/extent record format (20-byte records at 0x050B80) is not decoded, so files have not been extracted. Next step: decode one inode-to-block mapping using a file whose contents are known, such as the `snmpd` setup text at 0x11DA24, then rebuild the volume from dumps 3, 4 and 5.
- **Boot entry point.** The image header at bank offset 0x1000 is only partly read because every fourth byte is missing. Next step: confirm the load address and the entry branch once lane 3 is available, or recover the missing bytes from opcode context.

## Method

I mapped entropy and fill per 64 KB sector with a short Python script, then hex-dumped sector starts. The repeating 48-byte header and its unit-number field, compared across dumps 3, 4 and 5, gave the lane order. I interleaved sector 0 of the three dumps byte by byte with a placeholder for the missing lane, which recovered the boot-loader text. I ran `strings` over the rest of the image and searched for directory-entry patterns. Comparing 512-byte block hashes against every sibling dump found shared units with dumps 3 and 5 only. I decoded 68k opcodes by hand from hex because the local radare2 install was broken, and confirmed the product name with a web search for the `SII ... NS-2482` string.
