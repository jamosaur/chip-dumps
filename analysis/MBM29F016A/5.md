This chip comes from the on-board "Flash Rom" of an SII (Seiko Instruments) **Multi Access Server NS-2482**, an ISDN and frame-relay router running Seiko's STREAMS-based **NS-OS 3.1** on a 68k-family CPU. The snmpd setup file stored in it sets `SysDescr "SII Multi Access Server NS-2482."` (0x0FD9FE). Every 64 KB erase unit starts with the same flash-translation-layer (FTL) header (`24 11 00 80 …`), and the FTL stores each unit's data in plain byte order. The first unit is different. It holds every fourth byte of a 68k program (the POC-IDL loader), so the chip was byte lane 1 of a 32-bit bus with four chips. The FTL drives each chip as a separate byte-wide device, and its unit numbering shows the four-chip interleave. This chip holds 31 of the volume's 128 logical units. The rest are on the three partner chips.

## Layout

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 64 KB | Logical unit 0x01, erase count 0. FTL header at 0x000000; 0x000040–0x0003FF is zero, except `FB` at 0x0001FF. From 0x000400 to about 0x003874: byte lane 1 of a 32-bit 68k program image (POC-IDL loader, code at CPU flash offset about 0x1010) |
| 0x010000 | 64 KB | LU 0x05: header, then all zero |
| 0x020000 | 64 KB | LU 0x4E: file data. Indirect block list at 0x028400, `abcd` load module at 0x02E000 |
| 0x030000 | 64 KB | LU 0x0D: header, then all zero |
| 0x040000 | 640 KB | LU 0x41, 0x19, 0x1A, 0x1E, 0x21, 0x26, 0x2A, 0x2F, 0x33, 0x36: file data (68k executables, `.r` modules, setup scripts and text files) |
| 0x0E0000 | 64 KB | Spare (transfer) unit: `24 11` then erased `FF`, with only the word at 0x0E0026 = `0007` written |
| 0x0F0000 | 576 KB | LU 0x49, 0x48, 0x45, 0x47, 0x50, 0x54, 0x56, 0x0E, 0x5E: file data. LU 0x0E (0x160000) holds the root directory |
| 0x180000 | 512 KB | LU 0x61, 0x65, 0x69, 0x6D, 0x71, 0x75, 0x79, 0x7D: header, then all zero |

## Findings

- **FTL unit header (64 bytes, big-endian words).** It is identical in every used unit except for three fields. Bytes 0x00–0x23 are `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20` followed by zeros. That probably encodes 128 units, 128 blocks per unit, 512-byte blocks and 32 units per chip. 0x24 is the logical unit number. 0x26 is probably the erase count: it is 0 on the units that still hold factory data and 7 on the spare unit. 0x2C and 0x2E hold the same value (1–4), whose meaning is unknown. Block 0 of each unit is the header. Blocks 1–127 (0x0200–0xFFFF) hold data.
- **The logical unit numbers confirm the addressing.** Joining the units in logical order makes code and tables run on across unit boundaries:
  - LU 0x48 ends with `2A BC F0 F0` (0x10FFFC) and LU 0x49 begins with `F0 F0` (0x0F0200), which together make `move.l #$F0F0F0F0,(a5)`.
  - LU 0x47 ends in a `bsr.l` whose displacement finishes at the start of LU 0x48 (0x100200).
  - LU 0x19 and 0x1A carry one 20-byte record table across the boundary.
- **File-system block address = LU × 127 + (offset − 0x200) / 512.** The root directory is at FS block 0x6F2, the first block of LU 0x0E (0x160200). The indirect block at FS block 0x26F3 (0x028400) holds `00 00 26 F4`. Block 0x26F4 (0x028600) lists the consecutive data blocks 0x26F5–0x2720. With 128 units of 127 blocks, the volume has 0x3F80 blocks (about 8 MB), which is four times this chip's capacity. Block 0x26F4 lies in LU 0x4E, which is on this chip.
- **Four-chip interleave.** Every unit that was never rewritten (erase count 0) has a logical number of 4 × (physical unit) + 1: 0x01, 0x05, 0x0D, 0x21, 0x61 … 0x7D. The volume was therefore formatted with logical unit = 4 × sector + chip, and this is chip index 1. Units that were later moved by garbage collection (0x4E, 0x41, 0x0E …) break the pattern.
- **Directory format.** A directory block has 32-byte entries: a 4-byte big-endian inode number and a 28-byte name, starting with `.` and `..`. The root contains `admin bin boot.3rd bootconf driver etc init init.root mnt mnt2 mnt3 nsx.sys pocvup save`. Other directories here are `admin` (`arch ifconfig flPurge flPush flftp …`), `bin` (`ping telnet netstat ospfroute …`) and `driver` (`QMC.drv QCH.drv MCardI.drv en.drv en960.drv fr.drv l2ctl.drv l2hsd.drv e2prom.drv …`). The inode table is not on this chip.
- **Executable format.** 68k load modules start with the magic `AB CD 02 00 05 32 00 00 06 55 06 55 06 55`. They have a section count at 0x0E, a 32-bit header size (0xF0–0x120) at 0x28, the code size at 0x2C and 28-byte section entries from 0x50 named `code const string data ram`. Two are visible in place at 0x02E000 and 0x0A0200, and 48 in the reassembled logical space.
- **Code is 68k for a 68020-class or CPU32 core.** Frequent `4E75`, `48E7`, `4CDF`, `4E71` padding to 4-byte function alignment, and `61FF` (`bsr.l`). The `QMC.drv`, SCC and `qmcno` references point to a Motorola MC68360 QUICC (CPU32+) with QMC microcode. That last point is an inference.
- **Unit 0x000000 is one byte lane of a 32-bit image.**
  - The text in it reads at stride 4: `- 26AE159d0X` at 0x000E46 is every fourth character of `0123456789ABCDEF` / `0123456789abcdef`.
  - Byte pairs such as `DF 75 E7 6F` are lane samples of `4CDF xxxx 4E75 4E71 48E7 xxxx 2A6F`.
  - Taking every fourth byte of the `POC-IDL Ver 3.0` / `Pocvup version 1.0` load module stored in the file system (logical LU 0x48, physical 0x0F0B20 area) reproduces long runs of this unit. The code section's first word `613C` lands at chip offset 0x000404, so file code offset c sits at CPU flash offset c + 0x1010 in lane 1. The flash header area at 0x0000–0x0FFF is not part of the image.
  - Some runs are shifted by 0x200 CPU bytes and some do not match at all, so the lane copy is a slightly different build from the file.
- **Factory zero fill.** Units never rewritten since programming have `00` in 0x40–0x1FF and in all unused data. Units the FTL rewrote in service have `FF` there. The image was most likely programmed from a file in which empty space was zero.
- **Firmware identity strings.**
  - `NS-OS version 3.1 start.` (0x10F600)
  - `3rd Boot version 1.2 start.` (0x162C71, the `boot.3rd` file)
  - `POC-IDL Ver 3.0` (0x0F0BE8)
  - `POC-vup Flash Rom Write Error.` (0x0F0B59)
  - The `init.boot` script (0x167000) chooses between `# Flash Rom boot` and `# Mem Card boot`.
- **Protocol stack strings.** ISDN layer 2 (`L2CTL:(%x)Layer1 Not Ready`, 0x04021A), INS1500 (Japanese primary-rate ISDN) port setup, frame relay (`FR:%d,OVER MAX FLAME SIZE(%u)`), PPP, OSPF, SNMP, telnet and FTP. User setup files (hosts, SNMP communities) are present. Site-specific values in them are not reproduced here.

## Device

**Seiko Instruments (SII) Multi Access Server NS-2482**. Confidence is high for the product, from the `SysDescr` string, `sii` route entries and the NS-OS strings. Confidence is medium for the board position. This chip is the second byte (lane 1, D23–D16) of a 32-bit Flash ROM bank of four MBM29F016A, 8 MB in all. The bank holds the CPU-executable POC-IDL loader at its start, lane-split across the chips. After that, the bank is used as an FTL flash disk in which each chip is driven byte-wide.

## Open questions

- **Inode table and superblock.** They are on other chips, because no inode-like table was found in the 31 units here. Next step: reassemble the volume with the partner chips (logical unit = header word 0x24) and parse blocks 0x000–0x6F1.
- **Header words 0x2C/0x2E (values 1–4) and the `FB` byte at 0x0001FF.** Their meaning is unknown. Compare with the same fields on the partner chips.
- **Version of the lane-split loader.** It differs from the POC-IDL file in the FS. The other three lanes are needed to rebuild it, then diff it against the file.
- **CPU.** MC68360 is inferred from the driver names. Disassembling `QMC.drv` or the loader's start-up code for QUICC register accesses (MBAR at 0x0003FF00) would confirm it.

## Method

I used Python (`-I`) for per-sector entropy and fill maps, `xxd`, `strings` and `binwalk`, which found no known signatures. I decoded the 64-byte unit headers and rebuilt a sparse logical volume by placing each unit's 0x200–0xFFFF at LU × 0xFE00. Code continuity across unit boundaries checked the ordering. I parsed directory blocks (4-byte inode + 28-byte name) and listed `AB CD 02 00` load-module headers. I identified unit 0 as a stride-4 lane by trying address-bit permutations (all failed), looking at 68k byte-pair statistics, and searching its 16- and 24-byte runs against every-fourth-byte slices of the reassembled volume. I rendered the unit map with Pillow.
