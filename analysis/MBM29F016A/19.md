This 2 MB image is one chip of a four-chip flash array that held the file system of a Seiko Instruments (SII) **NS-2482** "Multi Access Server": a Japanese communication server and WAN router built on a Motorola MC68360 QUICC. Each 64 KB sector is a file-system unit with its own 48-byte header, followed by 127 blocks of 512 bytes. Those blocks hold whole, contiguous files: 68k executables, `init.conf` scripts and directory and inode blocks. The blocks are not interleaved, even though the chip sat on a 32-bit bus. The device is named by the SNMP string `SysDescr "SII Multi Access Server NS-2482."` and the header line `Communication Server NS-2482 System Software 1998.08.31 (Ver 3.1)`. One region differs: sector 0 holds every fourth byte of a 68k boot/IPL program (byte lane 2). Its full copy is also stored as a normal file in this chip's file system, which shows that the array was also read as linear 32-bit memory.

## Findings

- **Unit header** (every sector, offset +0x00): `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`, then zeros up to +0x24. The words probably include a magic `0x2411`, 0x0080 (128 blocks per unit) and 0x0200 (512-byte block). At +0x24 is a big-endian u16 logical unit number, at +0x26 a u16 that is probably an erase or generation count (0–12), and at +0x2C/+0x2E a u16 status written twice (values 1, 2, 3, 4, 0x13). Bytes +0x30–0x3F are zero. +0x40–0x1FF are FF in units with status 2/3/4 and zero in units with status 1.
- **Logical block addressing is verified**: logical block = unit × 127 + (offset − 0x200)/0x200. The inode at 0x100200 lists blocks 0x24B4/0x24B5. Block 0x24B4 is unit 0x49 index 125, which is offset 0x11FC00 in sector 17. That block holds the text `# command interpreter setup`, matching the inode's size of 727 bytes.
- **Unit numbering points to four chips.** Every untouched unit (generation 0, all zeros) has logical number 4 × sector + 2: 0x02, 0x06, 0x0A, 0x12, 0x2E, 0x32, 0x62 … 0x7E. Units that were rewritten carry other numbers (0x09, 0x0E, 0x10 … 0x5F). The highest number, 0x7E, implies 128 logical units, or four 2 MB chips (8 MB). The format numbered units across the chips (unit = 4 × sector + chip), so this is chip index 2.
- **Inodes** are 128 bytes (sector 16): a u32 mode written as hex digits (`0x0755`, `0x0664`, `0x0777`), u16 link count at +4, u32 size at +0x0A, three Unix times at +0x16, +0x1A and +0x76, u16 block count at +0x20, and u32 block numbers from +0x22. The 110 records show creation `1998-08-31`, modification `1999-07-12` and the latest access or change `1999-07-17 02:04` UTC.
- **Directory entries** are 32 bytes: a u32 inode number and a 28-byte NUL-padded name. Root directory (0x160200): `admin bin boot.3rd bootconf driver etc init init.root mnt mnt2 mnt3 nsx.sys pocvup save`. Driver directory (0x164E00): `MCardI.drv QCH.drv QMC.drv am.drv e2prom.drv en.drv en960.drv fifo.drv fr.drv frnet.drv ip.drv ipnhr.drv l2ctl.drv l2hsd.drv …`.
- **Executables** use a private header: magic `AB CD 02 00 05 32 00 00 06 55 06 55 06 55`, a header length of 0xF0/0x100/0x110 at +0x28, sizes at +0x2C/+0x30/+0x34, and a section name `code` at +0x50. There are 60 headers on this chip, each at the start of a 512-byte block (for example 0x03F400, 0x040200, 0x069400).
- **CPU**: hand-decoded 68k code throughout, for example at 0x110214 `48E7 010C` (movem.l), `286F 0010`, `D0B9 0000B1A8`, `4CDF 3080`, `4E75`. The image contains 4011 `4E75` and 2078 `4CDF` patterns. The CPM interrupt registers `CICR/CIPR/CIMR/CISR` and the text `SDMA bus error` (0x038963 onward) identify an MC68360 QUICC, and `#---- SI(QUICC Serial Interface)` appears at 0x142C9F.
- **Software**: a Unix-like RTOS with STREAMS drivers, a VFS, and an `init.conf` scripting language (`$BIND["/driver/udp.drv"]`, 0x0A4200). It includes OSPF, IPX, AppleTalk (`ddp.drv`, `enlap.drv`), frame relay, ISDN LAPD, HSD leased lines, SNMP, telnet and FTP, plus a `ddx` debugger (`------  68000 REGISTERS -------`, 0x0476F7). The kernel's error strings start around 0x038900 (`BusError(SR:%04X PC:%08X EA:%08X SSW:%04X FA:%08X)`).
- **Boot setup** (0x092C00): boot mode `mem|net|auto`, core dump to `SRAM`, `FLASH1` or `FLASH2` cards of 1, 2, 4 or 8 MB, and `Serial No.`/MAC address prompts.
- **Flash updater and IPL**: the file in sector 17 contains `Pocvup version 1.0 start.` (0x110B20), `POC-vup Flash Rom Erase Error.`, `POC-IDL Ver 3.0 ` (0x110BE8), a 68020/030 exception-name table and T1/E1 line-status text (`CCITT Recommendation G.703`, `FCC Part68,OptionA`, `TAOS active`).
- **The sector 0 data is byte lane 2 of that program** (verified). Taking every fourth byte of the stride-1 copy, at phase 2 from a 512-byte block boundary (0x10DCDA + 4k, with one 0x200 step where the file crosses a block gap), reproduces chip 0x001050–0x003875 exactly. The giveaway is `37BF26aex` at 0x3860. It is every fourth character of `0123456789ABCDEF\0` `0123456789abcdef\0` `0x`, which is stored in full at 0x110B7F. The earlier lane bytes (0x000410–0x000E70) match library code that is also present elsewhere in the file system. The lane image ends where the file-system copy's T1/E1 strings begin (`NqReset has occurred,or no program input`, 0x11ACAE), so it is probably an older build of the same program.
- Free and deleted blocks are zero, not FF. Erased flash would read FF, so the file system probably zeroes discarded blocks instead of erasing them. That fits unit 0x09, where only the 28 blocks of inode records hold data and the other 99 are zero, and the fully zeroed generation-0 units.

## Device

**Seiko Instruments (SII) NS-2482 Multi Access Server**, running system software Ver 3.1 dated 1998.08.31. Confidence is **high**, because the image contains both the product's SNMP `SysDescr` string (0x11DA0C) and the system-software banner (0x149004). The firmware matches a communication server or access router with Ethernet, ISDN, HSD, frame relay and T1/E1 interfaces, built on an MC68360. The chip was one of four MBM29F016A on a 32-bit bus, forming an 8 MB flash array: probably an on-board file-system flash, or possibly one of the `FLASH1`/`FLASH2` memory cards the setup menu mentions. The file-system driver addresses each chip as its own byte-wide device. This chip carries data bits D15–D8 (lane 2, counting 0 as the most significant).

## Open questions

- **Header field meanings.** Status values 1–4 and 0x13, and the +0x26 counter, are only inferred. Comparing with the other three chips, and with an erase-and-rewrite sequence, would settle them.
- **Why the lane image sits in unit 0 of a file-system array.** The header bytes at chip offset 0 rule out booting the 68360 directly from CPU address 0 of this array. More likely a boot ROM jumps to the IPL at array offset 0x1000. Interleaving sector 0 of all four chips would rebuild the 56 KB program and show its vector table or entry point.
- **The superblock, root inode table and free map** are not on this chip. Look for them in the other three chips, especially in their low units.
- **`nsx.sys`** (inode 467) is presumably the OS image. Its blocks and inode would need the full array.
- **Which `.r` libraries and drivers map to which ABCD files.** That needs the inode table for inodes 1–470, which is held on the partner chips.

## Method

Python (`python3 -I`) scripts in a temp directory computed per-sector entropy and zero/FF fill, then classified each 512-byte block. They also decoded the 32 unit headers, scanned for 128-byte inode records (validated by timestamp ranges) and 32-byte directory entries, and checked the logical-block formula against a known inode. `strings` and `grep -b` located identifying text. The lane hypothesis was tested by searching for 16-byte probes from sector 0 in every stride-4 phase of the whole image. The 68k code was decoded by hand from common opcodes, because no m68k disassembler was installed. The block map was rendered with Pillow.
