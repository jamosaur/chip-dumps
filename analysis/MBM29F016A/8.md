This chip holds every fourth byte of a 32-bit-wide flash array, with data lines D0 and D2 swapped. The first 1.07 MB is one lane of compressed data. It ends in a lane-split ZIP central directory entry and end-of-central-directory record, which only decode once D0/D2 are swapped back. After the archive comes about 36 KB of log text, also lane-split, with record headers, banner lines and 83-character memory-dump lines. The rest of the chip is erased. The evidence for the stride and the bit swap is listed below. The chip cannot be read on its own: the file name, the archive start and readable log text all need the other three lanes.

## Layout

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x10B895 | Compressed data, entropy 7.96 to 7.99 bits per byte: one lane of the ZIP member's deflate (or similar) stream. It contains a short run region at 0x106E6E to 0x106F6F (FCh, F8h, 88h, 3Fh, C4h runs once swapped). |
| 0x10B895 | 0x14 | One lane of a ZIP central directory header (byte 1 of each 4-byte group) and the EOCD record |
| 0x10B8A9 | 0x0D | Unexplained bytes after the EOCD, possibly a ZIP comment or padding |
| 0x10B8B6 | 0x10 | Log record header (`BA 00 xx 00` + `cho0009`) and 5 × FFh |
| 0x10B8C6 | 0x8C9D | Lane-split ASCII log (CR/LF text) with more 16-byte record headers at 0x10F7A4, 0x10F8A5 and 0x1120CD |
| 0x114563 | 0x0EBA9D | Erased (FFh) to the end of the chip |

## Findings

- **Data bits D0 and D2 are swapped.** Brute-forcing all 8! data-bit permutations against character statistics of the text region picks D0<->D2. The ZIP structures confirm it independently. Raw `4E` and `03` become `4B` (`K`) and `06`, exactly where the ZIP signatures `PK 01 02` and `PK 05 06` put them. Every structure below is quoted after the swap unless it says "raw".
- **The bus is 32 bits wide and this chip is one byte lane (stride 4).** The log has 110 segments of the form `LF <61 chars> CR <20 chars> LF`. This is what one lane shows of identical 83-byte lines (81 characters plus CR LF): 83 ≡ 3 (mod 4), so the CR and LF fall in this lane once every four lines, splitting them 3:1. In all 110 the only colon is at index 22, which is character 8 of the second line. That matches a `XXXXXXXX: ` address field. A stride of 2 cannot produce this. Pairing physically adjacent bytes scores best under a bigram test, so the address lines are in order.
- **ZIP central directory entry, lane-split (0x10B895).** Lane bytes `4B 00 00 7A 66 75 2C 00 00 00 00 00 34 45 4E` (raw `4E 00 00 7A 63 75 29 00 00 00 00 00 31 45 4B`) are bytes 1, 5, 9 … 57 of a `PK 01 02` header:
  - `K`
  - version-made-by high byte 00 (MS-DOS)
  - flags high 00
  - modification time high byte 7Ah (15:16 to 15:23)
  - CRC byte 1 = 66h
  - compressed-size byte 1 = 75h
  - uncompressed-size byte 1 = 2Ch
  - name-length high 00
  - comment-length high 00
  - internal-attributes high 00
  - external-attributes byte 3 = 00
  - local-header-offset byte 3 = 00
  - name characters 3, 7 and 11 = `4`, `E`, `N`

  The EOCD signature byte (06h) follows at 0x10B8A4, which fixes the name length at 12, an 8.3 name of the form `???4???E.??N`. The extension is probably `.BIN`.
- **EOCD (0x10B8A4).** Lane bytes `06 00 00 00 00` are EOCD bytes 3, 7, 11, 15 and 19: signature, CD-disk high, total-entries high, CD-size byte 3 and CD-offset byte 3. The archive is under 16 MB. Only one central directory entry is visible in this lane, so the archive probably holds a single file.
- **The archive does not start on this chip.** No lane-split local header with the same name is present. Offset 0x000000 holds `49` (raw `4C`), which is none of `50 4B 03 04`. This lane alone holds about 1.07 MB of compressed data, so the four lanes of this bank hold about 4.3 MB. The local header and the start of the data are probably in a lower bank of chips.
- **Log record headers.** There are four 16-byte slots: 0x10B8B6, 0x10F7A4, 0x10F8A5 and 0x1120CD. Each holds `BA 00 xx 00`, then `cho` and four digits, then five FFh or 00h bytes. The slot at 0x10F7A4 holds `BA 00 AE 00 47 00` and FFh, as if the write was interrupted. Examples: `BA 00 7C 00 cho0009` (raw `BA 00 79 00 66 68 6F 30 30 30 3C`), `BA 00 09 00 cho0009` and `BA 00 D5 00 cho0017`. The `cho` digits come out contiguous in this lane, unlike the log text. The header was probably written one byte per 32-bit word, but that is unverified. The same lane-split first line, `Co4R0rs vox h1/4y mr`, follows two of the headers.
- **Log content.** One lane is not readable as words, but the structure is clear:
  - **Banners:** `==h laCkers=====`, `==MonrTe=====`, `==acders=====` and `===osvI ====`.
  - **Register-style lines:** e.g. `FFr=FF3 FFr=FF3 FF7FF`.
  - **A fixed-width table:** 9-character rows such as `00   tMd`.
  - **A message:** repeated more than 120 times with an incrementing counter (`…36Cir2`, `…37Cir2` …).
  - **Timestamps:** a digit after `':` that runs 4, 5, 0, 1, 2, which looks like the tens digit of seconds or minutes.
  - **Memory dumps:** an 8-digit address and eight 32-bit words per line, values right-aligned with spaces (`       0`). Rebuilding the visible address digits from groups of four lines gives addresses of the form `62xxxxxx` (for example 0x6231235x, 0x6252E6E8 and 0x624C1D64), stepping 0x20 per line. This looks like crash or diagnostic output, most likely exception reports with register and stack dumps.

## Device

Unknown, low confidence. The image comes from a 32-bit system with at least four, and probably eight or more, MBM29F016A chips as a 32-bit flash array with D0/D2 crossed on this chip. The flash holds a ZIP-packaged firmware file (probably `….BIN`) and the device's own text crash/debug log, written after the archive. The memory dumps point to RAM or a mapped region at 0x62xxxxxx. Nothing in this lane names the CPU, the maker or the product.

## Open questions

- **Lane index.** Which of the four lanes this chip is cannot be told from this image alone. Next: align with the partner chips. The lane holding `P` at the `PK 01 02` header (same offset 0x10B895) sits one byte before this one.
- **Archived file name and size.** Next: get name characters 0 to 2, 4 to 6 and 8 to 10, and the CD size and offset, from the other three lanes at 0x10B895 to 0x10B8A8.
- **Compression method and contents.** The method high byte is in a lane not seen here. Next: interleave the four lanes, prepend the lower bank and inflate.
- **The 13 bytes at 0x10B8A9** (`00 00 FE 43 4F 53 53 FA 00 41 2C 1D BB`). Next: check the EOCD comment-length field in the lane holding EOCD byte 21.
- **CPU architecture.** Next: rebuild the log from all four lanes and read the register names in the crash dumps.

## Method

The image was swept with Python in 64 KB sectors and 1 KB blocks for entropy, FFh/00h counts and printable ratio, and binwalk found no signatures. I brute-forced data-bit permutations by scoring the text region, then checked address order with a bigram test. To find the bus stride, I looked at how CR and LF fall in the lane and where the colon sits in the dump lines. Applying the D0/D2 swap let me decode the lane-split ZIP central directory and EOCD field by field. I rebuilt partial hex-dump lines by placing each lane character at line position 3, 0, 1 or 2 (mod 4). All scripts ran in a temporary directory with `python3 -I`, and the dump was not modified.
