This chip is one of four 8-bit flash chips on the 32-bit bus of an MC68360 (QUICC) based communication server. A configuration script in the image names it: `Communication Server NS-2482 System Software 1998.08.31 (Ver 3.1)` (0x149000) and `SysDescr "SII Multi Access Server NS-2482."` (0x11D9FE). The OS treats each chip of the bank as its own byte-wide device. Every 64 KB sector is a file-system unit with a 64-byte header, followed by 127 blocks of 512 bytes. Files therefore read contiguously on this chip. Sector 0 is the exception. It holds one byte in four of a boot program (`POC-IDL Ver 3.0`) that the CPU runs from the full 32-bit bank. The unit numbering and the byte phase of that boot image both put this chip on byte lane 2: data bits D15–D8, with lane 0 the most significant byte.

## Layout

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x000040 | Unit header (unit id 0x0002), the same format as every other sector |
| 0x000040 | 0x0003C0 | Zero |
| 0x000400 | 0x003476 | Lane-split boot image `POC-IDL Ver 3.0`, every 4th byte (CPU bank offsets 0x001002–0x00E1DA, phase 2) |
| 0x003876 | 0x02C78A | Zero (rest of sector 0, plus sectors 1 and 2 apart from their headers) |
| 0x030000 | 0x150000 | File-system units in sectors 3–23: 68k executables (`ABCD 0200` headers), drivers, interpreted setup scripts, directories. Obsolete blocks are zeroed |
| 0x180000 | 0x080000 | Sectors 24–31: unit header only, the rest zero (fully obsolete or never-used units) |

## Findings

- **Unit header** (every sector at +0x00). The first 0x24 bytes are identical in all 32 sectors: `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`, then zeros. Read as big-endian 16-bit words, it contains 0x0080 (128 blocks per unit), 0x0200 (512-byte blocks) and 0x0020 (32 units per chip). The fields that vary are at +0x24 (unit id), +0x26 (a small counter, 0–0x0E, probably an erase or reclaim count) and +0x2C/+0x2E (the same value repeated, 1–5). The rest of the header block is `FF` in units that have been rewritten and `00` in units still in their original state.
- **Unit ids show the 4-chip, per-lane numbering.** The untouched units carry ids 0x02, 0x06, 0x0A (sectors 0–2) and 0x62, 0x66 … 0x7E (sectors 24–31), which is exactly 4 × sector + 2. Rewritten units carry other ids from the same 0–0x7F range, for example 0x10, 0x12, 0x18 and 0x4E. The volume has 128 units across four chips, and this chip was originally formatted as chip/lane 2.
- **No erased space.** Every data block is either live data or zero. There are no all-`FF` blocks, so obsolete blocks are marked by programming them to `00` (see the block map). The logical-to-physical block map is not stored in the unit headers. It probably lives in a map file or on the other chips (`Warning:Map synchronization fail<dev:%s>`, 0x39221).
- **Directories.** The directory format is 32-byte entries: a 4-byte inode number followed by a 28-byte name. The first block of each of four directories is on this chip:
  - root at 0x160200: `admin bin boot.3rd bootconf driver etc init init.root mnt mnt2 mnt3 nsx.sys pocvup save …`
  - `/admin` at 0x160400: `ar arch bind boardinf cp ddx debfunc debug df flPurge flPush flftp ifconfig iostat …`
  - `/bin` at 0x160600: `date linestat mstat netstat ospfifstat ospfroute overrunstat page passwd ping settty su telnet tnstat …`
  - `/driver` at 0x164E00: `MCardI.drv QCH.drv QMC.drv am.drv e2prom.drv en.drv en960.drv fifo.drv fr.drv frnet.drv ip.drv ipnhr.drv l2ctl.drv l2hsd.drv …`
- **Executable format.** 59 blocks start with the magic `AB CD 02 00` (for example 0x03F400, 0x10E000, 0x160800 and 0x165200). The header continues `05 32 00 00 06 55 06 55 06 55 00 04`, followed by size fields (0x03F400: `0000 0110`, `0000 AFCC`, `0000 BAA8`, `0000 BAA8`) and at +0x50 a segment name (`code` or `ram`). This is probably the OS's own load-module format. The code is 68020+ (`61FF` BSR.L, `4E75`, `48E7`/`4CDF` MOVEM), for example at 0x030200.
- **CPU is an MC68360 QUICC.** Exception reports print the CPM interrupt registers `CICR`, `CIPR`, `CIMR`, `CISR` (0x38963), and there are `SDMA bus error` (0x389BF), `QMC BD memory get` (0x38E94) and `#---- SI(QUICC Serial Interface)` (0x142C9F) strings.
- **Boot chain.** `boot.3rd` (code around 0x160800–0x163100) prints `3rd Boot version 1.2 start.`, `check 2nd Boot version number NG.`, reads `/bootconf` and loads `/nsx.sys` from `Memory Card` or `Flash Rom` (0x162C71–0x162DCC). `pocvup` (0x110B20: `Pocvup version 1.0 start.`, `POC-vup Flash Rom Write Error.`) rewrites the flash boot area.
- **Lane-split boot image in sector 0.** Sampling `pocvup`'s data at 0x110EDA–0x11B2xx with a stride of 4 reproduces this chip's 0x001100–0x003876 byte for byte. The relation is chip offset L = (file offset − 0x10CCDA) / 4, with one 512-byte step in the file at L ≈ 0x1500. `pocvup` therefore carries the full 32-bit boot image, and this chip holds the bytes at offsets ≡ 2 (mod 4). The `POC-IDL Ver 3.0 ` string appears lane-split at 0x001044 (`CLr0`). The lane's C `ctype` table at 0x000E60 (`00 20 20 28 28 20 20 20 20 10 10 10 10 04 04 04 10 81 81 01 …`) is the standard table sampled at entries 2, 6, 10 …, which again fits lane 2 if the table is long-aligned. The image also contains 68k exception names (`Reset Initial Interrupt Stack Pointer`, lane-split at 0x00365F) and T1/E1 line-interface diagnostics (`Remote Loopback active`, `CCITT Recommendation G.703`) that appear in clear at 0x11A653–0x11ADFD.
- **Network OS content.** The image contains a `ddx` debugger (0x470BC, with `68000 REGISTERS` and commands such as `MD`, `BS` and `LDM`), a streams/VFS kernel (`panic(os)`, `[OS-res-loader:load %s at %08x (size %x)]` at 0x38DE9), OSPF, SNMP (`snmpInBadVersions`), telnetd, frame relay (`frdte1`, `inarpd`), PPP (`LCP`/`NCP CONNECTION STATUS`) and IPX/AppleTalk options. There are interpreted setup scripts in a Pascal-like language (`VOID FUNCTION buildVLif[p:LIST]`, `$SYS[WAIT;…]`, 0x144C00) and a comment dated `obsolete 1998.3.11` (0x145E59).

## Device

**Seiko Instruments (SII) NS-2482 "Multi Access Server" / communication server, system software Ver 3.1 (1998-08-31). Confidence: high** for the product, because both the SNMP `SysDescr` and the init script header name it. A web search found SII's later NS-2240/NS-2250 console servers but nothing on the NS-2482 itself. The hardware is an MC68360 with four MBM29F016A chips forming an 8 MB 32-bit flash bank, plus a PC-card memory slot (`MCardI.drv`, `Memory Card`), an EEPROM (`e2prom.drv`), Ethernet (`en.drv`, `en960.drv`) and serial/WAN ports through the QUICC SCCs and QMC, with T1/E1 line interfaces. The reset vectors cannot be at bank address 0, because that address holds the interleaved unit headers. The `3rd Boot` / `2nd Boot` messages suggest that a first-stage boot ROM elsewhere jumps to POC-IDL at about 0x1000 in this bank.

## Open questions

- How the flash file system maps logical blocks and where its inode table and block map are. Next step: rebuild the volume from all four lanes, for example by decoding inode numbers such as `nsx.sys` = 467.
- The meaning of header fields +0x26 and +0x2C/+0x2E, and of the constant `24 11` magic. Comparing unit headers across the four lanes and following reclaim activity should settle them.
- The ABCD load-module header fields beyond the sizes. Disassemble the OS loader (`OS-res-loader`) to see how it parses them.
- What `POC` stands for (probably power-on check plus initial downloader) and where the first-stage boot ROM is. The full 32-bit sector 0 from all lanes would show the entry point at 0x1000.

## Method

Python (`python3 -I`) scripts produced a per-sector entropy/`00`/`FF` map and a per-512-byte block classification (zero, code by 68k opcode counts, text, data). I compared the 64-byte headers of all 32 sectors and ran `strings` plus targeted hexdumps. To show the sector 0 boot region is a stride-4 lane, I searched the stride-1 file data for every-4th-byte samples of each 128-byte chunk and checked the ctype table. I decoded the directory blocks as 32-byte (inode, name) entries, rendered the block map with PIL, and ran one web search for the model name.
