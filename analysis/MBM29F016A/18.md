This chip holds every other byte of a big-endian Hitachi SuperH (SH-1 or SH-2) firmware image. The CPU read it on a 16-bit bus with this chip on D15–D8, so the chip has the even-address bytes. Code is only readable here as the high byte of each 16-bit instruction. That is still enough to recognise it. The standard SH call sequence `mov.l @(disp,PC),r3 / jsr @r3 / nop` shows as the byte run `D3 43 00`, which occurs over 10,000 times. Prologues show as `2F 2F 2F 2F 4F 7F` (push r14–r8, `sts.l pr`, `add #-n,r15`) and epilogues as `7F 4F 68 69 6A 6B 6C 6D 00 6E` (pop r8–r13, `rts`, pop r14 in the delay slot). Text is split the same way: the RCS keyword `$Header: ` shows here as `$edr `. That pattern starts 66 version strings, which date the source files to 1996–1997. Japanese Shift-JIS strings show only their lead bytes (81h–98h). The other half of every instruction, string and pointer is on a partner chip.

## Layout

Offsets are on this chip. The CPU address of a byte here is about twice its offset, because the chip holds only even addresses.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x3A | Header: `AA`×8, a parameter block, two `AA BB CC DD` markers and five length/checksum-like fields |
| 0x00003A | 0x200 | Exception vector table, 256 × 32-bit entries (2 bytes per entry on this chip) |
| 0x00023A | 0x3EC | Small tables: (count, pointer) pairs at 0x000270–0x0004B5, then zeros |
| 0x000626 | 0x4BE | Short wrapper functions and pointer tables |
| 0x000AE4 | 0x1F8 | 252 default exception stubs, `bra common / mov #vec,r4` (`A1 E4` / `A0 E4`) |
| 0x000CDC | ~0x1A0B00 | Main SH program, with RCS strings, jump tables and literal pools mixed in |
| 0x1A1838 | ~0x4E700 | Data tables: fixed-size records (22-, 34- and 16-byte records on the CPU side), monotonic lookup tables, parser-like state tables, Shift-JIS strings |
| 0x1F0000 | 0x1F49 | Tables, then Shift-JIS string records at 0x1F15EA |
| 0x1F1F00 | 0x2049 | A second, smaller block of SH code ending in the last `$Header` string at 0x1F3F28 |
| 0x1F3F49 | 0xC09F | Erased (`FF`) |
| 0x1FFFE8 | 0x18 | Trailer: `00 00 2D 2D 2D 2D 00 82` twice, then `AA`×8 |

## Findings

- **Byte lane, stride 2.** Instruction sequences are contiguous here: the call idiom `D3 43 00` is three consecutive opcodes, and the register save/restore runs `2F`×n and `68 69 … 6E` step one register per byte. A 32-bit bus with stride 4 would skip every other instruction. Text confirms it. `$edr ` is the even characters of `$Header: `, and RCS state `Exp $` shows as `Ep$`.
- **This is the even-address lane (D15–D8), and the CPU is big-endian.** All 66 `$Header` strings start at an even offset on this chip, which is a 4-byte-aligned CPU address. That is normal for compiler string literals. The same lane holds the high (opcode) byte of every SH instruction, and on SH that byte is at the even address only in big-endian mode.
- **Architecture: SH-1 or SH-2, no FPU.** The opcode high bytes match SH: `4F`+`7F` for `sts.l pr` and `add #imm,r15`, `D0`–`DF` for PC-relative loads, `89`/`8B` for `bt`/`bf`, `A0`/`A1` for `bra`, and `E0`–`EF` for `mov #imm`. `8D`/`8F` (the SH-2-only delayed branches `bt/s` and `bf/s`) occur no more often than undefined opcodes such as `8A`/`8C`. So either the CPU is an SH-1 or the compiler targeted SH-1. `Fx` bytes are rare, so there is no SH-3E/SH-4 FPU code.
- **Header at 0x000000.** The raw bytes are `AA AA AA AA AA AA AA AA 12 56 0A 01 8B 00 03 FF 00 00 00 FF 00 FF 00 00`, then `AA AA BB BB CC CC DD DD` at 0x000018 (and again at 0x000032). Between the two markers are `00 28 97 C6 00 02 D6 6E 00 10 D2 F1 00 06 7B 19 00 0C`. Read as 32-bit words they look like sizes (0x2897C6 is 2.6 MB, which fits a 4 MB two-chip image). Only half of each original word is on this chip, though, so the real values are unknown. They are not byte sums of this chip. The image ends with the same `AA`×8 at 0x1FFFF8, so the head and tail markers are probably a validity signature for a loader or updater.
- **Vector table at 0x00003A–0x000239 (CPU 0x74–0x473).** There are 256 entries. Entries 4–255 point at 252 four-byte stubs at 0x000AE4–0x000CDB (CPU 0x15C8–0x19B7). Byte 2 of each entry (`15`, `16`, … `19`) is exactly bits 15–8 of its stub's CPU address. So the program is linked to run at the CPU offsets implied here: base address bits 15–0 are zero, and byte 1 of every address is on the partner chip. About 30 vectors (for example 8, 57–61, 63, 65–68, 73, 81, 109–111, 117–120, 125, 126, 129–132, 141, 145) point instead at full handlers around CPU 0x0D00–0x3000. Those include about 30 register-saving interrupt wrappers at 0x000E7C–0x001405. Entry 0 (power-on PC) has bytes `00 … 04 …`, which does not land in this image's own code. So the reset vectors are probably supplied by a boot ROM or a different memory map, and this table is installed through VBR.
- **Default exception stubs at 0x000AE4.** `A1 E4` ×126 then `A0 E4` ×126 decode as `bra handler / mov #n,r4`, one per vector. On the partner chip the `mov` immediates should count up from 04h to FFh.
- **RCS version strings.** There are 66 `$Header: … Exp $` strings, the first at 0x01003C (`$edr dcv129/32 31:2aizm dtl$`). The digits that survive show versions 1.1–1.9 and two-digit years. Ten strings show `7` (1997) and eight show `6` (1996) in the year position. Surviving module-name fragments include `ig…`, `dfi…`, `h_…`, `cg…`, `n_…`, `rc…`, `vdp…` and `a_a…`. Two-digit years and `$Header` suggest RCS 5.x from the mid-1990s.
- **Shift-JIS text.** The string tables at 0x1F15EA onward and around 0x1B5680 contain runs of `81`–`98` separated by `00` and `FF` padding. Those are Shift-JIS lead bytes. `82`/`83` (hiragana/katakana) and `88`–`98` (kanji) dominate, so the user-facing text was probably Japanese. Short ASCII tags such as `po21`, `pob0_0` and `pok3_6` sit between them, and `ACLCSDRVSp2 972:80` at 0x1B588A looks like half of a version string dated 97.
- **Data region 0x1A1838–0x1F0000.** It holds no code idioms. Autocorrelation shows record strides of 11 and 17 bytes on this chip (22 and 34 at the CPU), for example at 0x1BC000–0x1C3FFF and 0x1D0000. There are monotonic tables of `02 02 … 03 03 …` (0x1A8000) and ASCII-ordered parser-like tables at 0x1B80F7–0x1B9B00. No bitmap or font structure was visible in a grayscale render.
- **Tail code block 0x1F1F00–0x1F3F49.** This is a second SH code section after the data. It uses the same call idiom and ends in its own `$Header` string at 0x1F3F28 (`$edr v_a_rmcv139/22 40:0acoeEp$`). Its literal-pool entries (`00 67`, `00 8C`, `00 7D`, `00 91`, …) point back into the main program's address range. It may be an add-on module or a flash-update routine that is copied to RAM.

## Device

**Low confidence.** This is a Japanese embedded product from about 1996–1998, built around a Hitachi SH-1 (SH703x class) or SH-2. Its firmware is about 4 MB, stored in two 8-bit flash chips side by side on a 16-bit bus. The evidence is the SH opcodes, the 1996/1997 RCS dates and the Japanese text. A 4 MB SH firmware of that age with large data tables and Japanese menus fits a car navigation unit, a printer/fax/copier controller or a karaoke or amusement machine. Nothing on this lane names the maker. The flash rather than mask ROM, and the `AA` head and tail markers, suggest the firmware could be updated in the field.

## Open questions

- **What the full strings say.** Interleave this chip with its partner (this chip on the even bytes) to read the RCS paths, author names and Shift-JIS messages. That should identify the product.
- **Address byte 1 and the reset path.** The interleaved image would give full 32-bit vectors and pool constants. From those, the flash base address and the SH variant can be read off the peripheral register addresses (SH-1 05FFFExxh or SH-2 FFFFFExxh).
- **Header fields.** The values between the `AA BB CC DD` markers are probably size and checksum words. Check them against the interleaved 4 MB image.
- **Tail code block.** Disassemble 0x1F1F00–0x1F3F49 (CPU 0x3E3E00–0x3E7E92) once it is interleaved, to see whether it is a flash writer.

## Method

Python 3 for per-sector entropy and fill, runs of `00`/`FF`, byte and bit histograms, autocorrelation and the block map. I used `xxd`, `strings` and `binwalk` (no known container signatures). Stride and lane came from counting SH idioms (`D3 43 00`, `4F 7F`, `7F 4F 68…`) and from projecting known words onto even and odd characters, which found `$Header: ` as `$edr `. The vector table was decoded by matching byte 2 of each entry against the CPU addresses (twice the chip offset) of the 252 `bra/mov #n,r4` stubs. Full disassembly was not possible with only the opcode high bytes.
