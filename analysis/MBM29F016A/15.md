This chip holds a quarter of a flash disk from a Seiko Instruments (SII) **NS-2482** communication server, also called the "Multi Access Server". The NS-2482 is an ISDN, frame-relay and PPP WAN router built around one or more Motorola MC68360 QUICC processors. Every 64 KB sector is one erase unit of an 8 MB disk made of 128 units, and a 512-byte header (magic `24 11`) gives each unit's logical number. A simple Unix-like filesystem sits on top of those units. Its superblock carries the BSD FFS magic `0x011954` and the OS calls it `ufs`. The strongest identification evidence is a deleted version file reading `Communication Server NS-2482 System Software 1997.10.29 (Ver 2.2)` and an SNMP setup file with `SysDescr "SII Multi Access Server NS-2482."`. The unit numbers show that this was the fourth of four identical chips.

## Layout

Each sector is one unit: a header block (0x0000–0x01FF), then 127 data blocks of 512 bytes. The logical disk address is `unit × 127 + block`.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 64 KB | Unit 3: raw area before the filesystem. About 13 KB of an unidentified binary at 0x000400, then zeros |
| 0x010000 | 128 KB | Units 7 and 11: all zero (unused raw area; unused inodes) |
| 0x030000 | 128 KB | Units 19–20: compiled modules (`ls`, `md`, `mount`, `ps`, `ospfsetup`, `rcp`, …) |
| 0x050000 | 64 KB | Unit 23: mostly deleted data from 1997; small live scripts |
| 0x060000 | 64 KB | Unit 8: boot block (zero), superblock 0x060400, inode bitmap 0x060600, block bitmap 0x060800, inodes 0–479 from 0x061000 |
| 0x070000 | 1.0 MB | Units 74, 36, 75, 43, 48, 52, 56, 60, 76, 66, 70, 79, 80, 88, 32, 89 (in that order): file data, live and deleted. Scripts, modules, OSPF/PPP/frame-relay code, setup templates |
| 0x170000 | 64 KB | Unit 28: deleted 1997 data (PPP/IPCP module) |
| 0x180000 | 448 KB | Units 99–123 (every 4th): all zero, free space at the end of the disk |
| 0x1F0000 | 64 KB | Unit 17: second root-directory block 0x1FB600, `/vup`, deleted 1997 `/version`, `Pocvup` flash updater |

## Findings

- **Unit header.** All 32 sectors start with the same 20 bytes, `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`. These probably encode 128 blocks per unit, 128 units and a 0x200-byte block. Three fields vary:
  - +0x24 is the logical unit number. All 32 values are unique, and data runs on unbroken from unit 19 (0x03FFFF) into unit 20 (0x040200).
  - +0x2C and +0x2E hold two equal copies of a count that matches erase activity. The superblock unit has 31; never-rewritten units have 1.
  - +0x26 is an unexplained counter, 0–14, and is 0 in every unit with count 1.
- **Four-chip set, this one is the last.** Every unit with erase count 1 sits at sector *s* with unit number 4*s*+3. Examples are sector 0 (unit 3), sector 5 (unit 23), sector 10 (unit 43) and sector 0x18 (unit 99). The formatter therefore dealt units 0–127 across four chips in turn, and this chip got 3, 7, 11, …. Units rewritten later have moved: sector 3 holds unit 19 instead of 15. The data inside a sector is contiguous, so each chip has a full byte lane to itself. This is not a lane-split image.
- **Two kinds of unit.** Units with count 1 have zeros from 0x0030 to 0x01FF of the header block, so they were probably programmed from a complete disk image at the factory. Units rewritten in the field by the flash driver have `FF` from 0x0040 to 0x01FF.
- **Superblock at 0x060400** (logical block 1017):
  - +4 is the magic `00011954`.
  - +0x0C gives 15,112 blocks.
  - Four (start, length) pairs follow: inode bitmap 0x3FA/1, block bitmap 0x3FB/4, inode table 0x3FF/0x2F3 and data 0x6F2/0x380F. The data area ends at block 16,129, which is 127 units × 127 blocks.
  - +0x30 is the date `0096 0708` and +0x34 is time_t `31E0BC72` (1996-07-08 07:44 UTC). This is when the filesystem was created.
  - Logical blocks 0–1015 (units 0–7) are outside the filesystem. The start-up script runs `mkrd 0 1016 1`, which matches this area's size.
- **Inodes** are 128 bytes, four per block:
  - type at +0: `0000` file, `0010` directory, `0020` symlink
  - mode at +2, written as hex-coded octal (`0755`, `0775`, `0777`)
  - link count at +4 and size at +0x0A
  - three Unix times at +0x12, +0x16 and +0x1A, and the block count at +0x1E
  - 18 direct pointers from +0x22, then single-indirect and double-indirect pointers

  The inode bitmap (MSB first) matches the deleted inodes exactly. The block bitmap is indexed from block 0x6F2. It marks 6,392 of 14,351 data blocks as in use, and nothing beyond unit 95 is in use.
- **Directories** are 32-byte entries: a u32 inode number and a 28-byte name. When an entry is deleted, its inode number and the first byte of its name are zeroed. The second root block at 0x1FB600 lists `sbin`, `setup`, `share`, `stand`, `tmp`, `usr`, `vup`, `version` and `os_version`, plus deleted `init.root`, `?sx.sys` and an older `os_version`.
- **History from the timestamps.**
  - 1997-10-29 04:23–04:24 UTC: factory files, matching "1997.10.29 (Ver 2.2)".
  - 1998-08-31 06:22 UTC: a version-up, which wrote inodes 413–479 (`mkrd`, `ospfdrvsetup`, `ospfflagchg`, `ospfrdsts`, a new `setup/default/setupfile.def`, …).
  - 1999-07-12 06:20 UTC: a second update deleted 141 of the inodes stored here. Its new files (inode 480 and up, for example `/sbin/arp` = 529 and `/version` = 589) are on the other chips.
- **Recovered files.** 64 files can be reassembled completely from this chip alone. They include `/etc/hosts`, `/etc/services` and about 25 files in `setup/common` (`interface`, `route`, `ospf`, `ipfilters`, `telnetd.conf`, …). Most are factory defaults. `interface` lists `en0` and `hsd11`–`hsd38`: three boards with eight high-speed digital lines each. The others are `/sbin/led`, `mcload`, `mcftp`, `mode`, `pocver` and `linestatis`, `/share/cmd`, `command` and `dupifd`, `init.boot` (the start-up script, first block at 0x117400) and the `/bin`-style tools `ls`, `md`, `mount`, `ps` and `msgstat`. A further 9 files are only partly present.
- **Interpreted script language.** The system is driven by scripts in a Pascal-like language with `$`-prefixed built-ins: `$PLUGIN`, `$BIND`, `$PUSH` (stacks drivers such as `Mcard`, `pt`, `ramd`, `rawfs` and `smcasy`), `$SYS`, `$BDEV`, `$WDOG`, `$BOARDID` and `$ISOCNBOARD`. A diagnostic script at 0x1FFE00 counts up to three `QUICC#` boards. `$BDEV` = 3 means "Flash Rom boot", and any other value means memory-card boot.
- **Executables.** Compiled modules start `AB CD 02 00` and have sections named `code`, `const`, `string` and `data`; `/sbin/led` is at 0x083E00. Some tools are classic a.out OMAGIC files (`00 01 01 07`, machine ID 1 = mc68010), such as the `ps` image at 0x04BE00. The module code uses `BSR.L` (`61 FF`) and `4E75` returns, which needs a 68020 or CPU32 core. That fits the MC68360 QUICC named in the scripts.
- **POC and version-up.** Unit 17 contains `Pocvup version 1.0 start.`, `POC-vup Flash Rom Erase Error.` and `POC-IDL Ver 2.1` (0x1F0720–0x1F07E8). Next to them is a 68k exception table with messages from `Bus error` to `Vect #%d %s SR=0x%04X PC=0x%08X`. `/sbin/pocver` prints the `Extended POC version.` list. "POC" appears to be the boot monitor, which is not on this chip. Unit 56 at 0x0DD037 holds a version-up FTP server, with strings like `version up server ready.` and `(system image for versionup.)`.
- **Related model.** The `linestatis` script contains blocks marked `#/***** NS-2282MH *****/` (0x084E43), so the script set is shared with the NS-2282MH.
- **SNMP.** The `snmpconf` template gives `sysObjectID 263.2.1` (0x15F060), which is under enterprise number 263.
- **Unidentified binary at 0x000400–0x003875** (logical blocks 382–409, in the raw area). It is not 68k: there are no `4E75` or `4E56` words. It contains runs of ASCII letters in scrambled order, such as `oderlscnrieaHrTVievIteaie`. Byte strides 1–16, transposition and permutations of the low six address bits do not make it readable.
- `setup/common/pw` and `authent` exist. They look like factory defaults and are not reproduced here.

## Device

**SII (Seiko Instruments) NS-2482 Communication Server / Multi Access Server**, a Japanese WAN access router with Ethernet, ISDN PRI, frame relay, PPP and OSPF, from about 1997. Confidence: **high**. The product name and version appear in the deleted `/version` text and the SNMP `SysDescr`. The scripts refer to QUICC boards, `hsd` WAN ports and frame-relay or PRI setup per WAN. The filesystem shows the factory install on 1997-10-29 and field updates in 1998 and 1999.

The four MBM29F016A chips probably formed the unit's on-board "Flash Rom" boot disk. They could also have been a 8 MB linear-flash memory card, since the software supports booting from either. This image cannot tell the two apart.

## Open questions

- **What does header field +0x26 mean?** It is not the erase count, and it is 0 in never-rewritten units. Comparing it with the same units on the partner chips, or disassembling the flash driver (`Mcard`/`pt`), should settle it.
- **What is the binary at 0x000400?** It may be a QUICC microcode patch, a CPLD/FPGA file or packed boot code. The neighbouring raw-area units 0–2 and 4–6 on the other chips should show its start and any header.
- **What did the 1999-07-12 update install?** `/version`, `/os_version` and the newer inodes are on the other chips (inode table units 9, 10, 12 and 13).
- **Who owns the data in units 74–89?** These units are fully allocated, but the files using them have inodes on other chips, so they cannot be named from this chip alone. Reassembling all four chips would allow a full file listing.
- **Is enterprise 263 SII's?** Check the IANA private enterprise number list.

## Method

Per-sector entropy and fill showed a 32-byte-header pattern in every sector. Decoding the header fields gave the unit numbers, and placing each sector's 127 data blocks at `unit × 127` rebuilt a partial logical disk. In that disk, the superblock (found by searching for `00011954`), the bitmaps, the 128-byte inodes and the 32-byte directory entries were decoded with short Python scripts. Files were reassembled from direct and indirect block pointers, and the start-up and setup scripts were read for context. Strings, a stride and permutation search on the raw-area binary, binwalk (no hits) and the `file` command on the extracted modules completed the work. The sector map was drawn with Pillow from the block bitmap.
