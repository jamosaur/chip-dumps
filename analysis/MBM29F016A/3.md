This is one chip of a four-chip, 8 MB flash disk from a Japanese WAN router running an operating system that calls itself `NS-OS version 3.1` (0x12F200). Every 64 KB sector starts with the same 64-byte unit header, and a 16-bit logical unit number at +0x24 places it in the disk. The partition record at 0x000200 reads `flush(FLUSH-EEPROM boot/partition(boot=512k) 8M byte(erase block = 64Kbyte)`. The units on this chip hold 50 relocatable 68k executables (magic `AB CD 02 00`), kernel and driver code, setup scripts in the router's own `$FUNCTION[...]` language, and a Lisp command shell. The scripts and strings describe ISDN BRI/PRI, NTT High Super Digital (HSD), frame relay, PPP, IPX, AppleTalk, OSPF and SNMP. The CPU is a 68EC040 main processor with MC68360 QUICC communication processors. Text and code read cleanly at stride 1, so the chip sat on its own 8-bit path for the file system. The exception is a 13 KB area at the start of sector 0, which is probably one byte lane of a 32-bit boot program.

## Findings

- **Unit header.** Each sector starts with `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`, then zeros. The 16-bit word at +0x24 is the logical unit number, +0x26 is a small count (0–8, meaning unknown), and +0x2C/+0x2E repeat the same value (1–9), probably an erase count. Units that were never used show count 1. The constants are likely the 512-byte sector size (`02 00` at +0x0E), the 64-byte header (`00 40`) and 32 units per chip (`00 20`), but this is not confirmed.
- **Logical numbering.** Every unused unit has logical number = 4 × physical sector (0x180000 → 0x60 … 0x1F0000 → 0x7C, 0x010000 → 0x04, 0x030000 → 0x0C). The format therefore numbered units round-robin across four chips, and this chip is chip 0 of 4. Units in use were later remapped by wear levelling: L0x25, L0x29 … L0x39 (≡ 1 mod 4) were moved here from another chip. 4 chips × 32 units = 128 units = 8 MB, which matches the partition text.
- **Unit payload.** 0x0040–0x01FF is `FF` in used units and the payload runs from +0x200 to +0xFFFF (127 × 512-byte sectors). Logical units join end to end. L0x1C → L0x1D continues the string `PPP:T1TO-(LCP:` / `%d,%d,%d)` across 0x06FFFF/0x070200. L0x42 → L0x43 → L0x44 continue code and then a relocation table across 0x02FFFF/0x100200 and 0x10FFFF/0x110200. Freed or never-used units are zero-filled rather than erased.
- **Partition geometry** at 0x000280 (32-bit big-endian): `0x7F`, 0, 1, `0x7F`, `0x200`, `0x3F8`, 0, `0x3F01`, 0, `0x1D45`, `0x194D`, `0x9EC`, `0x1F41`, `0x1FC0`. 0x7F gives 127 logical units, which leaves one spare unit for reclaim. 0x3F01 = 16129 = 127 × 127 is the total number of sectors. All the later values are multiples of 127, so they are sector numbers on unit boundaries: 0x3F8 → unit 8 (the end of the 512 KB = 8-unit boot partition), and 0x9EC, 0x194D, 0x1D45, 0x1F41, 0x1FC0 → units 20, 51, 59, 63, 64. These are probably file-system metadata locations. Unit 64 (L0x40, 0x0F0000) holds ordinary code, so the exact meaning is open.
- **Boot partition lane.** 0x000400–0x003876 does not read as stride-1 data, even though the rest of the chip does. Its byte histogram matches the opcode high bytes of 68k code (cosine 0.92 against high-byte lanes of this chip's own code, against 0.47 for low-byte lanes). A bigram model fits every-4th-byte samples of 68k code better than every-2nd-byte or contiguous samples (log-likelihood −8.95 against −9.74 and −10.29 at equal sample size). Fragments such as `P0scnc` … `P5scnc` and `A1scnc` repeat with a fixed period, as a table seen through one lane would. The boot partition is logical units 0–7, which is physical sectors 0–1 of all four chips, so it is probably stored 32-bit interleaved for execute-in-place, with this chip as one lane. That is most likely D31–D24, since this is chip 0. Unit L0x04 (0x010000), the second boot unit on this chip, is empty.
- **Executable format.** Its magic is `AB CD 02 00 05 32 00 00 06 55 06 55 06 55`, followed by a 0x110-byte header. The header holds the header size at +0x28, the end of the loadable image at +0x2C, and the total file length at +0x30/+0x34. It names the sections `code`, `const`, `string`, `data` and `ram`, with 16-byte section records at +0xD0 (id, offset, memory size, file size). After the image comes a table of 20-byte records that start `00 20 20 1B`, probably relocations. There are 50 headers on the chip, for example at 0x043200, 0x12F400 and 0x143E00 (the largest, 0x1F9F4 bytes). All are aligned to 512-byte sectors.
- **System calls** are 48 stubs of the form `48 78 00 nn 61 FF …`, ending in `4E 44 4E 75` (`TRAP #4; RTS`). They are followed by the names of shared libraries: `stdio`, `libperr`, `libmisc`, `libsetup`, `libmem` and `libctype` (for example at 0x045A3C).
- **CPU.** `61 FF` (BSR.L) throughout means a 68020 or later. Code at 0x12F518 does `MOVEC CACR,D0` and tests bits 31 and 15, then `CPUSHA DC` (`F4 78`, 0x12F522) and `CINVA IC` (`F4 98`, 0x12F52A), which are 68040-family instructions. The `cpuinfo` tool prints `Main Board CPU    : 68EC0%2d (%2dMHz)` (0x08C7E4). Kernel strings dump the `CICR/CIPR/CIMR/CISR` registers and an `SDMA bus error` (0x128343–0x1283CF). Scripts mention `QMC`, `SI(QUICC Serial Interface)` and `SPI(QUICC Serial Peripheral Interface)` (0x0E330B), all MC68360 QUICC features.
- **Kernel.** Logical unit L0x48 (0x120000) holds exception and panic strings, `[OS-res-loader:load %s at %08x (size %x)]`, root-device setup (`open-mc 0`, `open-flash 0`, `open-ramd`, `FlashEEPROM: No Memory.`) and file-system messages, from 0x1282E0 to 0x128CE0. A one-sector file at 0x12F200 contains `NS-OS version 3.1 start.`, probably the `/version` file that `show -a /version` prints.
- **Scripts.** Plain-text scripts use a Pascal-like language with `$BIND`, `$PLUGIN`, `$SYS[WAIT;…]` and `VOID FUNCTION … BEGIN … END`. Examples: `# High Super Digital (HSD) setup` (0x080200), WAN and timeslot builders that use `$EXTBOARDID[cpno];0x34` → `# 8BRI+PRI` (0x13EA2A), `# reload & PRI 1997-10-09` (0x13E250), and the init script at 0x154700, which binds `/driver/MCardI.drv`, `enIpx.drv`, `ipxr.drv`, `ddp.drv`, `enlap.drv` and `tn.drv` and probes up to three extension boards.
- **Lisp shell.** A Lisp command shell (`define`, `lambda`, `_$PR`, around 0x0B3400–0x0B6400) also contains a compiler for the script language. The shell has a hidden superuser path prefix command `nsxi` (0x0B612C) that adds `/admin/` to the search path.
- **Utilities found:** a memory-card FTP loader (`-S Slot-No. : 1/2`, `-C Card-size`, `-E Erase-block-size`, 0x0408BE), `ifconfig`, `iostat` (`/setup/common/iostat.0`), `ls`, `date`, `statis`, `telnet`, `snmpd` (MIB-II and frame-relay groups), and the PPP/LCP/IPCP/CHAP/PAP state machine.
- **Setup paths:** `/setup/common/pw`, `/setup/common/snmpconf`, `/setup/default/setupfile.def`, and `/usr/setup/wan10` … `wan30` (0x08B470), which suggests WAN ports are numbered 10–30 across three boards.
- No compressed containers were found. Text is ASCII only, with no Japanese text strings.

## Device

**Probably a Japanese multi-port ISDN/leased-line access router or remote-access server from about 1997–1998, running NS-OS 3.1. Confidence: medium for the class of device, low for the maker and model.** The evidence is the 68EC040 main CPU with up to three extension boards, each driven by an MC68360 QUICC with up to 8 BRI + PRI or HSD ports (`wan_pri_ports:= (9,10,19,20,29,30)`). The Japan-specific features are NTT HSD, ISDN `CableOff`/`CableOn` and the 1997 date. Two PCMCIA memory-card slots are used for loading and backup, and the 8 MB on-board flash disk is made of four MBM29F016A chips. Web searches for `NS-OS` with these features found no matching product. No vendor name, model number or copyright string appears on this chip.

## Open questions

- **Maker and model.** Look for a `sysDescr` or `sysObjectID` value, the `/version` contents or banner text on the other three chips. The SNMP enterprise OID would name the vendor.
- **Boot program.** Interleave the 0x000400–0x003876 regions of all four chips at stride 4, trying lane orders, and confirm 68k code and readable strings. The `C3 46 DF FF` at 0x0003FC may be a checksum or the first lane bytes.
- **File-system metadata.** The directory and allocation structures are not on this chip; only logical unit 0x40 of the listed metadata units is here. Rebuild the full 127-unit volume from all four chips by logical number, then read the sectors listed at 0x000280 (units 8, 20, 51, 59, 63, 64).
- **Header field +0x26.** Its meaning (0–8) is unknown. Compare it with the other chips' headers and with the number of live sectors per unit.
- **Kernel identity.** It is not certain which `AB CD` file is the kernel proper. The 0x12F400 image (cache setup and a 256 KB BSS) is a candidate. Load it at its section addresses in a disassembler to confirm.

## Method

I used Python (`python3 -I`) for per-sector entropy and fill statistics, the per-unit header table, the continuity checks across logical units, histogram and bigram tests of byte lanes, and the search for the `AB CD 02 00` executable headers. I also used `xxd`, `strings` and `grep` for hex inspection and string mining, and hand-decoded 68k opcodes. `binwalk` found no known signatures, and searches for EUC-JP and Shift-JIS text found nothing. The unit and block map was rendered with Pillow.
