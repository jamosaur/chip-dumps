This is one of four 8-bit flash chips from the on-board flash ROM of a Japanese multi-port ISDN / frame-relay / leased-line router from about 1995–1997. The image has two parts. Unit 0 holds one byte lane of a boot image that the 32-bit CPU reads across all four chips. Every other unit belongs to a flash file system that addresses each chip separately as an 8-bit device. This chip carries 31 of the volume's logical 64 KB units and one erased spare. The file data is plain and contiguous. It holds 66 Motorola 68020+ executables in a custom `ABCD` format, router setup and help text, and scripts in a house language with `$PLUGIN[...]`, `$SYS[...]` and `$READBYKEY[...]` calls. The strongest identifiers are the boot-loader strings `3rd Boot version 1.2 start.`, `load OS from %s` and `/nsx.sys`, ISDN code (`buildINS1500`, `PH:ISDN CableOn`, `TEI`) and support for 30 WAN ports (`ppp.wan#  PPP Parameters (#:1-30)`).

## Findings

- **Unit header (all 32 units).** The bytes are `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`, then zeros to 0x23, then a big-endian u16 logical unit number at 0x24, a u16 at 0x26 (0–7) and a duplicated u16 pair at 0x2C (`0001 0001` to `0009 0009`; probably an erase count). The `0200` and `0080` fields match the geometry of 512-byte blocks × 128 per 64 KB unit. In live units, bytes 0x40–0x1FF are FF; in units that still carry their factory-format content they are zero.
- **Logical unit mapping, verified.** The logical stream is blocks 1–127 (0xFE00 bytes) of each unit, in the order given by the logical unit number. The executable at 0x13FA00 (L=0x53) runs off the end of its unit. Its code continues without a break at 0x140200, the first data block of L=0x54: `2F00 2254` / `2069 0048 4E90`. Its strings (`fscopy: FS update time get Error.` at 0x140DF6) lie in that next unit.
- **This chip is chip index 1 of 4.** Units still in their formatted position carry logical numbers 4×unit+1: 0x01, 0x05, 0x0D, 0x21, and 0x61 to 0x7D for units 0x18 to 0x1F. So the volume interleaves logical units over four chips, about 128 units or 8 MB. The other logical numbers (0x16 to 0x5C) were reassigned when units were reclaimed. Their erase counts are 2–9. The spare is unit 0x0E.
- **No directory on this chip.** File names appear only inside scripts and tables (`/setup/common/servers`, `/sbin/ospfrestart`, `/share/initSubr.r`). There are no directory entries or inode-like records, so the root and metadata are probably in logical units held by the other chips, possibly L=0x00.
- **Boot code is lane-split.** Bytes 0x000400–0x003875 are not readable as a stream, but they contain every fourth character of strings that the 3rd boot also has. Examples: `il oc  c.` from `initialize memory card NG. no card.` (0x000DCC), `naearNfar.` from `initialize flash rom NG. format error.` (0x000DDF) and `c%s=0PxX` from `Vect #%d %s SR=0x%04X PC=0x%08X` (0x000DB0). Hex-digit tables appear as `26AE159d0X` (0x003860). One 87-byte run (0x0009CA–0x000A20) matches stride-4 bytes of a file-system routine in the 3rd boot (0x0F4F69 onward).
- **The boot lane is odd (1 or 3).** The lane's byte histogram matches the odd lanes of 68k code (cosine 0.95; even lanes 0.86). Pairs such as `DF 75` come from `4CDF xxxx 4E75` (movem/rts) spaced 4 bytes apart. Lanes 1 and 3 cannot be told apart from statistics alone. The chip index of 1 fits lane 1.
- **`ABCD` executables (66 headers, all 512-byte aligned).** The header is `AB CD 02 00 05 32 00 00 06 55 06 55 06 55`. A section count (2–5) sits at 0x0E, and header size = 0xD0 + 0x10×count at 0x28. The u32 at 0x2C is the file image size and the u32s at 0x30/0x34 are the memory size. A name table at 0x50 has 0x1C-byte entries `code`, `const`, `string`, `data`, `ram`. Section descriptors at 0xD0 are 16 bytes each: id<<24, address, size, file size. Code starts with `4879 ...` and uses `61FF` (bsr.l) and `4E90`, so it is 68020 or later and big-endian. After each image come zero padding and runs of 20-byte records containing `00 20 20 1B` (13,572 of them). These are probably relocation or symbol records.
- **3rd boot loader** at 0x0F3600 (image 0x27E0). It contains 68k exception names (`Bus error`, `Addr error`, `Line emu1 trap`), `3rd Boot version 1.2 start.`, `check 2nd Boot version number NG.`, `initialize memory card NG. no card.`, `initialize flash rom NG. format error.`, `get bootconf NG.`, `/nsx.sys` (0x0F5DAC) and `load OS from %s (%s %08X-%08X) OK.`. The OS can therefore load from `Flash Rom` or `Memory Card`. I could not identify `nsx.sys` itself. The largest executables here are 0x1BA40 bytes (0x0C1200) and 0x16384 bytes (0x170600), and both continue on other chips.
- **Router applications.** The executables cover a PPP authentication menu (0x0274C0, `>>> Version 1.0 ('95/09/05)`), ftp-like `load`/`store` commands (0x0226BD), ISDN layer 2 (`L2CTL:(%x)sWAIT(T205)`), frame relay (`invalid DLCI [%d]`), X.25-style `lcn`/`lcgn` config, OSPF (`ospfRoute:router link adv read error`), `netstat`, telnet and `fscopy`.
- **Setup text and scripts.** Unit L=0x21 at 0x080200 is a setup-file index, from `gateways  IP Static Gateway Information` through `servers  Server Programs`. It maps names to paths under `/setup/common`, `/setup/default`, `/setup/ttyp` and `/setup/wan1` to `/setup/wan30`. The script at 0x025400 restarts `ospfd`, and the one at 0x043E00 copies the memory card (`Memory Card is boot device.`). The script containing `# reload & PRI 1997-10-09` (0x13E650) builds INS1500 (ISDN PRI) and frame-relay ports.

## Device

The image comes from the on-board flash of a Japanese ISDN / frame-relay router or remote-access concentrator, built around a 68020-class (or later) CPU with a 32-bit flash bus of four MBM29F016A chips (8 MB). Confidence: **medium** for the device class, **low** for the maker.

- The device class follows from the WAN types (NTT INS64/INS1500 ISDN, HSD leased lines, frame relay, PPP), the 30 WAN ports, OSPF and SNMP, and the Japanese terms (`INS1500`, `HSD`, `TEI`).
- The dates (`'95/09/05`, `1997-10-09`) place the firmware around 1997.
- The memory-card boot option points to a PC Card slot.
- The OS file name `nsx.sys` and the `$`-function scripting language are distinctive. Web searches for them found nothing, so the maker is unknown.

## Open questions

- **Maker and model.** Search Japanese router manuals of 1996–98 for `nsx.sys`, `pppauth`, `fscopy` or the `$READBYKEY` script syntax. The other chips may also hold a `/version` file (the command `show -a /version` is referenced).
- **Exact boot lane (1 or 3).** Interleave this lane with the other three chips' unit 0 and check which order gives valid 68k code and readable strings.
- **File-system metadata.** No directory or block-allocation structures are on this chip, and the meaning of header fields 0x26 and 0x40–0x1FF is unconfirmed. Next step: find logical unit 0x00 and the directory on the partner chips and decode them.
- **The 20-byte `00 20 20 1B` records.** Decode one executable's trailer against its code to tell relocation records from symbol records.

## Method

`sha256sum`, then Python 3 (`-I`) scripts for per-unit entropy, a per-512-byte block map, header tabulation and an `ABCD` header walker. I used `strings`/`grep` and `xxd` for text and structures. The lane split was tested by matching stride-2 and stride-4 projections of the file-system strings against unit 0. Lane parity came from byte histograms of 68k code lanes. Unit chaining was checked by following an executable across a unit boundary. The 68k code was identified by hand from opcodes (no m68k disassembler was available). The block map was rendered with PIL.
