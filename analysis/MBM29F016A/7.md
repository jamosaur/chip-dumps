This chip holds every second byte of a big-endian Hitachi SuperH program. It sat on a 16-bit data bus as the low byte (D7-D0, odd addresses), and a partner chip held the high bytes. Three things show this. The low bytes of SH instructions are here in sequence: `0B 09` is `rts` / `nop`, `E6 D6 C6 B6 A6 96 86` is the push of r14 down to r8, and `26 F6 F6 ... 0B F6` is `lds.l @r15+,pr`, the register pops, then `rts` with a pop in the delay slot. The text shows only the odd characters of RCS keyword strings (`$Header: ... Exp $` reads as `Hae:` ... `Ep$`). Pointer tables also decode cleanly as bytes 1 and 3 of big-endian 32-bit words. Read that way, the image is an SH-1/SH-2 program linked at 0x00800000. That is chip select area 2 on the SH7034/SH704x family, and it is exactly the 4 MB that two 2 MB chips fill. The program starts with a 0x74-byte header, then a 256-entry exception vector table. The RCS dates point to 1996-1997.

## Layout

Offsets are chip offsets. CPU address = 0x00800000 + 2 × offset + 1.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x3A | Image header (16-bit fields): `AA` fill, magic that reads as `0x12345678`, `AA/BB/CC/DD` marker blocks, a short table of value pairs |
| 0x00003A | 0x200 | 256-entry SH vector table (vectors 0-3 zero, the rest pointing at stubs at 0x008015C8+) |
| 0x00023A | 0x62 | Small descriptor table (pointers 0x0083xxxx) |
| 0x00029C | 0x21C | Table of 67 16-byte records: id 0x01-0x43, type, handler pointer, small length |
| 0x0004B8 | ~0x600 | Mostly zero initialised data |
| 0x000AE4 | 0x1F8 | 252 four-byte interrupt stubs (`bra common` + `mov #n`, n = 4..255), common handler at 0x000CDC |
| 0x001000 | 0x1A1000 | Program code (several thousand functions), with a few table islands at 0x011000, 0x036000, 0x05A000 |
| 0x1A2000 | 0x50000 | Constant data: lookup tables, record arrays, rcsid strings |
| 0x1F2000 | 0x1F49 | Late code and runtime/math library, double-precision constants, final rcsid strings |
| 0x1F3F49 | 0xC0B7 | Erased (FFh) to the end of the chip |

## Findings

- **Byte lane, stride 2.** Adjacent bytes on this chip are adjacent 16-bit words in the CPU's view. Across the code area `0B 09` occurs 29,364 times, `0B F6` 6,890 times and `26 F6` 5,071 times. The descending runs `E6 D6 C6 B6 A6 96 86` (383 times) are the low bytes of `mov.l rN,@-r15` for N = 14..8. A stride of 4 would break these runs, so the bus is 16 bits wide, not 32.
- **Odd-address lane, big-endian.** The RCS strings show characters 1, 3, 5, 7 of `$Header:` (`Hae:` at 0x01003C, 0x012BC0, 0x02039E and 66 more places). Unexpanded `$Header$` reads `Hae$` at 0x1F3F24. C strings are word-aligned, so this is the odd lane. It also holds instruction low bytes, which on SH means big-endian. In the pointers, the varying low byte (bytes 1/3) is always even and mostly a multiple of 4, which fits the same reading.
- **Header (0x000000).** As (byte 1, byte 3) pairs of each 32-bit word: `AA AA` ×4, then `34 78` at word 0x10 (most likely the magic `0x12345678`), `00 00`, `00 00`, `10 FF`, `00 30`, `FF A0`, `FF D0`, `00 00`. Then come markers `AA AA BB BB CC CC DD DD` and five pairs `B4 50 / AB 0F`, `00 A0 / 7D 6D`, `00 F0 / 3B E6`, `00 EA / 99 15`, `00 78`. The markers repeat at word 0x64. These are probably what a boot loader checks before it jumps into the image (signature, sizes, checksums). The other half of each field is on the partner chip.
- **Vector table at image offset 0x74 (chip 0x00003A).** Vector n sits at image offset 0x74 + 4n, for n = 0..255. Vectors 0-3 (reset PC/SP) are zero, so reset is handled elsewhere. Most other vectors read `80 xx`, which means 0x0080xxxx. They point to consecutive 4-byte stubs at 0x008015C8 + 4(n-4), whose low bytes `F6 04`, `F4 05`, `F2 06` ... `00 FF` (chip 0x000AE4) are a `bra` with a falling displacement plus `mov #n`. Vector 11 (NMI) points to a separate handler at 0x008015B0. Vectors 60-63 read `00 A4`, `00 00`, `00 A4`, `00 4C`, i.e. 0x0000xxxx. That is area 0, where a boot ROM or on-chip ROM probably provides TRAPA services.
- **SH-1/SH-2 family.** A 256-entry table addressed as VBR + 4n is the SH-1/SH-2 exception model. SH-3/SH-4 use fixed VBR offsets instead. A link address of 0x00800000 is the start of CS2 (area 2, 4 MB) on the SH7032/7034 and SH7040-7045 memory maps.
- **Address mapping checks out.** Pointers found near the end of the chip have byte 1 = `BE` (for example `5F64 5F18 BEE8 BEB4` at 0x1F2004). Offset 0x1F0000 maps to 0x00BE0000, so these pointers land where they are stored. The record table at 0x00029C points to 0x0080-0x0095xxxx and one entry to 0x00B1xxxx, all inside the program. Two entries (ids 0x04 and 0x3C) point to 0x0003xxxx in area 0.
- **Record table (0x00029C).** It has 67 records of 16 bytes (8 per lane). The lane bytes are `[id][type] [ptr b1][ptr b3] [len][00] [00][00]`, for example `01 00 80 5A 01 00 00 00` and `02 01 8B B8 0B 00 00 00`, with ids 0x01-0x43 and types 0-5. It is probably a command or task dispatch table: id, argument count or type, handler, and a parameter length.
- **RCS keyword strings.** 69 `$Header$` strings each mark a source module, mostly in the data area (21 at 0x1E0000-0x1EFFFF, 27 at 0x020000). Decoding the visible half of the date fields gives two-digit RCS years. One string parity shows the tens digit `9` and the other shows units `6` or `7`, so the files were checked in during 1996-1997. Revision numbers run from 1.1 to 1.14, plus one 2.0. Only half of each file and author name is here. Filename fragments include `da_`, `c_r_`, `mh_`, `nh_`, `sh_`, `cg`, `ii` and `po`.
- **Data area.** 0x1A8000 holds 16-bit tables whose low bytes count `F0..FF 00..FF` (clamp or identity tables). 0x1B0000 is an array of 6-byte records (3 bytes per lane) holding a permutation of 0x00-0x60. 0x1D0000 has 44-byte records (22 bytes per lane). 0x1F3E00 has interleaved double-precision constants (`AA AA AA`, `CC CC`, `88 88 8A` patterns typical of polynomial coefficients). No fonts or bitmaps showed up when the data was rendered as 1-bpp; with only half of each 16-bit word here, any graphics would be split anyway.
- **No compression or containers.** binwalk finds nothing, and the per-sector entropy (5.1-7.1 bits) fits half-width code and tables.
- **Image end.** The last content byte is at 0x1F3F48, after an rcsid string. The rest is FFh, so the program is about 3.9 MB in CPU terms (0x00800000-0x00BE7E92).

## Device

Unknown, confidence **low**. Verified: a big-endian SH-1/SH-2 (Hitachi SH7032/7034 or SH7040-7045 class) system with about 4 MB of application firmware in two x8 flash chips on a 16-bit bus at CS2 (0x00800000). Reset and some trap services live in area 0, either the MCU's on-chip ROM or a separate boot chip. The sources were kept in RCS and dated 1996-1997, which suggests a Japanese-designed product of about 1997-1998. A 4 MB program was large for an SH-2 then. It points to a feature-rich appliance such as an office printer or MFP, a car navigation or audio head unit, a music workstation or an industrial controller. Nothing in this lane names the product, because all user-visible text (if it is ASCII or Shift-JIS) is split with the partner chip.

## Open questions

- **Product identity.** Interleave this image with its high-byte partner (bytes at even offsets) and read the complete `$Header$` paths, author names and any UI strings.
- **Exact CPU.** With full instructions, look for on-chip peripheral addresses in literal pools (0x05FFFExx for SH7034/704x, 0xFFFFFExx for SH7604) and decode the vector stubs' common handler at 0x008019B8.
- **Header semantics.** Once the partner lane completes the fields at image offsets 0x00-0x73, test whether the pairs at 0x40-0x60 are length/checksum pairs over the image.
- **Area-0 boot code.** Vectors 60-63 and two record-table entries call into 0x0000xxxx-0x0003xxxx. That code is not on this chip. Look for a boot ROM, or the MCU's internal flash, with TRAPA handlers at addresses ending `A4` and `4C`.

## Method

Python (run with `-I`) for per-sector entropy and fill statistics, FFh/00h run detection, and pattern counts of SH low-byte opcode idioms (`0B 09`, `26 F6`, `0B F6`, push runs) to set the stride and lane. binwalk for signatures (none). `strings` and hand decoding of `$Header$` fragments for lane parity and dates. The vector table was decoded as (byte 1, byte 3) pairs and matched to the stub sequence at 0x000AE4 to fix the table offset and the link base of 0x00800000. The content map was rendered with PIL by classifying 4 KB blocks on opcode-pattern density.
