This chip holds one of the four byte lanes of a 32-bit flash bank. The bank stores a single Cisco IOS router image for a 68k CPU. The chip's data lines are wired in a scrambled order. Once the bit permutation is undone, the lane contains every fourth byte of three things in turn: a flash file header, an a.out header, and about 3.9 MB of Motorola 68k code and data. The strongest evidence is the version banner. In stride 4 it reads exactly as `Cisco Internetwork Operating System Software` / `IOS (tm) …0 Software (IGS-D-L), Version 1?.?(?0), RELEASE SOFTWARE (fc1)` / `Copyright (c) 1986-199? by cisco Systems, Inc.` Two complete low-byte lanes of a CRC-16 table, which decode with the same permutation, confirm both the permutation and the stride. The image fills 0x000000–0x0F5C4D. The upper half of the chip is erased.

## Layout

Chip offsets. Each chip byte is CPU byte `4·offset + 1` of the bank (lane 1, bits 23–16).

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 16 B | Lane of a 64-byte flash file header: magic, length, checksum, date and name |
| 0x000010 | 8 B | Lane of a 32-byte a.out exec header (magic, text, data, bss, syms, entry, relocation sizes) |
| 0x000018 | ~0xF1234 | Text segment: 68k code with inline constants. It starts with a short table and an `FF` run (0x000036–0x00008E). Code runs to about 0x0F124B |
| ~0x0F124C | ~0x4A02 | Data segment: version banner, string fragments, CRC-16 tables, zero-filled arrays and structured tables |
| 0x0F5C4E | 0x10A3B2 | Erased (`FF`) to the end of the chip |

## Findings

- **Stride 4.** Text decodes only as every fourth character. At 0x0089BA the lane reads `: x80% x80% xa% x80% x80`. That is exactly what stride-4 sampling of a repeated `%08x ` (period 5) produces. Strides 1 and 2 give nothing. Byte statistics are the same for offsets mod 2 and mod 4, which fits a single lane.
- **Data-bit permutation.** The fix is to map chip D0..D7 to CPU byte bits 5,6,7,4,3,2,1,0. That is, D0→b5, D1→b6, D2→b7, D3→b4, D4→b3, D5→b2, D6→b1, D7→b0. Bits 1–6 were derived from a linear lookup table, and the D2/D7 ambiguity was settled by the 68k `RTS` low byte (`75`). Two 128-byte tables then match bit for bit: 0x0F2970 holds the low bytes of entries 1,3,5,…,255 and 0x0F2B43 holds entries 0,2,4,…,254 of the reflected CRC-16 table, polynomial 0x8408 (CRC-CCITT/Kermit). Only every other 16-bit entry is present, which again means a 32-bit bus.
- **Lane = 1 (bits 23–16, big-endian).** Decoded, the first byte is `D0`, the second byte of `0xBAD00B1E`. I recall that value as the magic of Cisco's early flash file header (not confirmed online). The a.out field at 0x000010 decodes to `02`, the second byte of a SunOS-style 68020 a.out magic `0x0002010x`. Both fit lane 1 and no other.
- **Flash file header** (raw `0e b9 77 00 e3 b1 09 09 ff…`, decoded `d0 3d ee 00 67 2d 30 30 ff…`):
  - Length bits 23–16 are `3D`, so the file is 0x3D0000–0x3DFFFF bytes. That agrees with where the data stops.
  - The checksum low byte is `EE`.
  - Byte 13 of the header is `00`.
  - Name characters 1, 5, 9 and 13 are `g`, `-`, `0`, `0`, and later positions are `FF`. This fits a name such as `igs-d-l.103-10` (that exact name is a guess).
- **a.out header** (raw `40 39 80 c0 00 00 00 00`, decoded `02 3c 01 03 00 00 00 00`):
  - Text is 0x3Cxxxx bytes, data 0x01xxxx and bss 0x03xxxx. There are no symbols.
  - Entry bits 23–16 are `00`. This fits an entry point of 0x0300xxxx, the flash window of Cisco 2500-class routers, as expected for a run-from-flash (`-L`) image.
  - Text plus data plus header comes to 0x3Dxxxx, which agrees with the file length.
- **68k code.** The decoded lane is dominated by 68k opcode low bytes:
  - `56 E7` (LINK A6 then MOVEM.L to -(SP)) occurs 2,637 times.
  - `5E 56` (UNLK A6 with the RTS in the other lane, then the next LINK) occurs 3,785 times.
  - `75` (RTS) occurs 9,605 times.
  - `4F` (ADDQ to A7 after calls) and `6E`/`2E` ((d16,A6) addressing) are also frequent.
  - In the raw chip bytes, the prologue appears as `7a 6a e7 73`.
  - MOVEM with predecrement rules out ColdFire. Together with the 32-bit bus this points to a 68020/030/040-class CPU.
- **Version banner.** Two identical copies sit at 0x0F1294 and 0x0F12F9 (raw `21 fa 22 4a cb 92 …`). The visible characters fit the following:
  - Platform field ending in `0` (`2500`, `3000` and similar).
  - Image `(IGS-D-L)`. The `IGS` prefix is the pre-11.1 naming for the 2500/3000 family, and `D` is the "desktop" feature set.
  - Version `1?.?(?0)`, release `RELEASE SOFTWARE (fc1)`, copyright `1986-199?`.
  - Build line `Compiled Mon ?1-Mar/Apr-9? ??:4? by …`.
  - Together with the file name these fit `Version 10.3(10)`. 11.0(10) is also possible from the banner alone.
- **Other string fragments** (lanes only): Cisco command and message text, such as phase matches for `Configuration register is` (0x0214F5, 0x04B10E) and `cisco Systems` (0x09A069). There is also an upper-case identifier table at 0x009C30.
- **No compression or filesystem.** binwalk finds nothing in the raw or decoded image. Entropy is 6.4–7.0 bits per byte in the text sectors and drops to 2.7 in the data sector.

## Device

**High confidence** that this came from a Cisco router with a 68k CPU, a 32-bit flash bank of four MBM29F016A (8 MB), and a single run-from-flash IOS file. The evidence is the IOS banner, the a.out run-from-flash header, the entry point at 0x0300xxxx, and the 68k code. **Medium confidence** that it is a Cisco 2500-series router, or a related 3000-series router (`IGS` images), on an 8 MB flash SIMM. The image is IGS-D-L, probably IOS 10.3(10), built around 1996.

## Open questions

- Exact version, build date and file name. Only every fourth character is here. The lane 0, 2 and 3 chips of the same bank would complete the banner and header.
- Platform string (`2500` or `3000`). Reading it needs the other lanes.
- The meaning of the a.out-adjacent words at 0x000018–0x000035 (decoded `ff de 00 00 02 01 00 02 00 3a 01 03 …`). Interleave the four lanes and compare with a known 10.3 `-l` image.
- The full file checksum and length. Combine the lanes, then verify the checksum over the file.

## Method

1. Per-sector entropy and fill maps, byte and popcount histograms, n-grams, and lane statistics (Python, run with `-I`).
2. A linear (XOR-basis) table at 0x0F2B43 gave the data-bit permutation. That table and its twin at 0x0F2970 were then matched against the CRC-16/0x8408 table.
3. The permutation was applied to the whole image. Strings were searched by stride-4 phase subsequences of known Cisco text, and 68k opcode low-byte idioms were counted.
4. The flash and a.out header fields were read from the first 24 bytes.
