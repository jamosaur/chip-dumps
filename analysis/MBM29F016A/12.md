This chip holds one quarter of an 8 MB flash disk from a Japanese 68k-based WAN router. Every 64 KB erase unit starts with a 64-byte header with magic `24 11`. The header gives 128 sectors of 512 bytes per unit and 32 units per chip. Its logical-unit field runs from 0x00 to 0x7C across a 128-unit space, which matches the driver banner at 0x0001FF: `xflush(FLUSH-EEPROM boot/partition(boot=512k) 8M byte(erase block = 64Kbyte)`. The data is 68k code and text from a Unix-like file system (`/setup/common/...`, `/sbin/`, `/etc/hosts`). The scripts name the MC68360 QUICC (`SI(QUICC Serial Interface)`, `QMC`), NTT `INS1500` primary-rate ISDN, frame relay, PPP, OSPF and SNMP. Logical unit 0 also holds a small boot image. That image is stored one byte lane at a time (every fourth byte of a 32-bit bus), unlike the file data, which is byte-contiguous.

## Layout

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 64 B | FTL unit header (logical unit 0x00, erase count 1); then zeros to 0x0001FE |
| 0x0001FF | 0x201 | Driver parameter sector: `xflush(...)` banner, geometry longs at 0x000280, `C3 46 DF FF` at 0x0003FC |
| 0x000400 | 0x3100 | Boot image, one byte lane (MSB of 16-bit words) of 68k code |
| 0x0034E0 | 0x3A0 | Same lane, data and string area (`CD2`, `P0scnc`... fragments) |
| 0x003880 | 0xC780 | Zero (rest of logical unit 0) |
| 0x010000 | 64 KB | Unit header (logical 0x04), all sectors zero |
| 0x020000 | 64 KB | Logical unit 0x3A: file-system data (68k executables) |
| 0x030000 | 64 KB | Unit header (logical 0x0C), all sectors zero |
| 0x040000 | 0x50000 | Logical units 0x44, 0x15, 0x41, 0x1D, 0x0F: file data |
| 0x090000 | 64 KB | Logical unit 0x25: all sectors zero |
| 0x0A0000 | 0x90000 | Logical units 0x29–0x48 (nine units): file data, scripts, executables |
| 0x130000 | 64 KB | Spare/transfer unit: erased except `24 11` magic and `00 0D 00 00` at 0x130026 |
| 0x140000 | 0x40000 | Logical units 0x52, 0x55, 0x5A, 0x5E: file data |
| 0x180000 | 0x80000 | Eight unused units (logical 0x60–0x7C), header only, sectors zero |

## Findings

- **Unit header** (verified on all 32 units). The big-endian 16-bit words at 0x00 are `2411 0080 0000 0080 0001 0080 0001 0200 0040 0020`. That reads as magic, then 128 sectors per unit, then 512-byte sectors (0x0E), a 0x40-byte header (0x10) and 32 units per chip (0x12). The word at 0x24 is the logical unit number, unique per chip, in the range 0x00–0x7C. The words at 0x2C and 0x2E are an erase or generation count, written twice (1 for never-rewritten units, up to 9 at 0x0E0000). The word at 0x26 ranges from 0 to 0x16 and is not identified. Header bytes 0x40–0x1FF are 00 in units that are still in their initial state and FF in rewritten units. No per-sector map exists, so sector *i* of a unit is probably logical sector *i* of that unit.
- **Interleaved unit numbering.** The eleven units that were never rewritten (erase count 1) carry logical number 4 × physical index (0x000000 → 0x00, 0x010000 → 0x04, 0x030000 → 0x0C, 0x180000–0x1F0000 → 0x60–0x7C). The format therefore numbered unit *n* as chip *n* mod 4, block *n*/4, so this chip is probably chip 0 of four. Rewritten units hold numbers from other residues (0x15, 0x29, 0x3A...) after wear-levelling.
- **Driver parameters** at 0x000280 are big-endian longs: `7F, 0, 1, 7F, 200, 3F8, 0, 3F01, 0, 1D45, 194D, 09EC, 1F41, 1FC0`. 0x7F is 127 data sectors per unit, 0x200 is the sector size, and 0x3F8 (1016 sectors = 8 units × 127) is the 512 KB `boot` partition from the banner, so logical units 0–7 are the boot partition. The other values are not decoded.
- **Lane-split boot image** in logical unit 0, sectors 2–28 (0x000400–0x003877). The bytes are 68k opcode high bytes without their low halves (`4E 08 67 08 67 4E 42 00`, runs of `4E`). A bigram test against this chip's own 68k code fits stride 4 at an even phase (log-likelihood −4.03/−4.07 per byte) better than stride 2 (−4.70). The image is therefore one byte lane of a 32-bit bus, and the high byte of a 16-bit word. If it was striped across logical units 0–3 (block 0 of each chip), the full image is about 55 KB, executed or loaded at 32-bit width. Its start (`32 03 00 00 61 60`) is not a vector table.
- **File-system data** is byte-contiguous: for example 68k code at 0x020200 continues across sector boundaries. Directory sectors use 32-byte entries, a 4-byte big-endian inode number followed by a 28-byte name. The examples are 0x0E6800 (`.`=0x194, `..`=0x12, `common`, `default`), 0x0E6A00 (`init.conf.local`) and 0x0E6C00 (`command.def`, `rs232c.def`). The code mentions `ufs` (0x0ED860) and `fs:run out of resource(bread)`. No superblock or inode table was found here, so they are probably on the other chips.
- **Executable format, magic `AB CD 02 00`**: 41 files start on sector boundaries (first at 0x026200). Each header has a section table with 28-byte entries named `code`, `const`, `string`, `data` and `ram`, then address/size triples. Code starts at the offset in the word at +0x2A (0xF0, 0x100 or 0x110, depending on the section count at +0x0E). Each code segment ends with the `4E44 4E75` stub (TRAP #4; RTS), which occurs exactly 41 times. Shared-library names follow it, for example `stdio`, `libmisc`, `libperr` and `libmem` at 0x026D74. System calls go through `61FF` BSR.L stubs (4829 occurrences), so the CPU is a 68020-class or CPU32 part.
- **Scripts** are in a custom bracket-syntax language (`$PR[err;"..."]`, `$SYS[WAIT;...]`, `FOREACH name IN args`). Examples are the WAN setup at 0x0E2200–0x0E6200, the shell profile at 0x0E7000 (prompt `(^) $ >`, alias `version` → `show -a /version`) and a `rm -r` implementation at 0x055A10. A Lisp-like compiler table appears at 0x0B3B12 (`(putprop 'VAR-ID ...`).
- **Hardware named in the scripts**: QUICC SI/SPI/QMC/SCC1/SCC2 and TDMa/TDMb (0x0E3311), ports `P1-1`…`P3-8`, `P1-WAN`, `P1-PRI` (0x05E33B), `# INS1500` (0x0E3AA8), BRI layer-1 messages (`PH:ISDN Cable Off`, `PH:PRI ACT` at 0x04B0DE) and a driver test script `test script for QMC,QCH,MHHDL driver` (0x05BE04).
- **Software**: SNMP MIB-II and Frame Relay MIB display (`mibdsp`, 0x029B7B), `ospfSetup` (0x02E7A8), PPP LCP/IPCP logs (0x112E02), `telnetd` (0x0CD92F), `rcp`, a `mkrd` RAM-disk tool (0x026E1F), plus IPX and AppleTalk setup (0x156BED, 0x156C93). Configuration lives in `/setup/common/` (`ifindex.map`, `snmpconf`, `ttygroup`, `pri_slots`).
- **Linked 20-byte records** with tag `00 20 20 1B` appear 22,520 times (first at 0x021A00). Each record is `[0020201B][flags 00000000/04000000][0][value][next offset or FFFFFFFF]`, with next pointers stepping 0x14. They are probably tables inside compiled script or object files. Not identified.

## Device

The source is a Japanese multi-port ISDN/frame-relay access router or remote-access concentrator. It used an MC68360 QUICC, up to three line cards each with eight BRI-style ports, one WAN port and one INS1500 PRI port, and Ethernet. Confidence is **medium** for the class of device and **low** for maker and model; no product name, vendor string or version string was found on this chip. The Japanese origin rests on NTT `INS1500`, the Fujitsu flash and the English phrasing (`buffer over floow`, `FLUSH-EEPROM`). The flash array was four MBM29F016A chips (8 MB), each run by the `xflush` driver as its own byte-wide device on a 32-bit bus.

## Open questions

- **Maker and model.** The `/version` file and the boot banner are probably on another chip. Next step: search the partner chips for `/version` contents, and search the web for `xflush`, `vlserver`, `setupwan.r` and the `ABCD0200` executable magic.
- **Order of the logical units and the file system.** Next step: combine all four chips by the unit number at offset 0x24, ordering sectors by unit × 127 + sector. Then look for the superblock and inode table, and check how the 512 KB boot partition is excluded.
- **Lane 0 or 2 of the boot image.** The bigram test does not separate them, but the unit numbering (4 × index + 0) points to lane 0 (D31–D24). Interleave the four chips' 0x000400 regions to confirm and find the boot entry point.
- **Unit header 0x26 and parameter longs 0x1D45…0x1FC0.** Compare with the partner chips' headers.

## Method

I used Python 3 (`-I`) for per-sector entropy and fill maps, header tabulation across all 32 units, a pattern search for sector-start magics and directory entries, and bigram log-likelihood tests that compare the boot region with stride-2/4 lanes of this chip's own 68k code. I also used `strings -t x` and `xxd`. binwalk found no known signatures. radare2 was broken on this host, so the 68k identification rests on opcode statistics (`4E75`, `48E7`, `4FEF`, `61FF`) and manual decoding. I rendered the sector map with Pillow.
