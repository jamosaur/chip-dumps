This chip holds part of a flash file system for a Japanese WAN router. Its software runs on a 68020 or later CPU and supports ISDN (basic and INS1500 primary rate), HSD leased lines, frame relay, PPP and OSPF. All 32 erase units start with the same 64-byte unit header (`24 11 00 80 …`). Each header carries a logical unit number, and on the units that have never been erased those numbers run 1, 5, 9 … 125, all ≡ 1 mod 4. So the volume was formatted across four chips, round-robin by unit, and this is the second chip of the four. The data units hold 55 relocatable 68k executables in an unidentified `0xABCD 0200` format, setup text files and an inode table with 1998–1999 timestamps. Unit 0 also holds about 13 KB of a 68k boot program that was stored for a 32-bit bus: only every fourth byte is on this chip.

## Findings

- **Unit header.** Bytes 0x00–0x13 are the same in every unit: `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`. Plausible meanings are 0x0200 for 512-byte blocks, 0x0040 for the 64-byte header, 0x0080 for 128 blocks per unit and 0x0020 for 32 units per chip, but these are unconfirmed. The big-endian word at +0x24 is a logical unit number, +0x26 is an erase or reclaim count, and +0x2C/+0x2E hold a repeated small count (1–0x15).
- **Logical unit numbering.** Units whose erase count is 0 (units 0, 1, 3, 8 and 24–31) carry L = 4·n + 1, for example unit 8 → 0x21 and unit 31 → 0x7D. Erased units carry numbers from all four residues (0x4F, 0x3F, 0x1A, 0x4C …), so garbage collection moved logical units between chips. The volume therefore has about 128 logical 64 KB units, roughly 8 MB, spread over four chips. This chip had index 1.
- **Erase state.** Units never erased are zero-filled, including the 0x40–0x1FF area. Units erased at least once have `FF` at 0x40–0x1FF, and their stale blocks are programmed to `00`.
- **File data.** Files sit in 512-byte blocks, zero-padded to the block end. For example, the file index at 0x080200 lists `gateways /setup/common/gateways.static`, `ppp.wan1 /setup/wan1/ppp` … `wan30`, and the `telnet.def` and command-interpreter setup follow at 0x081A00 and 0x081C00.
- **Executables.** There are 55 headers that start `AB CD 02 00 05 32 00 00 06 55 06 55 06 55` (first at 0x027E00). Each has a section table naming `code`, `const`, `string`, `data` and `ram`, followed by 16-byte entries of the form (type byte, offset, size, size). Type-2 files start their code at header+0xF0 with `4EF9 00000008 4E71` (`jmp $8; nop`). The largest image, at 0x0C1200, has a code size of 0x1BA40. Short library names also appear: `stdio`, `libmisc`, `libperr` and `libmem` (0x02C4D2).
- **CPU.** The code is big-endian 68k. It contains about 6,200 `bsr.l` (`61FF`) instructions, which need a 68020 or later, and capstone disassembles it cleanly (0x0476F0, 0x0C1320). The lane-split boot strings include `caCr`, part of "CACR", the 68020+ cache control register.
- **Inode table** at 0x0F0200, 128 bytes per entry:
  - +0x02 mode, stored as octal digits in hex: 0x0755, 0x0664, 0x0777
  - +0x04 nlink
  - +0x0A size (u32)
  - +0x16 and +0x1A times: 1998-08-31 and 1999-03-25
  - +0x1E block count
  - +0x22 block numbers (u32)
  - +0x76 mtime: 1999-03-17 to 1999-03-29

  Block numbers run 0x24B2–0x2F66. Neither `n/128` nor any simple per-unit formula maps them onto this chip's units. The translation is probably held in tables that are not here.
- **Boot program lane at 0x000400–0x003880.** This region holds only every fourth byte of the original:
  - At 0x000E62, `20 20 20 28 20 20 20 20 48 10 10 10 04 04 04 10 10 81 01 01 01 01 01 10 10 82 …` is exactly every fourth entry of a C `ctype` table.
  - The commonest non-zero bytes are `8F EF 75 6F 7C 79 DF E7`. These are the second bytes of `588F`, `4FEF`, `4E75`, `4879` and `4CDF`/`48E7`, which puts this lane on an odd byte (lane 1 or 3) of 68k code.
  - The text fragments are lane-split exception and diagnostic messages: the letters of "Level 4 Interrupt Autovector", "Interrupt Vector #" and "CACR" appear but are interleaved with other strings.
  - The probable reading is a boot or loader program that the CPU runs directly from four byte-interleaved flash chips at CPU offset 0x1000 onward. The file-system driver, by contrast, treats each chip as its own linear stream, which is why the file data here is not split.
- **Product clues:**
  - PPP/LCP/IPCP statistics and the `pppstat` usage text (0x022376). The modes `TP`, `PPP1` and `PPP2` and the services `CS` and `HSD` appear at 0x023524–0x02357C.
  - `buildINS1500` (0x0A9DAF) and `[basicISDN]`/`[promaryISDN]` (0x0E69BA).
  - The `VLSERVER STATISTICS` and `vlsetup:` commands (0x0A4B88).
  - Up to 30 WAN ports.
  - STREAMS-style driver strings (`strPutNext`, `<DPut:MPROTO>`).
  - A boot parameter menu with `boot mode (mem|net|auto)` and core dump to `card` (`FLASH1`/`FLASH2`) or `ftp` (0x029537–0x0296E0).
  - A script language using `$READBYKEY`, `$SYS`, `$PLUGIN` and `VOID FUNCTION … [ … ]`.

## Device

The source is a Japanese multi-port WAN router or access server built around a 68020/030/040, with ISDN BRI/PRI (NTT INS64/INS1500), HSD leased lines and frame relay. Its main storage is an 8 MB flash disk made of four MBM29F016A chips on a 32-bit bus. Confidence is **medium** for the device class, because the evidence is the protocol set, the Japanese carrier terms (INS1500, HSD) and the `/setup/wanN` layout. Confidence is **low** for the maker and model: no product name, vendor string or version banner was found on this chip. A Fujitsu-made flash chip fits a Japanese vendor but proves nothing. The inode times suggest the unit was configured in August 1998 and last modified in late March 1999.

## Open questions

- **Maker and model.** The `show -a /version` alias points at a `/version` file, which is not on this chip. Look for it, and for any banner, in the partner chips.
- **Block translation.** Inode block numbers (0x24B2…) do not map onto unit offsets by any simple rule. Find the per-unit map or allocation table on the partner chips, or a superblock in logical unit 0, then reconstruct the volume.
- **Executable format.** The `0xABCD 0200` header with `code`/`const`/`string`/`data`/`ram` sections and the `0532 … 0655 0655 0655` fields remain unidentified. Compare it with Japanese RTOS object formats; the next step is to search for the magic together with these section names.
- **Lane index.** The boot lane is an odd lane, and the unit numbering suggests chip index 1. The exact lane needs the other three chips to interleave and test which order gives readable 68k code and text.
- **The `FB` byte at 0x0001FF** in unit 0 has no explanation yet. It may be a flag in the reserved boot unit.

## Method

Sector entropy and fill statistics, a hex dump of every unit header and `strings` came first. A block classifier then mapped zero, FF, text, code and `0xABCD` headers per 512-byte block. Lane analysis on unit 0 matched a stride-4-sampled C `ctype` table and compared byte histograms against the lanes of the clean 68k code. The inode table was decoded field by field in Python, and capstone (M68K, 68020 mode) disassembled sample entry points. All scripts ran from a temp directory against the read-only image.
