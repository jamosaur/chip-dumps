This is the flash-memory ("FM") microprogram image for a microprocessor board in a Hitachi RAID300 storage controller (DKC). It starts with a little-endian directory (`DIRDIRT` at 0x000000), followed by a version record (`MPVRT`, `5247710300`) and three `OBJDIRT` object tables. Together they index 49 compressed objects: two Unix-`compress` (LZW) streams, then 47 gzip streams that are relocatable Intel i960 COFF modules named `ACMLOADD.abs` … `ZJCLOADSD.abs`, plus a patch object `ZZPTH1D`. The modules contain `S66 0927.1 Copyright(C)1997,2000,Hitachi,Ltd.`, `Starting Scan Polling(RAID300 PH1 DKA Kernel:97-04)` and `FM data is RAID300 DATA!!`. They use VxWorks APIs (`taskSpawn`, `symFindByName`, `moduleCreate`, `loadLib`) supplied by a kernel that lives elsewhere. The image is byte-wide, complete and self-consistent. The last five sectors hold leftovers of an older 1998 build that were never erased.

## Findings

- **Directory format (little-endian).** `DIRDIRT\0` is followed by six dwords, of which four are record offsets. Each `OBJDIRT\0` record is 0x228 bytes. It holds a type (6, 2, 3), a zero, three size/address dwords, a zero, an object count and a second count, then (offset, length) pairs. The pairs tile the image exactly from 0x000AA8 to 0x1A73B5.
- The boot loader's own debug strings name these fields: `objdirp->loadidl`, `textsizl`, `datasizl`, `bsssizl` and `objdirp->objlistt[i].objptrl/objlenl`.
- Type 6 lists sizes 0x25400 / 0x3800 / 0x7400, which are the boot object's text (0x25390) and data (0x3678) rounded up, plus a BSS/stack allowance.
- Type 3 lists 0xE400 / 0x400 / 0x2000, which matches its text size of 0xE038.
- Type 2 holds 0x80400000 / 0x51B400 / 0x424000 with counts 0x2F (47) and 0x0E (14). 0x80400000 looks like a load base, and the LOADD modules are linked from 0x00400000 upward. 14 equals the 13 LOADSD modules plus the patch object.
- **Version record.** At 0x000028 is the ASCII string `5247710300`, probably microprogram version 52-47-71-03/00. The six dwords at 0x000034 are `BF8C1C6C 13AB2AEF 0DB32D55 12A7B478 10D9EEFE 10DB9F4C`. The third, 0x0DB32D55, is verified as the 32-bit byte sum of all object data from 0x000AA8 to 0x1A73B4. The other five did not match simple byte or word sums of the compressed or decompressed objects. The boot loader prints `SUM CHECK ERROR` and `inir_ldchk1 %08x`, so these are probably load-check sums.
- **CPU is Intel i960 (little-endian).** All objects have COFF magic 0x0160, which is `I960ROMAGIC`; `file` misreports it as MIPS. The executable objects carry the f_flags value 0x1016, i.e. `F_I960CORE`, with optional-header magic 0x0108.
- In the boot object's text (289 KB unpacked), the most common top bytes of the words are i960 MEM-format opcodes: `lda` 0x8C, `ld` 0x90, `callx` 0x86, `st` 0x92, `ldos` 0x88. The text also contains 432 aligned `ret` words (0x0A000000).
- **Boot/loader object (0x000AA8).** COFF dated 2000-08-24, 1814 symbol entries, source files `inirinit.c`, `inirldcf.c`, `inirldchk.c`, `acsrsini.c`, `trmtools.c`, `zcum04.s`, build tree `/project/iosk360h/local94/src`.
- It decides between loading from "SM" (shared memory) and "FM" (flash): `SM/FM SAME FM LOADING !!`, `FM/SM both invalid`.
- It decompresses both `compress` and gzip data. It has `magic_header` and `magic_header_gzip`, and the message `invalid compressed data -- crc unmatch.`.
- It relocates and links the COFF modules with a private loader (`zldcoffOpen`, `zldcoffMod`, `zldcoffSymFind`), handles patch objects (`PATCHLOAD%02d`, `BUNKATSULOAD%02d` at +0x3F18; *bunkatsu* is Japanese for "split"), and starts tasks with `taskSpawn`.
- It also contains `RAID300 A+++++++ !!` (at +0x5518) and a version pair `52475100` / `52460101`.
- **External kernel.** The boot object leaves 146 symbols undefined. They include VxWorks calls (`taskSpawn`, `taskDelay`, `symFindByName`, `symAdd`, `sysSymTbl`, `moduleCreate`, `moduleSegAdd`, `ifAddrSet`, `inet_addr`, `fopen`, `malloc`). The real-time kernel and first-stage boot must therefore sit in another ROM on the board. No VxWorks banner is in this image.
- **Application modules (gzip, all dated 2000-09-27 06:47–06:49).** The prefixes and sample symbols suggest the subsystems below. The meanings are inferred from symbol names, not confirmed.
  - RAD: RAID parity and ECC (`radm_eccchk`, `radm_hole`).
  - SCS: SCSI drive commands (`scsd_cmdmain`, `scsd_cdbwr`).
  - RCH: cache (`rchs_getslcb`).
  - STG: staging (`stgn_free_slot`).
  - DRC/DRR: destage and drive recovery.
  - MRC/RCF: copy functions (`mrcs_parsetcpypos2`).
  - ERR: error handling, including `Errt Dump Tool  Version1.0-00` / `Copy Rights(c) Honma Products 1997`.
  - TRM: flash write and erase (`trmf_ersbytewrite`).
  - SVP/DSV: service-processor link.
  - INI: initialisation (`inii_main`, `inid_getmicid`).
  - ZCU/ZJC/ZSC: CU/job/SCSI-common layers.
- `COMLOADD.abs` holds `S66 0927.1 Copyright(C)1997,2000,Hitachi,Ltd.` at +0x1F80 and the `uncompress` routine.
- The LOADSD set repeats several subsystems (ACM, DEX, DRR, ERR, JMA, PRO, RAD, RCH, RSM, SPC, STG, TSP, ZJC) linked at 0x10000000. That is probably a second memory region or a second processor's address space.
- `DEXLOADSD.abs` contains `Starting Scan Polling(RAID300 PH1 DKA Kernel:97-04)` at +0xA4D8.
- `RCFLOADD.abs` contains `FM data is RAID300 DATA!!` and `FM data is RAID200 DATA!!`, a compatibility check against the previous controller generation.
- **Patch object.** `ZZPTH1D` (gzip mtime 2001-01-25 03:08) was built from a different tree, `/project/iosim20g/local66/src`. It lists per-subsystem patch sources (`acmpatch.c` … `rcfpatch.c`, `rsmpatch.c`). The loader messages describe how it is applied: it rewrites jump instructions in already-loaded code (`can't rewrite the jump instruction code`).
- **SVP object (0x19C159).** COFF dated 2000-02-22. Sources `svp0is00.c`, `svp1is01.c`, `svp6com.c`, `dsv2fun.c`. It uses `socket`/`connect`, `semTake`/`semGive`, `dkcMain`/`NetMain`, `SYSTEM TRACE AREA DUMP`. This is the TCP/IP link to the maintenance service processor.
- **Stale tail (0x1B0000–0x1FFFFF).** This area has no directory entry. Scanning it finds `compress` headers (`1F 9D 90`) at 0x1B79D8, 0x1BC578, 0x1BC5C7, 0x1C109F, 0x1CE3E7 and 0x1F6EAF. They decompress to i960 COFF modules dated 1998-11-12 whose sizes match older DRR, ERR, JMA, PRO, RAD and RCH "SD" modules.
- The last stream's COFF header puts its symbol table at 0x215B0, but only 0x100D2 bytes come out before the chip ends. The older build therefore ran past 0x1FFFFF and continued into the next flash device.
- The new image ends at 0x1A73B5 and was zero-padded to 0x1B0000. Sectors above that were left unerased.
- **Bus layout.** Strings, gzip headers and COFF headers are intact at byte stride 1, with normal bit order. This is a whole image, not a byte lane. Multi-byte fields are little-endian, as the i960 uses.

## Device

The source is a Hitachi RAID300 disk-controller (DKC) adapter board. In the 7700E generation, Hitachi's RAID300 was sold as the Hitachi Freedom Storage 7700E and OEM'd as the HP SureStore XP256. Confidence is **medium-high**.

- The RAID300 name, the Hitachi copyright and the RAID200 compatibility check come straight from the strings.
- The mapping of RAID300 to the 7700E is from Hitachi's internal naming, where RAID400/RAID450 were the 9900/9900V. It is not stated in the dump.
- The board is most likely a **DKA (disk adapter)** microprocessor package: the modules drive SCSI disks (CDB build, bus reset), compute RAID parity, and announce a "DKA Kernel". The loader also references `CHP`/`DKP` (channel/disk processor) and `CHAID`/`DKAID`, so the same FM image may serve both adapter types.
- The 2 MB MBM29F016A is one of the board's flash-memory chips. The truncated 1998 stream at the top implies at least one more FM chip continues the address space above this one.

## Open questions

- **The other five MPVRT check values.** Try 32-bit sums of the relocated text+data images as the loader would place them (load base 0x80400000), or sums per OBJDIRT group.
- **The exact meaning of OBJDIRT type 2's 0x80400000 / 0x51B400 / 0x424000 fields and the second count (14).** Disassemble the boot loader's `inir_ldinit`/`inif_conld` routines that read `objdirp`; an i960 disassembler (old binutils `i960-coff`, or Ghidra's i960 module) is needed.
- **CHA or DKA.** Find the routine that reads the adapter ID (`inid_getmicid`) and check which branch loads the SCSI-drive modules.
- **The older 1998 build.** The next flash chip on the same board should start with the continuation of the 1998 `RCHLOADSD` LZW stream and the rest of that build's LOADSD modules.
- **Version decoding.** Confirm that `5247710300` reads as 52-47-71-03/00 against HP XP256 / Hitachi 7700E microcode release lists.

## Method

The work used Python (`python3 -I`) for per-sector entropy, run detection, directory parsing and checksum tests. Binwalk and a manual parse of the `DIRDIRT`/`OBJDIRT` tables located the 49 objects, which were carved to a temp directory and unpacked with `gzip -dc` (it handles both gzip and `compress` .Z). The i960 COFF headers and symbol tables (24-byte entries plus a string table) were parsed with a small script. The CPU was confirmed from the COFF magic and flags and from opcode statistics, because no installed disassembler supports the i960. `strings` and symbol names identified the subsystems, and searching the top sectors for `1F 9D` recovered the stale 1998 modules. The layout map was rendered with Pillow.
