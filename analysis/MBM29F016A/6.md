This chip holds one byte lane of a 32-bit flash array, with four chips side by side, used by a 68000-family CPU with a 32-bit bus. Two things show the 4-byte stride. Text fragments match English sampled every fourth character, and a hex-dump column header reads `+1 +5 +9 +D` in one place and `+3 +7 +B +F` in another, which is exactly what every fourth character of `+0 +1 +2 … +F` gives. The code is 68k: the lane is full of `B9` (from `4EB9` JSR abs.l), `75` (from `4E75` RTS) and the pair `56 E7`. That pair is `4E56` LINK followed four bytes later by `48E7` MOVEM.L to -(A7), the standard C function prologue, seen through one byte in four. A directory at the start of the chip names the modules. Three program modules called `A1` and one called `X0` sit on 64 KB sector boundaries in the first 640 KB. The other 1.4 MB is erased.

## Findings

- **Bus layout: stride 4.** Letter pairs in the string areas (0x043000–0x046000, 0x06D700–0x06E700) were scored against English skip-k bigram models. They match English sampled every fourth character (skip-4 lift +0.010 against +0.05 for a sampled reference; skip-1 −0.66 against −0.68), not stride 1 or 2. The column-header fragments `+1 +5 +9 +D` (0x043757) and `+3 +7 +B +F` (0x0437B3, 0x05013D) are the exact stride-4 samples of `+0 +1 +2 … +F`. Data bits are in normal order: ASCII letters and 68k opcode bytes appear unpermuted.
- **Which lane.** The 68k opcode bytes seen are the *low* bytes of instruction words: `B9` is the most common non-zero byte in the code (about 4.6%), and `75`, `E7` and `56` are common. High opcode bytes (`4E`, `48`, `2F`, `61`) are rare. So this chip is lane 1 or lane 3 of the big-endian 32-bit word (lane 0 = D31–D24). This image alone cannot separate 1 from 3.
- **CPU.** The lane sequence `56 E7` (LINK A6 then MOVEM.L regs,-(A7)) appears 472 times in module 1 alone. MOVEM with predecrement does not exist on ColdFire, so this is a true 68k. A 32-bit bus points to a 68020, 68030, 68040, 68EC0x0 or 68360-class part.
- **Not a boot ROM.** Offset 0 holds the directory, not a reset vector table, so the CPU starts from some other device: a boot ROM, or another bank.
- **Module directory at 0x000000.** There are 14 entries of 8 lane bytes each, so 32 bytes per entry if the directory is spread across all four lanes. Lane bytes 0–3 are a 2-character name, then `20 00`. Byte 4 is always `50` (`P`). Byte 5 varies: `65 85 10 10 50 50 50 50 60 60 60 60 60 70`. Byte 6 is non-zero only for the first three `A1` entries and `X0`: `0D`, `02`, `05`, `07`. Raw entry 0: `41 31 20 00 50 65 0D 00`.
- **Module headers.** Each module starts with a 16-byte lane header:
  - 0x010000 `41 02 69 50 0D DE 41 00 59 00 00 E7 16 00 00 80`
  - 0x050000 `41 02 69 00 02 85 41 00 59 00 00 06 08 00 00 00`
  - 0x060000 `41 02 69 00 05 A7 41 00 59 00 00 70 00 00 00 00`
  - 0x080000 `58 02 59 00 07 56 58 07 59 00 00 B7 70 00 00 90`

  Byte 0 is the module's name letter (`A` or `X`). Byte 4 equals the directory's byte 6 for the same module (`0D`, `02`, `05`, `07`), which ties the directory entries to these four sectors. Bytes 4–5 read as a 16-bit value (0x0DDE, 0x0285, 0x05A7, 0x0756) roughly track module size in units of 64 lane bytes (256 CPU bytes). The fit is not exact, so this is unconfirmed.
- **Per-chip or spread headers?** The directory names and header letters are readable as consecutive lane bytes (`A1 `). That suggests the directory and headers may be written as independent byte-wide records on each chip, rather than as one 32-bit structure spread across four chips. Comparing the partner lanes would settle it.
- **Module sizes in CPU address space**, assuming all four lanes are equally full: `A1` #1 about 0xDC980 bytes (880 KB), `A1` #2 about 0x2BB80 (175 KB), `A1` #3 about 0x50300 (321 KB), `X0` about 0x79300 (484 KB). Each 64 KB sector here is 256 KB of CPU space, so the modules start at CPU offsets 0x040000, 0x140000, 0x180000 and 0x200000 from the array base. The whole array is 8 MB.
- **Fixed-size record table** at 0x040000–0x047000 (module 1 data). Marker bytes `8B`/`8C` and `E0` recur every 0x83 lane bytes, which is 524 CPU bytes. The marker changes from `8B` to `8C` at 0x040E69, like a sequence or type field. The body is zero at first and FF from 0x041F30. A small table at 0x041DCC reads `07 00 00 00 02 00 00 00 01 01 01 01 01 02 01 01 01 01 02 02 02 02`.
- **Debug or monitor UI.** Both `A1` #1 (0x043750–0x0437F0) and `A1` #2 (0x050120–0x0501A0) contain the fragments of a memory-dump screen: column headers, `------------` rules and address and data fields such as `+0 040000` and `00 4000 C0159D`. Printf formats show up as repeated `%`, `d20%`, `xx%` and `02` fragments around 0x043E00–0x043F80 (for example `%02x`, `%08lx`, `%d`).
- **Name table in `A1` #3** at 0x06DB00–0x06DE00. It is a dense run of upper-case letters and `_`, consistent with a symbol or command-name table.
- **65C02 code inside `X0`.** From about 0x096000 to 0x09E3E0, the byte statistics change completely. The common bytes become `A9` (LDA #), `8D` (STA abs), `4C` (JMP), `20` (JSR), `AD` (LDA abs), `85` (STA zp), `EA` (NOP) and `9C`. `9C` is STZ abs, which only the CMOS 65C02 has. The lane also contains a byte bit-reversal table sampled every fourth entry. At 0x09B283 it reads `00 20 10 30 08 28 18 38 04 24 …` (bitrev8 of 0, 4, 8, 12 …). At 0x09B2A5 it reads `41 61 51 71 49 69 …` (bitrev8 of 0x82, 0x86 …). So `X0` probably packages firmware for a 6502-family peripheral controller next to 68k code.
- **Odd-aligned 68k-like block in `X0`.** At 0x093000–0x095800, the frequent bytes are the high opcode bytes `4E`, `48`, `2F`, `20`, `70`, and the pair `4E 48` (LINK then MOVEM) appears. Everywhere else the chip sees low bytes. So this block is probably a 68k binary stored at a 1-byte offset inside the `X0` file, for example a download image for a second 68k board.
- **Unused space.** 0x0A0000–0x1FFFFF is erased (FF). The four partner chips together have about 6 MB free.

## Device

The array is 8 MB of 5 V NOR flash, built from four MBM29F016A chips on a 32-bit 68k bus. Its firmware is a set of named modules with a directory and a memory-dump monitor, plus code for a 65C02-family peripheral. That suggests a fairly large 1990s embedded system, such as telecom, test or industrial control equipment, with a 68020/030/EC030 or 68360 main CPU and at least one 6502-family sub-controller. **Confidence: low** for the product class, and no maker or product can be named. The stride-4 text hides every readable word, so recovering vendor strings needs the other three lanes.

## Open questions

- **Lane 1 or lane 3?** Look at the partner chips. The other low-byte lane will show the same `B9`/`75`/`56 E7` statistics, and the two high-byte lanes will show `4E`/`48`. The order can then be found by interleaving and checking that JSR targets and strings read correctly.
- **Directory and header format.** Check whether the other lanes carry the same `A1 `/`X0 ` names at the same offsets. If they do, the headers are per-chip byte-wide records. If not, rebuild the 32-byte entries and the 64-byte headers from all four lanes and decode the size and address fields.
- **What are `S1`, `I1`, `C1`, `N1`, `E1`, `L1` and `D1`?** Their directory entries have byte 6 = 0, so they are probably empty slots or modules stored somewhere else. Once the full entries are rebuilt, their field 5 values (`10 50 60 70`) may turn out to be addresses.
- **The 65C02 target.** After interleaving, disassemble the region from 0x096000 onwards. The I/O addresses (for example `$D00C`, `$D014` seen in the lane) may identify the peripheral chip.
- **Product identity.** Interleave all four lanes and read the strings. The monitor banner, error messages and the name table in `A1` #3 should name the system.

## Method

Python 3 was used for per-sector entropy and fill, FF-run mapping, string extraction at strides 1, 2 and 4, and skip-k English bigram scoring against a local text corpus to fix the stride. 68k code was confirmed by lane-byte histograms and the `56 E7` prologue pattern, and 65C02 code by opcode-frequency tests, with Capstone (MOS65XX mode) on short regions. binwalk found no known container signatures. The sector map was drawn with Pillow from a per-256-byte classifier. Scratch files were kept outside the repository.
