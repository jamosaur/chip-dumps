This image holds bitmap font data and a few tables. It contains no code. The lower megabyte is a complete character generator for a Chinese text terminal. Each glyph cell is 16 bytes (8×16, 1 bpp, MSB = left pixel). Address bit A19 selects the left half (bank 0, `0x000000`) or the right half (bank 1, `0x080000`) of a double-width character. The cell number is `704 + GBK index`, so `啊` (B0A1) sits at cell 9777 in both banks. Cells 0–511 hold eight 128-glyph single-width sets: control pictures, ASCII, DEC Special Graphics, ISO Latin-1 and IBM code page 437. Together these point to a VT220/ANSI/PC-console style terminal for the Chinese market. The upper megabyte uses the same cell numbering with 32-byte cells, but each cell holds only one 8-pixel slice of every row of a larger font. Each glyph's 24 or so rows are all present, but only 8 of its pixel columns. The other columns are presumably on partner chips.

## Findings

- **No erased flash.** There are almost no `FF` bytes. Unused space is `00`. Bank 0 and bank 1 have the same shape (0x60630 bytes of data, then zeros to the next 512 KB boundary), which is how the left/right split at A19 was found.
- **16×16 GBK index, verified.** cell = `704 + (lead − 0x81) × 191 + (trail − 0x40, or trail − 0x41 when trail ≥ 0x80)`. Offset = `cell × 16` (left half) or `0x80000 + cell × 16` (right half). Checks: `丂` (8140) at 0x002C00, `佨` (81DC) at cell 859, `盁 盃` (B09F/B0A0) right before `啊`, and `薄` (B1A1) exactly 191 cells after `啊`. The last non-zero byte of each bank falls in cell 24674 = FEA0, the last GBK code point.
- **Coverage.** All 6,763 GB2312 hanzi, 840 of the 846 symbol cells in rows A1–A9, 6,048 of the 6,080 GBK/3 cells and 8,075 of the 8,160 GBK/4 cells. The user-defined areas AAA1–AFFE and F8A1–FEFE are blank.
- **Font-builder fingerprint.** User-defined area A140–A7A0 is not blank. Its 665 cells are byte-for-byte copies of rows AC, AD, AE, AF, F8, F9 and FA (trail 0x40–0xA0), mapped one row each: A1→AC, A2→AD, …, A5→F8, A6→F9, A7→FA. Both the 16-dot font and the large-font lane have this.
- **Non-standard GB2312 symbols.** Rows A6–A8 carry vendor additions: `☎ ♠ ♥ ♦ ♣`, pointing hands and diagonal arrows in A6, accented Latin letters and extra superscripts in A8 and A9. See the symbol sheet.
- **Single-width sets, bank 0** (0x000000). Set 0: two-letter control pictures (`NU SH SX EX …`) for 0x00–0x1F, ASCII, and a DEL symbol. Set 1: control pictures, ASCII 0x20–0x5F, and DEC Special Graphics at 0x60–0x7E (`◆ ▒ HT FF CR LF ° ± NL VT ┘ ┐ ┌ └ ┼`, scan lines, `≤ ≥ π ≠ £ ·`). Set 2: a block/box-drawing set with numbers 0–20, `½ ¼ ¥ 《 》 ≡ ≈ ∫` and a clock symbol. Set 3: control pictures for 0x80–0x9F and ISO 8859-1 0xA0–0xFF.
- **Single-width sets, bank 1** (0x080000). Sets 0–1: ASCII with DEC graphics glyphs in 0x00–0x1F (set 1 also has DEC graphics at 0x60–0x7E). Sets 2–3: the full IBM CP437 (`☺ ☻ ♥ …`, `Ç ü é …`, box drawing, Greek/maths).

- **Large-font lane** (0x100000). It uses the same cell numbering as the 16-dot font, but each cell is 32 bytes: one byte per row, rows 0–25 used, almost all pixels in rows 1–24, and 6 bytes of padding. Each byte is 8 of a glyph's pixel columns, not the whole row. The cell size is confirmed by the tail: data ends in cell FEA0, about 95 cells before the end of the index, exactly as in the 16-dot banks.
- **What the lane shows.** `─` fills all 8 bits. `┌` sets bits 3–7, `┐` sets bits 0–3, and `│`/`┼` sit at bit 3. Thin verticals are missing: `口`, `日` and `目` show only their horizontal strokes. The heavy `┃` is 1 px wide. In left-right compounds the right-hand component appears horizontally compressed: `啊` shows `阝可`, `埃` shows `矣`. So the 8 bits sample columns spread over most of the glyph width rather than one contiguous strip. The height (about 24 rows) suggests a 24×24 font split across three chips (24 bits per row), but the exact column mapping cannot be settled from this lane alone.
- **Half-width glyphs in the lane.** In single-width sets 0–1 (ASCII-based), about 75% of the non-zero bytes have equal high and low nibbles. Each half-width glyph uses 4 bits of the lane, copied into both halves of the byte (`H` = `EE CC … CC EE`).

- **GB code table** (0x1F0000–0x1F4BFF). It holds 9,728 big-endian GB2312 codes (lead byte first). Two spaces (`2020`) are placeholders. The order follows the Unicode CJK block, which is Kangxi-radical order: `一丁七丈三上下不丐丑且丕世丙丞丢并 · 丨个丫中丰 · 串 …`. The source characters look traditional: `丢` stands where `丟` (U+4E1F) sorts, `并` where `並` (U+4E26) sorts and `乱` where `亂` (U+4E82) sorts. Simplified-only characters such as `万 与 专 业` are absent. So this is most likely a traditional→simplified (Big5 or Unicode → GB2312) conversion table, but the index it is addressed by is unknown: it is neither GBK- nor Big5-indexed, and not a direct Unicode offset.
- **Records at 0x1F4F00–0x1F53FF.** Short records such as `03 2F 00 A6A4 A6AF A6CF 11 3E 00 A6A3 21 5A 00 …` mix GB2312 codes from rows A4–A7 (hiragana, katakana, Greek, Cyrillic) with control bytes whose high nibble counts up 1, 2, 3, …. They are probably LZ-style compressed mapping tables for the national character sets.
- **National sets.** At 0x1FA5D0, 0x1FADD0 and 0x1FB5D0 (glyph 0x20 of each 128-cell set) there are 8×16 sets for Russian (KOI-7 order `Ю А Б Ц Д Е Ф Г …`), hiragana and katakana. The same sets appear in the 32-byte lane format from 0x1F5800.

- **No code.** binwalk finds no signatures. There is no vector table, no ASCII text beyond glyph data, and no checksum or header anywhere. The glyph controller must compute addresses directly from the character code.

## Device

This is the character-generator flash of a Chinese-market serial text terminal (confidence **medium**). The evidence:

- a GBK 16×16 font indexed straight from the GBK code, the usual design for a hardware text-mode character generator;
- VT220 control pictures and DEC Special Graphics;
- CP437 for ANSI/SCO console emulation;
- Latin-1;
- Russian/Japanese national replacement sets;
- a traditional→simplified table, consistent with Big5 display support.

The second, wider font (probably 24-dot) spread across several chips points to a higher-resolution display mode, or to a model that offered both 16- and 24-dot Chinese text. The maker and model cannot be identified (confidence **low** for any particular brand): there are no strings, logos or version numbers.

## Open questions

- **Column mapping of the large font.** Which pixel columns does each bit of the 0x100000 region represent, and how many partner lanes are there? Next step: interleave this region with the matching regions of partner chips (same 32-byte cells, the same `EE CC…` half-width pattern) and test 3-lane/24-bit and 4-lane/32-bit bit permutations against simple glyphs such as `口`, `田` and `─`.
- **Index of the GB code table at 0x1F0000.** Next step: build the Big5 and Unicode traditional repertoires in code-point order and align them with the placeholder (`2020`) pattern, or find the firmware that reads it.
- **Format of the records at 0x1F4F00.** Next step: try LZSS and other small LZ variants with a 2-byte literal unit, and check whether the output is a Unicode-to-GB map for Greek, Cyrillic and kana.
- **Cell 703.** The cell just before 0x8140 holds a `丂`-like glyph in both fonts. It is probably an artefact of the font builder, but it could be a cursor or default glyph.

## Method

I used Python 3 (PIL) in a scratch directory. First a per-64 KB entropy and zero-fill map, then binwalk (no hits). Next I rendered regions as 8×16, 16×16 and 8×32 1-bpp glyph sheets. I found the left/right split by pairing cell N with cell N + 0x80000, and the GBK index formula by rendering anchor characters (`丂`, `啊`, `薄`, `佨`) and solving for the row stride and base. I compared the 32-byte-cell region with the 16×16 font at the same index using box-drawing and simple characters. I decoded the table at 0x1F0000 with Python's `gbk` and `big5` codecs and tested it against GBK, Big5 and Unicode index hypotheses.
