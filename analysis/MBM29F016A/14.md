This chip holds one quarter of a flash disk from a **Seiko Instruments (SII) NS-2482 "Multi Access Server"**, a 68020-based WAN access router from about 1997. The SNMP setup file reads `SysDescr "SII Multi Access Server NS-2482."` (0x15F030), and a version file reads `Communication Server NS-2482 System Software 1997.10.29 (Ver 2.2)` (0x1FC400). Every 64 KB sector starts with the same 48-byte unit header, which carries a logical unit number. Data is byte-contiguous, so the flash disk is not split across byte lanes. The logical unit numbers run up to 123 and step by 4 in the units that were never moved. That fits a 128-unit (8 MB) pool striped across four 2 MB chips, with this chip as the fourth. The payload is a Unix-like file system: 32-byte directory entries, indirect blocks, a.out and other 68k executables, setup files and scripts in the router's own command language. One exception is unit 0, which holds a 13 KB stride-4 byte lane of 68k code. That is probably a boot or monitor image laid across all four chips on a 32-bit bus.

## Layout

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x30 | Unit header, logical unit 3 (the same 48-byte header starts every 64 KB unit) |
| 0x000400 | 0x3476 | Stride-4 byte lane of 68k code and data (ends 0x003875), the rest of unit 0 is zero |
| 0x010000 | 128 KB | Units with logical numbers 7 and 11: header only, data all `00` |
| 0x030000 | 0x150000 | 21 units of file-system data (logical 19, 20, 23, 8, 67, 36, 77, 43, 48, 52, 56, 60, 71, 68, 72, 82, 81, 88, 32, 91, 28): 68k executables, shared-library stubs, setup files and scripts |
| 0x180000 | 448 KB | Seven units with logical numbers 99 to 123 (step 4): header only, data all `00` |
| 0x1F0000 | 64 KB | Logical unit 17: exception-handler code, root and `/sbin`/`/share` directories, the version file and the `ar` backup script |

## Findings

- **Unit header (all 32 units, offset +0x00):** `24 11 00 80 00 00 00 80 00 01 00 80 00 01 02 00 00 40 00 20`, then zeros to +0x23, then four varying words at +0x24, +0x26, +0x2C and +0x2E. Probable fields: magic `2411`, 0x80 blocks per unit, 0x80 logical units, block size 0x200, unit size 0x40 KB and 0x20 units per chip. Only the 0x200, 0x40 KB and 0x20 values are confirmed by the layout.
- **+0x24 is the logical unit number.** Code runs on without a break from the end of physical unit 0x030000 (+0x24 = 0x13) into 0x040200 (+0x24 = 0x14). A `pea 0x64` at 0x03FFFC is followed by `bsr.l` / `lea 12(sp)` / `rts` at 0x040200. There is no per-block remap table: each unit stores 127 consecutive 512-byte blocks (block 0 is the header).
- **Striping across four chips.** Units whose +0x26 word is 0 all satisfy logical = 4 × physical + 3: units 0, 1, 2, 5, 10 and 24 to 30 hold logical 3, 7, 11, 23, 43 and 99 to 123. The other units have +0x26 = 1 to 10 and logical numbers of any residue mod 4. So +0x26 is probably a move or erase generation, and the disk was formatted by striping units across four chips with this chip at index 3. The +0x2C/+0x2E words are always equal to each other (1 to 0x1A). Their meaning is unknown, perhaps an erase count.
- **File-system block numbers.** The indirect block at 0x031000 lists data blocks `0x973, 0x975 … 0x984`. That matches FS block = logical unit × 127 + (block in unit − 1): this block is FS block 0x974, and the data around it (the `mcftp`-style card/FTP utility strings at 0x0307BE to 0x030D9B) fills the listed blocks.
- **Directory format:** 32-byte entries, a big-endian 32-bit inode number followed by a 28-byte NUL-padded name. Deleted entries have the inode and the first name byte zeroed (for example `?ew_image_loaded`, `?s_version`, `?ocvup` at 0x1FB720 to 0x1FB7C0). Directories found include `/` children `sbin setup share stand tmp usr version vup os_version` (0x1FB600), `/sbin` (0x1FB800), `/share` (0x1FBC00), `/etc` with `hosts networks resolv.conf services` (0x155400), `/setup` with `common default ipxr lb tty1 tty2 ttyp wan1…wan30` (0x155600), and per-WAN subdirectories `fr hsd layer2 ppp pri` (0x156E00 to 0x15ACC0).
- **Executables.** Three a.out OMAGIC headers sit on block boundaries (`00 01 01 07`, machine ID 1) at 0x039800 (text 0x22B8, data 0xA80, symbols 0x564, text relocations 0x5C8), 0x04BE00 and 0x04E400. Most other programs use a different format. They import shared libraries by name (`stdio`, `libmem`, `libctype`, `libsetup`, `libmisc`, `libtelnet`) after a `4E44 4E75` (`trap #4; rts`) stub, and carry 20-byte relocation/import records with the pattern `FF FF FF FF 00 20 20 1B` (0x031200 onward).
- **CPU: 68020 or later.** Code uses `bsr.l` (`61 FF`), `link`/`unlk` and `movem` throughout. An exception-name table at 0x1F9E37 lists 68020/030 vectors, for example `Defined for MC68020 and MC68030, no used by MC68040`.
- **Networking stack:** STREAMS/TLI (`t_open`, `getmsg`, `S_IOC_MUX_UP`), OSPF daemon and tools (`ospfd`, `ospfsetup`, `ospfflagchg`, 0x042956 onward and 0x0C9126), a PPP LCP/IPCP state-machine tracer (0x0720AB to 0x073B45), ping, traceroute, ifconfig, a GRE tunnel statistics tool `tnstat` (0x05D8B6), SNMP, telnetd and `vupd` (a version-up server).
- **Interfaces** (`/setup/common/ifindex.map`, 0x15B802): three slots `P1` to `P3`, each with 8 ports plus a WAN port, logical `en0 en1 hsd1 fr1 lo0`, and `hsd11` to `hsd38`. Other files cover ISDN BRI/PRI (`PH:ISDN Cable Off`, 0x10AECA), a `pri_slots` table of 24 64 kbit/s timeslots up to `p1536` with `H0`/`H1` channels (0x15DA00), frame relay and leased "hsd" lines. T1/E1 line-interface status strings (`TAOS active`, `LOS`, `CCITT Recommendation G.703`, 0x1FA48C) suggest primary-rate hardware.
- **Command language.** Setup and command scripts use an interpreted language with `$BIND[...]`, `$PLUGIN[...]`, `VOID FUNCTION`, `VAR x:INTEGER;` and `$SYS[WAIT;...]` (for example the login shell setup at 0x05BC06 and the `linestatis` script at 0x084622). A comment in `linestatis` names the variant `NS-2282MH` (0x085116).
- **Memory card:** `mcftp`, `mcload`, `cardcheck` and `cardcopy` copy the system to and from a PC card (`-S Slot-No. : 1/2`, `Memory Card is boot device.`, 0x089D27). `fscheck` (0x0ACD76) prints file-system fields: label, magic, `conf-pmap`, block-map, file-index shift count, create date/time and per-file data and indirect block lists.
- **Unit 0 lane data (0x000400 to 0x003875)** is not byte-contiguous. A C `ctype` table at 0x000E62 has runs about a quarter of the normal length: `04 04` for the ten digits, `81 81` for A to F, five `01` for G to Z. So the region is every fourth byte of a 32-bit-wide image. 68k fragments such as `DF 75` (the low bytes of `4CDF xxxx 4E75`) and quartered text (`oderlscnrieaHrTVievIteaie`, 0x000D8B) agree. Because the region sits in this chip's first unit with logical number 3, it is probably byte lane 3 of a boot or monitor image spread over the first units of all four chips.
- **Setup is factory default.** It contains only commented examples (`# nameserver 128.30.0.3`), `127.0.0.1`, an `install` host `1.0.0.1` and users `admin : 0 :` and `somebody : 100 :` (0x15E200). Other version strings: `pppauth` `Version 1.0 ('95/09/05)` (0x08DAF6).

## Device

**Seiko Instruments (SII) NS-2482 Multi Access Server, system software Ver 2.2 of 1997-10-29. Confidence: high.** The SNMP `SysDescr` names `SII Multi Access Server NS-2482.` with sysObjectID `263.2.1`, and the version file names `Communication Server NS-2482 System Software`. The hardware is a 68020-class router with three line slots of 8 ports plus a WAN port, Ethernet, ISDN BRI/PRI, frame relay and leased lines, and PC-card boot media. Its flash disk was four MBM29F016A chips (8 MB), of which this is probably the fourth. `NS-2282MH` appears as a related model or build variant. No public documentation for either model number was found.

## Open questions

- **Which logical units are on the other three chips?** The file-system label/superblock, block map and file-index table are not on this chip; logical units 0, 1 and 2 are good candidates. Next step: match units with the same header and +0x24 values 0 to 127 that are missing here.
- **Is unit 0 a boot image or a lane-split file?** Interleaving unit 0 of all four chips (byte lanes 0 to 3) should give readable 68k code from about CPU offset 0x1000. That would settle the lane order and whether this chip is lane 3.
- **Meaning of header words +0x26 and +0x2C/+0x2E**, and of the leading words `0000 0080 0001 0080 0001`. Comparing headers across the four chips, or disassembling the flash driver (probably in a kernel file such as the deleted `?sx.sys`), would decode them.
- **The executable format** with `FF FF FF FF 00 20 20 1B` records and named shared libraries is undocumented here. Disassembling a loader stub and the `trap #4` handler would identify the OS.

## Method

Per-sector entropy and a 512-byte block map (Python) located the content. Hex dumps of every unit header showed the shared 48-byte header and the logical-unit field, which was confirmed by code continuity across a unit boundary. `strings` and a scan for 32-byte directory entries recovered the file tree, and a scan for a.out magics found the relocatable executables. The indirect block at 0x031000 checked the block-number formula. Run-length comparison of the `ctype` table showed the stride-4 lane data in unit 0. Model and maker came from the version and SNMP setup files, followed by web searches on the model numbers. The block map image was rendered with Pillow.
