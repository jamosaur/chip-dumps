This is the boot flash of a Realtek RTL8373/RTL8372-family 2.5 Gbit/s Ethernet switch. The image holds firmware for the switch chip's embedded 8051 core, built with Keil C51 and split into one common area and four code banks. The strongest evidence is in the strings. `init_8373N_8224N_QC`, `RTL8371B start`, the serial-menu text `chip sel:8373/8372: 3, 8224: 4`, and `RL6818C_pwr_on_patch_phy_v007` name the parts directly. The code itself is unambiguously 8051: it has a Keil startup routine, a putchar that polls `SBUF` (SFR `99h`), and bank-switch stubs that write SFR `96h`. Only the first 0x02F9E0 bytes are used. The rest of the chip is erased.

## Findings

- **8051 common area at offset +2.** The interrupt vectors decode correctly only if CPU address = file offset − 2. The reset vector at 0x000002 is `LJMP 2F87`, and file 0x002F89 holds the Keil C51 startup sequence (`MOV R0,#7F / CLR A / MOV @R0,A / DJNZ`, `MOV SP,#21h`). Vectors 0x0003, 0x000B and 0x0013, plus the extended vectors 0x0043 and 0x004B, jump to ISRs at 0x34A2, 0x33BD, 0x346E, 0x3452 and 0x3489. Each of these ISRs starts by saving `PSW` and selecting a register bank. The serial vector is not used, so the UART is polled.
- **Banking scheme.** Four stubs at CPU 0x0100, 0x010C, 0x0118 and 0x0124 save SFR `96h`, load it with bank 1–4, call `JMP @A+DPTR` and restore it. A table of 31 trampolines at CPU 0x0133–0x01CD (`MOV DPTR,#target / AJMP stub`) holds 29 entries into bank 1 and 2 into bank 2. Their targets match function starts only when bank *n* sits at file offset 0x4000 + (*n*−1)×0xC000 and maps to CPU 0x4000–0xFFFF. That gives 48 KB banks packed directly after the 16 KB common area. A published analysis of an RTL8372N switch describes the same layout. Generic-pointer helpers at CPU 0x0DF0–0x0E4E read constants from other banks the same way, by writing SFR `96h` and then using `MOVC`.
- **Main flow.** `main` is at CPU 0x30AE. It clears xdata variables, prints `\nRTL8371B start` through `printf` at 0x1D36, then calls switch init (bank 2 0x69C4 and bank 1 0xC90F) with a 3000 ms delay (`0x0BB8`) between them. It then loops forever over a bank 2 poll routine (0x7060) and a common routine at 0x2377. Bank 1 init code repeatedly fills 32-bit xdata variables at 0x00B5–0x00C0 and then calls a helper at 0x4ED1 with a 16-bit argument such as `0x0414`. This is probably a switch-register access routine.
- **Console.** The firmware has an interactive UART menu (help text at 0x017613). It offers raw switch, PHY (MMD), SerDes and RTL8224 register read and write (`wd`/`rd`, `wd1`–`wd3`, `rd1`–`rd3`), `rst` for a chip reset, and IEEE IOL test modes for 10M, 100M, 1G and 2.5G on ports 0–7. It also has SerDes PRBS31/PRBS9, TX amplitude and pre/post-emphasis tuning, impedance (`z0`) and an eye monitor, each for either the 8373/8372 (`chip 3`) or the 8224 (`chip 4`).
- **Eight 2.5G ports.** Every port prompt reads `port: 0-7`, and the SerDes options cover two SerDes on each chip. That fits an RTL8373 (four internal 2.5G PHYs plus a 10G SerDes) paired with an RTL8224 quad 2.5G PHY.
- **PHY patches.** Bank 1 strings `RL6818B_pwr_on_patch_phy_v006` and `RL6818C_pwr_on_patch_phy_v007` report patch loading. The bank 2 tables at 0x010324–0x012847 are their data. They hold register/value pairs and `0xA436` (address) / `0xA438` (data) pairs, which is the standard Realtek PHY SRAM/microcode patch port, followed by 8-byte masked writes (register, `0x000F`, `0x0000`/`0x0008`, value). `RL6818B`/`RL6818C` are probably Realtek's internal names for two silicon revisions of the 2.5G PHY.
- **Patch database in bank 4.** 0x028000–0x02F9B7 holds exactly 1,640 records of 19 bytes. Each record is op (1), port mask (1, always `0x0F`), page/MMD (2), register (2), msb (1), lsb (1), data (2), compare op (1) and 8 zero bytes. This matches the `rtk_hwpatch_t` layout used by Realtek's `phy_rtl826xb_patch` code. The strings `phy_rtl826xb_patch_flow`, `PATCH CHECK: Failed entry` and `phy_rtl826xb_patch_db_init` sit next to it. The four-port mask suggests the database is the patch for the RTL8224 quad PHY, which shares Realtek's RTL826xB patch framework. This is likely but not verified. Ops 1, 2 and 4 occur 1,350, 29 and 92 times, and one entry at 0x02ED2D differs (`C8 … 03 E8`, probably a delay).
- **SPI-flash driver.** Common-area strings (`__spi_flash_op_wrapper`, `spi_flash_erase`, `flash write area is protected!`, `erase_block_adr is not aligned!`) show the firmware can erase and write its own flash. However, no configuration or settings sector was found. Everything after the code is erased.
- **I2C / PSE / EEPROM.** Strings at 0x017500–0x017611 (`getPseReg`, `setPseReg`, `getEEReg`, `I2c_EE_test`, `rtk_i2c_data_read error`) show I2C access to an EEPROM and to a PSE (PoE power-sourcing) controller. The bank 1 string `mac[0]=0x%bx,…` prints a MAC address. No MAC address or serial number is stored in the image.
- **No version, date, web server or upgrade header.** There is no HTTP/HTML, no version string and no build date. The upgrade-image magic `0x12345678` documented for RTL8372N web-managed firmware is absent. This is an unmanaged-style image with only a serial console.

## Device

**Realtek RTL8373(N) + RTL8224(N) 2.5GbE switch.** Confidence is high for the chipset and medium for the product class. The device is probably an 8 × 2.5G unmanaged switch, likely with a 10G SFP+ uplink. This configuration is common in no-brand 2.5G switches sold online. The chipset and port count come straight from the strings: `8373/8372` and `8224` chip selectors, `init_8373N_8224N_QC`, and ports 0–7. The PSE (PoE controller) I2C routines hint at a PoE model, but they could be unused SDK code. `QC` in `init_8373N_8224N_QC`, together with `Please Confirm DUT & Tool_Channel!`, might mean this is a factory-test build rather than shipping firmware. However, the image boots straight into normal switch initialisation, and many vendors ship Realtek's reference firmware with its debug menu left in. The banner `RTL8371B` does not match any public part number. It may be an internal SDK project name.

## Open questions

- **Header `00 40`.** It is not confirmed as the common-area length. Next step: compare with another RTL837x flash dump, such as the RTLPlayground images, or check whether the boot ROM documentation describes it.
- **PoE.** It is unknown whether the PSE routines are actually called. Next step: trace callers of the `getPseReg`/`setPseReg` functions in bank 2 with a bank-aware disassembler (Ghidra plus a banking script).
- **Bank 3 and 4 entry.** No trampolines into banks 3 and 4 were found in the common area. Next step: find how the patch flow is entered, perhaps through function pointers or bank 2 code, using a full banked disassembly.
- **`RL6818B`/`RL6818C`.** Which physical PHY these patches target (RTL8373 internal PHYs or RTL8224) is unresolved. Next step: compare the patch data with Realtek SDK sources such as the OpenWrt or GL.iNet RTL8224 drivers.
- **MAC source.** Where the printed MAC address comes from (I2C EEPROM, chip eFuse or a default) is unknown. Next step: follow the code around the `mac[0]` format string at 0x00ECC4.

## Method

I mapped the image in 4 KB sectors by entropy and `00`/`FF` fill, ran `strings` and `binwalk` (no known containers), and hex-dumped each region start. The interrupt vectors gave the −2 common-area offset. I parsed the trampoline table at file 0x000135 and brute-forced bank base offsets by checking whether each target is preceded by a `RET`. Bank 1 fits base 0, which gives 48 KB banks from 0x004000. I then built per-bank 64 KB CPU views (common area plus bank) and disassembled the startup, `main` and the init entry points with a small Python 8051 disassembler, because rizin and the REA providers had no 8051 support in this environment. Record formats were found by striding through the tables. The layout map was rendered with Pillow.
