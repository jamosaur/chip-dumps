This chip holds one byte lane of a 32-bit flash bank, and the bank contained one Cisco IOS image for the 2500 series. Two quirks hide this. The data bits are fully reversed (D0 to D7, D1 to D6, and so on), and only every fourth byte of the CPU's view is on this chip. After the bits are reversed, the code shows 68000-family opcode high bytes, and function prologues sit 4 bytes apart. Every fourth character of the standard IOS banner is here: decimating `Cisco Internetwork Operating System Software` at phase 2 gives `sIrw rnymfr`, which appears twice. The first 16 bytes match the lane-2 view of a Cisco flash file header (magic `0x0B` from `BAD00B1E`). The name starts `c2500-i…`, and the length byte agrees with where the data ends.

## Layout

Offsets are chip offsets. CPU address ≈ chip offset × 4 + 2.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x10 | Flash file header, lane 2: magic, length, flags, date, then 4 characters of the file name |
| 0x000010 | 0x08 | a.out exec header, lane 2 (magic 0x0107, text, data and bss sizes, entry) |
| 0x000018 | 0x78 | Start of the text segment: 28 bytes, then FF from 0x000034 to 0x00008E |
| 0x000090 | ≈0xA870 | Tables with no 00 bytes: 0x04-dominated with a 3-byte period up to 0x0057FF, then FF and small even values up to ≈0x00A3FF |
| 0x00A900 | ≈0x12AB00 | 68k code mixed with strings (text segment) |
| ≈0x135418 | ≈0x46AB | Data segment: banner strings, tables, and a run of 52-byte records at the end |
| 0x139AC3 | 0xC653D | Erased (FF) to the end of the chip |

## Findings

- **Bit order.** Reversing every byte turns `0x04` into `0x20` (space), and text fragments and 68k opcodes become readable. The raw bytes have bit 0 set only 17% of the time, and in the corrected form that low bit 0 belongs to even opcode bytes.
- **Bus layout, 32-bit stride.** The corrected bytes are dominated by 68k opcode high bytes: `2F`, `61`, `67`, `4A`, `48`, `4E`, `42`, `60`, `66`. Complete 68k words are rare: `4E75` appears only 60 times in the whole image. The sequence `4E 4E 48` (unlk/rts, link, movem.l at 4-byte steps) occurs 1775 times. `4E 4E 4E FF 48`, which a 16-bit lane would give, occurs 0 times. The other phase also shows up: `4E FF` followed by a movem-mask byte (`30`, `3F`, `38`). After `4E 4E 48`, the next byte is usually `26`, `24` or `28` (move.l to d3, d2 or a4). So the chip sat on a 32-bit bus and holds the high byte of one 16-bit half.
- **Which lane.** Lane 2 (D15–D8, the third byte of each big-endian long), from the file header and a.out header below. The header bytes are only consistent if this chip holds bits 15–8 of each long.
- **Flash file header (0x000000).** Raw `D0 56 FF 00 AC 96 8C 2C`, corrected `0B 6A FF 00 35 69 31 34`, then 8 × `FF`. Recalled from memory, not checked against a source, the Cisco class-B flash file header is: magic `BAD00B1E`, length, 16-bit checksum and 16-bit flags, date, 48-byte name. It reads as:
  - magic byte 2 = `0B`;
  - length bits 15–8 = `6A`;
  - flags high byte = `FF`;
  - date byte 2 = `00`;
  - name characters 2, 6, 10 and 14 = `5`, `i`, `1`, `4`;
  - name characters 18 onwards are unwritten (FF).
  The name is therefore `c2500-i-l.1xx-4…`, 15–17 characters long.
- **Length check.** Content ends at chip offset 0x139AC2, about CPU 0x4E6B0B. Take away the 0x40-byte header and the file length is about 0x4E6ACx. Its bits 15–8 are `6A`, which matches the header.
- **a.out header (0x000010).** Corrected `01 50 1A B4 00 00 00 00`:
  - magic 0x00000107 gives byte 2 = `01`;
  - text bits 15–8 = `50`, data `1A`, bss `B4`;
  - syms `00`;
  - entry `00`, which fits the usual 2500 run-from-flash entry of 0x03000060;
  - relocation sizes `00`.
  A text segment of about 0x4D50xx and a data segment of about 0x11Axx add up to the file length. Text would then end near chip offset 0x135418, which is where the code stops and the banner strings begin.
- **IOS banner (0x13546A, repeated at 0x1354CF).** The lane-2 characters are `sIrw rnymfrI( 0frC0LVi1(,ESOA()oi  69ysSe .meo5n 5ya`. Fitted against the standard banner, this gives:
  - `IOS (tm) 2500 Software (C2500-?-L), Version 1?.?(???),`;
  - `… SOFTWARE (fc?)`;
  - `Copyright (c) 1986-199?`;
  - `Compiled Mon ?5-J?n-?? ?:?5? by ??a…`.
  The release number has three characters inside the parentheses, so it is probably `4` plus a letter, to match the file name.
- **Compiler style.** Functions use `link a6` + `movem.l …,-(sp)`, and the stack is cleaned up with `lea n(sp),sp` (`4F` is a common opcode high byte). This is 68k, not ColdFire: the ColdFire prologue pattern `4E 4E 4F 48` never occurs.
- **Trailing table (0x1398D5–0x139AC2).** 52-byte records (13 lane bytes each) of the form `05 05 00 00 00 XX 00 00 00 XX 00 00 00`. XX rises slowly and concavely from `39` to `50`.
- **Tables at 0x000090–0x00A8FF.** No 00 bytes over about 43 KB, mostly `04` and `FF` with a 3-byte period, then FF and small even values. Their meaning cannot be read from one lane.

## Device

**Cisco 2500-series router or access server (68EC030), high confidence.** The evidence:

- the IOS banner fragments, `2500` and `(C2500-…-L)`;
- a file name starting `c2500-i`;
- a 68k instruction stream on a 32-bit bus;
- a single run-from-flash ("-l") image in the Cisco flash file format.

Four 2 MB Am29F016B chips make an 8 MB 32-bit bank, which fits a 2500 flash SIMM. The image fills about 5.03 MB of it. The feature set is probably the base IP image (`-i-l`), from IOS 11.x or 12.0. The copyright year ends 199x.

## Open questions

- **Exact IOS version and build date.** These need the other three lanes: interleave them with this one at stride 4 after reversing the bits on each chip, then read the banner at about CPU 0x4D5100.
- **Header field layout.** The class-B header layout above is recalled, not verified. Check it against the full header from the other lanes (the magic should read `BA D0 0B 1E`).
- **The tables at 0x000090–0x00A8FF.** Lane-split, so their contents are unclear. Decode them once the full words are available.
- **The board's data-bit reversal.** It could come from the SIMM's wiring or the reader adapter. Compare the bit order of the partner chips.

## Method

Python 3 for these steps:

- per-sector entropy and fill statistics;
- a test of address-line permutations and a bit-reversal translation, which fixed the bit order;
- byte-transition statistics on 68k opcode high bytes (prologue patterns at 2- and 4-byte strides), which fixed the bus width;
- searches for known strings decimated by 4 at each phase, which identified IOS and the banner.

Lane 2 was confirmed by fitting the Cisco flash file header and the a.out header against the image's end offset. binwalk found no signatures, which is expected for a lane-split image. The content map was rendered with PIL.
