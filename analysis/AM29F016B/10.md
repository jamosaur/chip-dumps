This chip holds one byte out of every four of a Cisco IOS "mz" router image. It is the most significant byte lane (D31-D24) of a big-endian 32-bit flash bank. The other three lanes were on other chips. Word-aligned magic numbers show only their first byte: `BA` of the Cisco Class B flash file magic `BAD00B1E` at offset 0, `7F` of an ELF header at 0x000010, `FE` of Cisco's `FEEDFACE` compressed-image header and `P` of a ZIP local header. The opcode bytes of MIPS code form clean prologue and epilogue sequences. Reading every fourth character of the stub strings gives `Self decompressing the image :`, `Cisco Internetwork Operating System Software`, an `IOS (tm) 3?00 Software (C36?0-..-M), Version 1?.0(?)T` banner, `Copyright (c) 1986-199? by cisco Systems, Inc.` and `Compiled Wed 24-Feb-99`. The rest of the chip is the ZIP-compressed IOS image, which ends cleanly at 0x175AB6, followed by erased flash.

## Layout

Offsets are on this chip. Image byte = 4 × chip offset.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x10 | Class B flash file header, lane 0 (magic, length, checksum, date, name) |
| 0x000010 | 0x47 | ELF32 header and program/section header area of the IOS file (image byte 0x40) |
| 0x000057 | 0xCFC | MIPS self-decompression stub code (opcode bytes only) |
| 0x000D53 | 0x304 | Zero fill |
| 0x001057 | 0x1BF | Stub message strings, every 4th character |
| 0x001216 | 0x5B | Inflate tables (cpdist, mask_bits) and other data |
| 0x001271 | 0x5B | IOS version banner, every 4th character |
| 0x0012CC | 0x27 | Zero fill and a few data bytes (`80 00 00 23 00 00 00`) |
| 0x0012F3 | 0x05 | `FEEDFACE` compressed-image header |
| 0x0012F8 | 0x1747BF | PKZIP archive: local header, deflate data (about 5.8 MB across all lanes), central directory, end record |
| 0x175AB7 | 0x8A549 | Erased (`FF`) to the end of the chip |

## Findings

- **Bus lane.** The code region's opcode histogram (6-bit field of each byte) is dominated by SPECIAL, addiu, lw, sw, jal, lui, beq and bne. Sequences such as `8F 03 27` (lw ra / jr ra / addiu sp) and `27 AF` (addiu sp / sw ra) recur at function boundaries (for example 0x000068, 0x0003A3). So each byte is the top byte of a 32-bit instruction: one lane of four, stride 4.
- **Endianness.** At 0x001268 the bytes `00 00 00 00 00 03 0F 3F FF` are the high bytes of every second entry of the 16-bit `mask_bits` table from gzip's `inflate.c` (0x0000, 0x0003, 0x000F, ... 0xFFFF) stored big-endian. A little-endian layout would give `01 07 1F 7F` instead. At 0x001252, `00 00 01 02 04 08 10 20 40` matches the inflate `cpdist` table the same way. So the CPU is big-endian MIPS, and this lane is byte 0 of each word (D31-D24). Data bits are in normal order: the ASCII decodes directly.
- **Class B file header (0x000000).** `BA 00 A4 49 63 30 2D 31 2D 00…`. These bytes fit the 64-byte Cisco low-end (Class B) flash file header: magic `BAD00B1E`, a length with MSB 00, a checksum with high byte `A4`, and a date with high byte `49`. If the date is Unix time, it falls between Oct 2008 and May 2009, probably when the file was copied to flash. The name has `c` at character 0, `0` at 4, `-` at 8, `1` at 12 and `-` at 16, with NUL at 20. That is a 17-20 character name such as `c36?0-..-...1...-...`. The field layout comes from memory, not from a reference I could confirm. The magic byte, the 64-byte size and the following ELF header all agree with it.
- **ELF header (0x000010, image byte 0x40).** `7F 01` (ELFCLASS32), then `80` at the e_entry position (KSEG0 entry point) and `20` at the e_flags position (EF_MIPS_ARCH_3, MIPS III: R4600/R4700/R5000 class). Further `80` bytes at 0x00001F/0x000020 are p_vaddr/p_paddr of the first program header. I could not tie the later `80` and `10` bytes (0x000028 to 0x000050) to a header layout.
- **Stub code (0x000057-0x000D52).** About 13 KB of MIPS code in the full image. COP0 and CACHE instructions cluster at 0x000095-0x000111, which is cache initialisation and flushing before control passes to the unpacked image. A run of about 50 near-identical short functions at 0x0003A3-0x0005BA looks like call wrappers, probably into the ROM monitor. The block at 0x000D06-0x000D52 (`24 AC` repeated) is an unrolled store loop.
- **Stub strings (0x001057-0x001215).** These lane matches are exact: `Self decompressing the image : ` (lane 0x0010ED), `Expected a checksum of` (0x0010DC) and `checksum is incorrect` (0x001114). Register-dump style labels ending in `a0`, `a1`, `a2`, `a3` sit at 0x001196-0x0011AF.
- **Version banner (0x001271-0x0012CB).** Reconstructed from every fourth character, this reads `Cisco Internetwork Operating System Software`, then `IOS (tm) 3?00 Software (C36?0-??-M), Version 1?.0(?)T, RELEASE SOFTWARE (fc?)`. The lane characters `O t 3 _ t e 3 - M _ s _ 0 T R A S W _ 1` fit this exactly, with double spaces at two places. Then `Copyright (c) 1986-199? by cisco Systems, Inc.` (`C r t ) 8 9 b i _ t , c`) and `Compiled Wed 24-Feb-99 ..:.. by c...`. 24 February 1999 was a Wednesday.
- **FEEDFACE header (0x0012F3, image byte 0x4BCC).** `FE 00 00 9A 9D`: magic, two sizes below 16 MB and two checksums with high bytes `9A` and `9D`. It sits exactly 20 bytes (five words) before the ZIP archive. That matches Cisco's self-decompressing image layout: magic, uncompressed size, compressed size, two checksums, then the archive.
- **ZIP local header (0x0012F8, image byte 0x4BE0).** The lane bytes are `50 14 08 58 09 5D F4 00 36 49 49`, which decode as:
  - signature `P`;
  - version needed 0x14;
  - method 8 (deflate);
  - date low byte 0x58 (day 24, month 2);
  - CRC byte 2 = 0x09;
  - compressed-size byte 2 = 0x5D;
  - uncompressed-size byte 2 = 0xF4;
  - extra length 0;
  - name characters 2, 6 and 10 = `6`, `I`, `I`.
- **ZIP central directory (from image byte 0x5D6A89, lane 0x175AA3).** The lane shows bytes 3, 7, 11 and so on: `02 00 00 26 A6 00 00 00 00 00 00 33 2D 42`. These give:
  - date high byte 0x26, so with the local low byte the date is 1999-02-24, matching the compile date;
  - CRC = `A6 09 ?? ??`;
  - compressed size about 0x5D1E7F (about 6.1 MB);
  - uncompressed size `00 F4 ?? ??` (about 16 MB);
  - name characters 1, 5 and 9 = `3`, `-`, `B`.
- **Archive member name.** Together with the local header, the name is 12 characters, `?36?0-I?.BIN`, almost certainly `C3640-IS.BIN` or `C3620-IS.BIN` in DOS 8.3 form.
- **End record (lane 0x175AB1).** The lane shows bytes 1, 5, 9, 13, 17 and 21: `4B 00 00 00 1E 00`. These are the `K` of the end-of-central-directory signature, a central directory size below 256, and a central directory offset whose byte 1 is 0x1E. A central directory at zip offset 0x5D1EA9 agrees with all three. The archive is 0x5D1EF9 bytes and ends at image byte 0x5D6AD8, the last lane byte before the `FF` fill. The ZIP is therefore complete across the four lanes, and no second flash file follows it.
- **Compressed data statistics.** Lane entropy is 7.95 bits/byte from 0x001300 to about 0x110000 and 7.99 from there to 0x175AA0. In the first part every bit is set 54% of the time, against 52% after. This probably marks a change in what is being compressed inside the IOS image, such as code giving way to data. It is not a sign of damage.

## Device

**Cisco 3600-series modular router (3620 or 3640 most likely), system flash. Confidence: high for Cisco 3600 IOS, medium for the exact model.**

- The flash file, ELF, FEEDFACE and ZIP structures are the standard Cisco "mz" image in a Class B (low-end) flash file system.
- The banner names "3?00 Software" and an image `C36?0-??-M`. The ZIP member `?36?0-I?.BIN` and the MIPS III, big-endian, KSEG0 code all point to the 3600 family, which uses R4700 or R5000-class CPUs.
- Four 2 MB AM29F016B chips on a 32-bit bus make an 8 MB flash SIMM, a stock 3620/3640 system flash size.
- The image is IOS 12.0(x)T built 24 Feb 1999, which fits 12.0(3)T, probably the IP Plus (`IS`) feature set. The 3660 was released later in 1999, so a 3620 or 3640 is more likely.

## Open questions

- **Exact model, feature set and release.** The banner and file name are missing three of every four characters. The partner lanes would give `C3620`/`C3640`, the feature letters and the version.
- **Full flash file name and header fields.** The full name, length, checksum and flags need the other three lanes. Next step: reassemble with the partner chips and parse the 64-byte header.
- **Contents of the compressed image.** Inflating the ZIP needs all four lanes. Once the bank is rebuilt, check the inflated ELF's CRC against `A6 09 ?? ??` and its size against `00 F4 ?? ??`.
- **Meaning of the date field.** The header date high byte `49` (Oct 2008 to May 2009) is 10 years after the build date. Confirm the Class B header layout against a reference tool or a known-good flash image before relying on it.

## Method

I checked the SHA-256, then computed per-sector and per-4 KB entropy, fill bytes and per-bit statistics with short Python scripts. Hex dumps of the head, the code/text transition and the tail followed. binwalk found nothing because every structure is lane-split. I identified stride 4 and the MIPS architecture from a histogram of the 6-bit opcode field and the recurring prologue/epilogue byte sequences. I fixed endianness and lane by matching the inflate `mask_bits` and `cpdist` tables. To read the strings, I slid candidate Cisco strings over the lane at all four phases and kept only exact multi-character matches. I decoded the Class B, ELF, FEEDFACE and ZIP structures field by field from the bytes visible at 4-byte spacing and cross-checked them (the archive length from the end record against the lane offset of the end record, and the date across the two ZIP headers). The region map was rendered with Pillow.
