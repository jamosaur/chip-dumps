This 2 MB image is one byte lane of a ROM set that fed a 32-bit big-endian 68000-family bus (68020 or later, or ColdFire). The chip holds every fourth byte of the CPU's view. The other three lanes were on three other chips. Most of the evidence comes from screen images. They render cleanly as 8-bit-per-pixel pictures 512 pixels wide when each chip byte is taken as every fourth pixel. One of them is a title screen reading `GOLD TOUCH Multi-Game`, and others show bingo cards, game symbols and a pirate-ship scene. The program area is full of 68k opcode high bytes (`4E`, `48`, `2F`, `4C`) in the pattern a single 32-bit lane would produce. A small sector holds records that the machine wrote at run time, and the top 256 KB holds 8-bit unsigned PCM audio.

## Layout

Offsets are chip offsets. The CPU address of chip byte `o` is probably `4·o + 2` from the base of the ROM set.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x000100 | Lane of the 68k exception vector table (256 vectors) |
| 0x000100 | 0x000300 | Lane of a header: fixed-width text fields at 0x000118–0x00017F, then initialised data |
| 0x000400 | 0x02FA80 | Lane of 68k program code |
| 0x02FE80 | 0x008180 | Lane of strings (upper-case menu and test text, `%d`/`%s` formats) and constant data |
| 0x038000 | 0x008000 | Sparse tables (mostly zero, small values such as 07, 08, 3A–3C) |
| 0x040000 | 0x001C2E | Records written in-system (meters or event log); rest of sector erased |
| 0x041C2E | 0x00E3D2 | Erased (FFh) |

## Findings

- **Stride 4, not 2.** In the code area the bytes `48` (`H`) and `4E` (`N`) are the most common after `00`, so this lane carries opcode high bytes. If the chip held the high byte of every 16-bit word, epilogues would show `4C 4E 4E` (`movem.l`, `unlk`, `rts`). Instead `4C 4E` occurs 641 times and `4C 4E 4E` only 4 times. Runs like `HHHHHN` (0x0013FB) also fit: five 4-byte `pea` instructions followed by `jsr` each put exactly one opcode high byte on a 32-bit lane. A row width of 128 chip bytes, which is 512 CPU pixels, is what makes the images line up.
- **The lane is probably bits 15–8 (lane 2 of 0–3).** Three things point that way.
  - The lane carries opcode high bytes, so it is lane 0 or lane 2.
  - The vector table bytes look like the middle of addresses in low memory. The reset PC byte is `0A`, the default handler `95` repeats for vectors 2–63, and user vectors carry `81 81 8C 95 8C 18 4C 95 27` at 0x000040 and `4D`/`4E`/`4E`/`4F` at 0x000080–0x0000B0. As top bytes of addresses (lane 0) these would be scattered across the 4 GB space.
  - The 1-bpp font slices at 0x05A000 show right-hand edges of glyphs such as `)` and the right halves of digits. That fits pixels 16–23 of a 32-pixel row.
- **Vector table.** It starts at 0x000000 with `00 0A 95 95 …`. Initial SSP byte 2 is `00` and initial PC byte 2 is `0A`. Every exception vector from 2 to 63 has `95`, so they all go to one default handler.
- **Header text.** Text fragments sit in 64-byte CPU slots at 0x000118 (`S -G C`), 0x000128 (`RN.`), 0x000138 (`ce8 3`), 0x000148 (`X`), 0x000158 (`P`), 0x000168 (`C `) and 0x000178 (`RDy`). Each is every fourth character of a longer string. `ce8 3` and `RDy` may come from a date or build string, but the rest of the text is on other lanes.
- **Strings.** The strings at 0x02FEF0–0x037FFF are mostly upper-case with `%d`, `%s`, `%1` formats. Fragments like `CRCR` (0x0368C3), `TKST`, `WIN`, `ERR` and `PRT` hint at service or test menus, but nothing reads as words from one lane.
- **Run-time records at 0x040000.** This is the only sector with an erased tail inside the low half. Its data stops at 0x041C2E, so the machine almost certainly wrote it as non-volatile storage. The first block repeats roughly every 23–24 chip bytes, so the record is probably about 94 CPU bytes and not a multiple of 4. Fields include a rising value `F3 F3 F4 F4 F5 F5 F6 F6 F6 F7 F7 F8 F8` (possibly a date or counter) and a 16-bit-like field `02 12`, `02 94`, `02 A4`, `02 B6`, `02 91` …. That suggests bookkeeping meters or a play log.
- **Lookup tables at 0x050000.** The bytes `01 03 05 … FD FF` are a byte table T[x] = x/2 seen at x = 4k+2. Similar ramps follow, and then large zero-filled tables to about 0x05A000.
- **Graphics.** Row-to-row correlation peaks at 128 chip bytes over 0x05F8A8–0x0680xx, 0x080000–0x08FFFF, 0x0A4000–0x0AFFFF, 0x0D8000–0x0EFFFF, 0x120000–0x127FFF and 0x14B800–0x153FFF. Those are full 512-pixel-wide screens. Other blocks correlate at 15, 23 and 24 chip bytes (60, 92 and 96 pixels): sprite sheets for reel and card symbols. The screens begin part-way into a 512-byte row, so they probably carry a small header or follow each other back to back.

- **Audio.** 0x1C0000–0x1F6FFF has a byte histogram centred on `80` and falling off symmetrically (`80` > `81`≈`7F` > `82`≈`7E` …). Neighbouring bytes are close (mean step 9–35), and short `80` silence runs separate samples (for example 0x1D0F54, 225 bytes). That is unsigned 8-bit PCM. On a 4-way interleave each lane would hold every fourth sample, which still looks smooth for low-pitched sound.
- **No compression or filesystem.** binwalk finds no known signatures, and the only high-entropy area is the audio.

## Device

The best guess is a **"Gold Touch" multi-game gambling or amusement machine** (bingo plus slot or keno-style games). The confidence is **medium** for the type of machine and **low** for any specific maker or model. The title text and game screens are direct evidence. The CPU is a 68000 family part with a 32-bit data bus, so a 68020/68030/68EC020 or a ColdFire. It runs from a 4 × Am29F016B set (8 MB) and drives an 8-bit palettised display at least 512 pixels wide. The in-flash log sector suggests the ROM set doubled as non-volatile storage. A web search for "Gold Touch Multi-Game" found no matching product.

## Open questions

- **Exact lane and CPU address of chip byte 0.** Interleaving this image with its three partner chips would confirm lane 2. Then the vector table can be read in full and the code disassembled from the reset vector.
- **CPU model (68020+ vs ColdFire).** Disassemble the merged code and look for instructions ColdFire lacks, such as `movem` with predecrement, byte or word `cmp` forms, and `link`/`bfext`.
- **Palette.** The renders use palette indices as grey levels. The palette is probably in another lane or in the data area. Look for 256-entry RGB tables after merging the lanes.
- **Record format at 0x040000.** Decode it after merging, and compare it with the meter labels in the strings.
- **Audio sample table.** Find the start/length table, probably in the data area or at 0x1F7000, and confirm the sample rate.
- **Header text at 0x000460 (CPU).** It needs the other lanes. It may hold a copyright, version or date.

## Method

Worked in a temp directory with Python 3 (`-I`), `xxd`, `strings` and `binwalk`. Steps were per-sector entropy and fill statistics, counts of 68k opcode byte patterns to choose between stride 2 and 4, and a row-width search (mean absolute difference between rows for widths 4–700). Images were rendered with PIL as 8-bit grey from 128-byte rows, stretched 4× horizontally to restore the aspect ratio. The horizontal seams of the screens were removed by choosing a start offset. Audio was recognised from its byte histogram, sample-to-sample step size and silence runs.
