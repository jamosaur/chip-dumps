This 2 MB image is one byte lane of a 32-bit flash bank. In it, the most significant byte of every 32-bit word belongs to a PowerPC system. Code regions show the top bytes of PowerPC instructions in the usual proportions: `38`/`39`/`3C`/`3D` (addi/addis), `7C`/`7D`/`7F` (opcode 31), `80`–`83` (lwz), `90`–`93` (stw), `48`/`4B` (b), `40`/`41` (bc) and `4E` (blr/bctr). The prologue sequence `94 7C 93` (stwu r1; mflr; stw) occurs 2,837 times. Consecutive bytes here are consecutive instructions, so the CPU sees one byte from this chip in every four (stride 4). The other three lanes, D8–D31, were on three more chips, so the bank was 4 × 2 MB = 8 MB. The content is organised in 256 KB CPU blocks, one per 64 KB sector of this chip, and each block starts with a small `M` header. Blocks 0 and 1 stand alone. Blocks 2–9 are chained into one image of about 1.8 MB. Block 31, at the top, has a different header and holds records and settings. A CPU address is 4 × the offset on this chip (plus the lane offset 0).

## Findings

- **Byte lane and bus width.** The byte histogram of 0x040040–0x07FFFF matches PowerPC primary opcodes 14, 31, 32, 18, 15, 16, 36, 24, 11 and 21, in that order. Adjacent bytes decode as adjacent instructions: `94 7C 93 …` is stwu, mflr, stw, and `7C 4E` is mtlr followed by blr. That gives stride 4, with this chip on the most significant byte (D0–D7 in PowerPC numbering, lane 0). The bit order is normal: the opcodes are plausible without any permutation.
- **Reset vector.** Only 5 bytes are set between the block 0 header and 0x000800. They are `20` at 0x00003F (CPU 0xFC) and `3C 38 7C 4E` at 0x000040 (CPU 0x100–0x10C). That is the classic PowerPC reset stub: load a 32-bit address with lis/addi, move it to CTR or LR, then branch. The reset vector sits at offset 0x100 of the flash. With an 8 MB bank, the alias of 0xFFF00100 would be chip offset 0x1C0040, which is erased. So the board most likely took exceptions at 0x00000100 with the flash decoded at address 0 during boot. MPC8xx or MPC5xx parts with the right reset configuration do this, as do 6xx/7xx cores with MSR[IP]=0. That last point is an inference.
- **Block headers.** Every used 64 KB sector (256 KB at the CPU) starts with `4D 00 00 00`. Lane bytes 4 and 5 act as chain flags: `FF FF` for blocks 0 and 1, `FF 80` for block 2, `80 80` for blocks 3–8 and `80 FF` for block 9. That reads as "has predecessor" and "has successor", so blocks 2–9 form one image. Byte 6 varies per block (`12 A5 2F 4A BA BB 9A A7 2E 1A`), probably the top byte of a checksum. Byte 8 is always `80`. Byte 10 is `FF` in block 0, `71` in block 1 and `00` in blocks 2–9, possibly a type code. Lane bytes 0x0C–0x3E are erased. The byte at 0x3F (CPU 0xFC) varies per block: `20 1B 83 E8 78 77 97 8A 03 98`.
- **Boot code.** PowerPC code runs from 0x000840 (CPU 0x2100) to 0x000BFF and from 0x000C58 to 0x0018F3. Its prologues and epilogues (`94 7C`, `7C 4E`) are intact. Before it, 0x000800 holds `52 42 00 FC F9 4D 49 65 73` followed by zeros. That is a lane of some header or table at CPU 0x2000; its meaning is unknown.
- **Parameter table in block 0.** 0x008000–0x0083EF holds 63 records of 16 lane bytes (64 bytes at the CPU). Byte 0 is an index running from `01` to `17`, bytes 1–8 are a lane-split name (`Pem`, `Pern`, `SP in`, `I rds`, `I0eds` …) and bytes 9–15 are a lane-split value (`PRA`, `D8XSX36`, `292`, `02:93`, `M86`, `22`, `31` …). From index `08` on, the records come in pairs whose second member has a short name and the value `22` or `21`. This looks like a board or slot description table, but only every fourth character is here.
- **Block 1 (unknown sparse data).** About 53 KB on this chip (≈ 211 KB at the CPU) is mostly `FF` with sparse cleared bits, with patterns such as `3F FF 3F FF F3 3F FC CF`. No row period turns up in an autocorrelation, and 1-bpp renders at many widths show no image. The chunking into runs of about 736 and 1,500 bytes separated by FF gaps fits frame- or column-organised configuration data. Possibly this is an FPGA/CPLD bitstream (low confidence), but it could equally be compressed or packed data.
- **Big-endian ARM code inside the chained image.** In block 2 most non-zero bytes are `E0`–`EB` (`E5` LDR/STR, `E3` MOV/CMP immediate, `E1` register ops, `E2` ADD/SUB, `EB` BL, `E9`/`E8` STMDB/LDMIA, `EA` B), mixed with conditional forms `0A`, `1A`, `9A`, `3A`, `BA`, `DA`, `03`, `13`, `05`, `15`. These are ARM condition-code top bytes, and on lane 0 they mean ARM big-endian code: 0x0200C0–0x02A2C1 and 0x02B943–0x02FFB0, about 200 KB at the CPU. Small ARM pieces also sit at 0x033CCA–0x033E07 and 0x034FD5–0x03513F, padded with `FF`. Lane-split printf strings with `\r\n` are interleaved. This is probably firmware for an ARM-based coprocessor or peripheral chip, which the PowerPC application downloads at run time.
- **PowerPC application.** From 0x0340CA to the end of block 7, and into block 9, the data is PowerPC code interleaved with string tables. The strings include many `D:`-prefixed debug messages (from 0x039A51), lane-split help text containing `%` format specifiers, `\r\t` and `L2`, and identifier/message pairs such as ` PXMTLE` / `ErF raspe` and ` PX_CTD` / `ErraaIfom sti` (0x090040 on). There are also `TX…` and `NB…` mnemonic tables (0x03EB89, 0x03E678). No RTOS banner (VxWorks, pSOS, OSE, Nucleus, Linux) projects onto this lane at any of the four alignments.
- **Block 31 (records and settings).** The header is `4D 00 52 4E 07 00 B2 0F 00 00 00 00 05 00 00 00 00 00 54 00 53 00 43 00 54 00 55 00`, giving `T S C T U` at every other lane byte. Then 4-byte records `B2 xx 00 00` follow, where xx is `D`, `T`, `K`, `I`, `P`, `F` or `H`. The `B2` byte moves one lane position later in each 16 KB run: offset 0 in 0x1F0000, offset 1 in 0x1F4000, offset 2 in 0x1F8000 and offset 3 in 0x1FC000, where the records end at about 0x1FD01C. So the CPU-side record stream drifts by 4 bytes per 64 KB, a sign that the records are not 16 bytes long at the CPU, or that the stream has periodic headers. A small structured area at 0x1FF220–0x1FF820 holds repeated `00 08 00 40` and `00 90` words. The last byte of the chip (CPU 0x7FFFFC) is `4D`.
- `RN` occurs both in the block 2 image (0x020080, CPU 0x200) and in the block 31 header (0x1F0002). It may be a shared signature split across lanes.
- No standard container signatures were found (binwalk: none). The blocks are not ELF, COFF/XCOFF or compressed streams as far as one lane can show.

## Device

The device is an unidentified embedded system built around a 32-bit PowerPC with 8 MB of boot flash made of four Am29F016B chips. It also carries a second processor or ASIC with an ARM core, whose big-endian firmware is stored in the main image. **Confidence:** high for "PowerPC, 32-bit bus, this chip is D0–D7, ARM firmware embedded"; low for the product class. The `L2`, `TX` and `D:` debug fragments, a `1S1 hzo2S2 hzo…` list (0x039B85) that may name per-slot frequencies,, together with the slot or board table in block 0, point loosely to telecom or network equipment (a line card or controller). Reading the text needs the other three lanes.

## Open questions

- **Product identity.** All strings are lane-split. Interleaving this chip with the D8–D31 chips, at stride 4 with this chip first, would make the help text, the `D:` debug messages and the block 0 table readable.
- **Block header meaning.** The full 256-byte headers (CPU 0x00–0xFF of each block) need all four lanes. Check whether byte 6 together with lanes 1–3 is a CRC over the block and whether the word at CPU 0xFC is a length.
- **Block 1 contents.** Interleave the lanes and look for an FPGA sync word (Xilinx `AA 99 55 66`, Altera/Lattice preambles) or a compression header at CPU 0x40100.
- **ARM firmware.** Once the lanes are interleaved, disassemble the code at CPU 0x080300 onwards as ARM big-endian to find its entry point and the peripheral it drives. Then identify the chip from the register addresses it touches.
- **Block 31 record format.** Use the full words to work out the record length and why the alignment drifts by 4 bytes per 64 KB.
- **Exact CPU.** Disassemble the boot code at CPU 0x2100 with all four lanes and look at the SPR numbers (IMMR 638 means MPC8xx, HID0/HID1 mean 6xx/7xx).

## Method

I checked the SHA-256, then mapped per-sector entropy and the fill levels of `FF` and `00` with a Python script. I hex-dumped every sector header and content boundary, and ran binwalk and strings. To fix the bus layout, I took byte histograms of the code regions and mapped them to PowerPC primary opcodes, and checked that adjacent bytes formed instruction sequences (stwu/mflr/stw, mtlr/blr). I found the ARM regions the same way, from the `E0`–`EB` condition-code top bytes. I tried autocorrelation and 1-bpp renders on block 1. I projected about 200 candidate vendor, RTOS and keyword strings onto the lane at all four alignments. All scripts ran with `python3 -I` in a temp directory, and the sector map was rendered with Pillow.
