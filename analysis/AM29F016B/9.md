This chip holds one byte out of every 32-bit word of a Cisco IOS router image. The data bits are reversed: chip bit *i* is CPU bit 7−*i*. Once the bits are flipped back, English letter frequencies appear, but the text reads only every fourth character. Long fragments match well-known IOS strings exactly when sampled at stride 4, with no mismatches. One example is `Coterpt tSw`, the stride-4 sample of `Cisco Internetwork Operating System Software`. Fitting the banner gives `IOS (tm) 2500 Software (C2500-P-L), Version 11.?(4), RELEASE SOFTWARE (fc1)`, `Copyright (c) 1986-1998` and `Compiled Tue 1?-?u?-98 … by phanguye`. The code is 68k, and the image starts with what is almost certainly a Cisco flash file header (magic `BAD00B1E`). This chip is lane 1, carrying CPU data bits D23–D16. The 4.8 MB file fills the first 1.17 MB of this chip, and the rest is erased.

## Layout

All offsets are chip offsets. CPU address = 4 × offset + 1, relative to the start of the flash bank.

| Offset | Size | Contents |
|---|---|---|
| 0x000000 | 0x10 | Flash file header, lane 1 only: magic byte `D0`, length byte `4A`, checksum byte `92`, date byte `00`, then file-name characters 1, 5, 9, 13 and 17 (`2 - . - i`); the rest is `FF` |
| 0x000010 | 0x26 | Start of the IOS file (CPU 0x40): header bytes `02 49 01 05 00 00 00 00 …` (bit-corrected), consistent with an a.out exec header |
| 0x000036 | 0x59 | `FF`, unused header space |
| 0x00008F | ~0x0FF70 | Pointer and lookup tables (lane bytes `04`, `0C`, `20` and similar in long runs) mixed with sparse `FF`-filled tables |
| 0x010000 | ~0x117000 | 68k code with string pools spread through it (the orange cells in the map); IOS CLI help, logger formats and HTML pages |
| 0x127000 | ~0x3FD5 | Version banners at 0x12700B and 0x1270D4, then initialised data and repetitive tables up to the end of the file |
| 0x12AFD5 | 0xD502B | Erased (`FF`) to the end of the chip |

## Findings

- **Data bits reversed.** Every byte is wired D0↔D7, D1↔D6, D2↔D5, D3↔D4. A search over all 40,320 bit permutations for 64-byte windows rich in lower-case letters finds 1,171 windows under full reversal, against a median of 10. Among the permutations that score equally, upper/lower-case and letter-frequency checks (`e n t s i a r o` order) leave only full reversal. `00` and `FF` are unaffected, so the erased tail and zero fills look normal in the raw dump.
- **Stride 4, so a 32-bit bus.** Byte frequencies show no 2- or 4-byte alignment. Letter pairs are nearly independent (a common-bigram ratio of 1.13, where text read at stride 1 gives 2.78). Stride-4 samples of stock phrases are found, with shuffled-letter controls near zero: `lg ed` and ` hrr.` (from `All rights reserved.`), `cian` 62 times (`configuration`), `vdpdc` (`Invalid input detected`), `Agsmd` (`Ambiguous command`), `eRRotad` (`Press RETURN to get started`) and `H>ATE` (`<HTML><HEAD><TITLE>`). Stride-2 and stride-8 samples of the same phrases do not occur.
- **Lane 1 (D23–D16, big-endian).** Long runs of one constant byte equal bits 23–16 of their own CPU address: `11` ×1028 at 0x046E35 (CPU 0x11B8D4), `37` at 0x0DDC57 (0x37715C), `3E` at 0x0FB089 (0x3EC224), `0C` at 0x032311 (0x0C8C44) and `08` at 0x020F2A (0x083CA8). These are tables of pointers to nearby addresses. This also places the bank on a 16 MB boundary; on a Cisco 2500, flash sits at 0x03000000. The header bytes below support the same lane.
- **Flash file header** (likely Cisco "class B": magic, length, checksum and flags, date, name[48]). Byte 0 is `D0`, the second byte of `BAD00B1E`. Byte 1 is `4A`, which fits a file length of about 0x4ABF1x, since the data ends at CPU 0x4ABF54. The name characters at positions 1, 5, 9, 13 and 17 are `2 - . - i`, which matches `c2500-p-l.113-4.bin` (or another `c2500-?-l.NNN-N.bin`), followed by `FF`.
- **IOS file header at 0x000010.** Bit-corrected lane bytes are `02` (machine type 2 = 68020 in a SunOS-style a.out magic), `49` (text size about 0x49xxxx), `01` (data size about 0x01xxxx), `05` (bss), then `00 00` (syms and entry; an entry at 0x0300xxxx would give `00`). Cisco 68k images are a.out-based, so this is likely an a.out header, but only one byte of each field is visible.
- **68k code.** The commonest bit-corrected 4-byte run is `5E 56 E7 6E` (1,072 times). It fits lane bytes of `4E5E 4E75 | 4E56 xxxx | 48E7 xxxx | 2x6E`: the end of one function (`unlk a6; rts`) and the start of the next (`link a6; movem.l …; move (d16,a6)`). Runs of `56 5E 56 5E` are empty `link/unlk/rts` stubs. Frequent lane values `75` (rts), `B9` (jsr abs.l), `8F` (addq.l #n,sp), `78` (pea abs.w), `2E`/`6E` (a6-relative) and `80` (tst.l/clr.l d0) fit the low bytes of 68k opcode words.
- **Version banner** at 0x12700B (second copy at 0x127070). It fits `Cisco Internetwork Operating System Software \nIOS (tm) 2500 Software (C2500-P-L), Version 11.?(?), RELEASE SOFTWARE (fc1)\nCopyright (c) 1986-1998 by cisco Systems, Inc.\nCompiled ??e ??-???-?? 0?:?0 by phanguye` with zero mismatches.
- **Short banner** at 0x1270D4 fits `2500 Software (C2500-?-L), Version 11.?(4), RELEASE SOFTWARE (fc1)\nCompiled T?? 1?-?u?-?8 ??:?? by phanguye`. Together the two give: feature set P (Service Provider), version 11.?(4), built on a Tuesday in June, July or August 1998, by `phanguye`. A copyright of 1998 with maintenance release 4 points to **11.3(4)**, but the minor digit is on another lane.
- **Embedded web pages.** Lane samples of HTML tags (`H>ATE` ×3, `</` ×18, `<D/L` from `</BODY></HTML>`, `t-eeh` from `Content-type: text/html`) show the IOS HTTP server pages that came with 11.x.
- The image ends at chip 0x12AFD4 (CPU 0x4ABF54). Nothing follows it, so the flash held exactly one file.

## Device

**Cisco 2500-series router (68EC030), flash bank of four AM29F016B: high confidence.** The banner names `2500 Software (C2500-P-L)`. The code is 68k, the flash is 32 bits wide, and the image runs directly from flash (the `-l` suffix and pointer tables that point into the flash itself). Four 2 MB chips make the 8 MB of flash that a 2500 with a Service Provider image would carry. The bit-reversed data lines are probably the board or SIMM routing, which Cisco's own software never sees. They could also be an artefact of the reader adapter, which a partner chip read the same way would show.

## Open questions

- **Exact version, build date and file name.** The minor version digit, the day and month, and most of the name are in lanes 0, 2 and 3. Read them from the partner chips at the same offsets (the banner at 0x12700B to 0x127040).
- **Header fields.** Only one byte of each 32-bit field is here. Combine all four lanes to get the length, checksum, date and a.out sizes, then check the flash checksum.
- **Whether the bit reversal is on every chip.** Check the partner lanes with the same letter-frequency test.
- **Disassembly.** Real disassembly needs all four lanes interleaved as big-endian longs and loaded at 0x03000040.

## Method

I hashed the image and mapped it by sector (entropy, `FF` and `00`), then ran binwalk, which found nothing. A brute-force search over the 40,320 data-bit permutations, scored on how many windows were rich in lower-case letters, found the full bit reversal. Letter-pair statistics measured against English corpora sampled at strides 1, 2, 4 and 8, together with searches for stride-4 samples of stock phrases checked against shuffled controls, fixed the stride at 4. The 68k identification came from recurring prologue and epilogue lane bytes, and the lane from constant-byte pointer runs that match their own addresses. A small fitting script, which places lane characters at positions 0, 4, 8 and so on of a candidate string and reports any mismatches, reconstructed the version banners. Python 3 with numpy and Pillow; the scratch scripts are not kept.
