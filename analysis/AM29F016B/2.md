This image is part of a flash file volume from a modular ATM multiservice access device. The volume has a flash translation layer (FTL) of 516-byte units, each a 4-byte tag plus one 512-byte logical sector, and a small file system on top. The files are a compressed firmware image of 677 KB, an 18 KB image tagged `6.01b3`, a table that maps PCI IDs to module types (`oc3`, `ds3e3`, `ds1e1`, `ces`, `ima`, `atm25`, `j2`, `enet`, `ospvideo`, `rvx`), a Vermont Views forms library for the craft-terminal menus, a termcap file and a Java applet archive. Most module IDs use PCI vendor `1284h`, which is assigned to Sahara Networks, Inc. Cascade bought Sahara in 1997, and Ascend then bought Cascade. All file timestamps fall between 05:02 and 05:06 on 27 March 1998. The dump itself is faulty. Address lines A15 and A19 had no effect when it was read, so only 512 KB of the 2 MB was really captured. That 512 KB appears four times.

## Layout

The second half of each 64 KB erase unit (`+0x8000`–`+0xFFFF`) is a copy of the first half, and `0x080000–0x0FFFFF` and `0x180000–0x1FFFFF` are byte-for-byte copies of the 512 KB below each of them. The table describes only the 32 KB pieces that were really read.

## Findings

- **Read fault.** A15 and A19 made no difference to the data: 0 of 1,048,576 byte pairs differ across either bit, while every other address bit from A10 to A20 changes more than 90 % of bytes. FTL units run straight across the `+0x8000` boundary (unit 63 starts at `+0x7EFC`) and their sequence breaks there, so the copies are a reading artefact rather than how the data was stored. Only 512 KB of the chip's contents is known.
- **FTL unit format.** Each 64 KB erase unit holds 127 units of 0x204 bytes. Each unit is a little-endian u16 status followed by a u16 logical sector number and 512 bytes of data. The status values are `FFFE` for live data (991 units seen), `FFFC` for obsolete (12), `FFFF` for free (3), and `FF8A`/`FF88` for the volume header unit (at 0x000000 and 0x170000). Logical sectors run in long sequential runs. For example, 0x0C9–0x1FC fill erase units 2–5 and 7 in order.
- **Volume header** at 0x000004, read as u32 LE: date bytes `1B 03 CE 07` (27/3/1998), time `0E 02 05 00` (05:02:14), `4E`, `1AD`, `2`, then u16 pair `20`/`40`, `37`, `10000` (erase unit size), `400000` (volume size 4 MB), `360000`, `0`, u16 pair `4`/`2`, u16 pair `204`/`200` (unit and sector size), `1B49`, `1A8E`, u16 pair `7F`/`4` (127 units per erase unit), `FEC00000`. The 4 MB volume over 64 erase units means this 2 MB chip is one of two. `FEC00000h` is probably the flash base in the CPU's address map. The two header copies differ only in the status byte (`8A` and `88`).
- **Volume label.** Logical sector 2 (chip 0x1768D4) starts `Disk #1`, then `6D 5B 2F 01`, date 1998-03-27 05:02:19, `8E 1A 00 00` (0x1A8E = 6798 logical sectors, about 3.3 MB), then 4, 5, 6, 0x45, 0, 0xFE.
- **File records** are 128 bytes each, four per logical sector, with record *n* in logical sector *n*/4. The fields are `01 00 03 00`, then the date and time (d, m, yyyy, s, m, h), `0x10000`, the size in bytes, the first logical sector, the sector count, and the sector count repeated at `+0x70`. Files are stored contiguously. The live records, from logical sectors 7–9, are:
  - Records 28–36: nine 452-byte files at logical sectors 0x46–0x4E, written 05:03:59–05:04:04.
  - Record 37: 18,376 bytes at 0x4F (the `6.01b3` image), written 05:04:05.
  - Record 38: 677,030 bytes at 0x73 (the compressed image), written 05:04:26.
  - Record 39: 994 bytes at 0x59E (the module-ID table), written 05:04:27.
- **Older record copies.** Obsolete copies of logical sectors 0x0C and 0x12, at 0x027CF8, 0x037AF4, 0x0678F0 and 0x107CF8, show more files mid-copy:
  - Record 48: 712,312 bytes at 0x78A, written 05:05:08 (the forms library).
  - Record 49: grows from 27,740 to 48,076 bytes at 0xCFA (the termcap file).
  - Record 50: grows from 72,716 to 89,364 or more bytes at 0xD58, probably the Java archive.
  - Records 72–74: 118 bytes, 13 bytes and 35,344 or more bytes at 0xF09–0xF0B, written 05:05:50–05:06:01.

  The whole volume was evidently loaded in one session of about four minutes.
- **File header.** Every file starts with seven u32 LE words: type, unpacked length, checksum, stored length, and three further words. The checksum's low 16 bits are the byte sum of the stored data and its high 16 bits are `0003`. The checksum is verified on the `6.01b3` image (`0x53DB`) and on three of the `bmkr.bin` files. Type 2 is stored data, with unpacked length equal to stored length. Type 4 is compressed.
  - `6.01b3` image (chip 0x060004): `02 00 00 00 AC 47 00 00 DB 53 03 00 AC 47 00 00`. A 16-byte version field `6.01b3` follows, then `88 47 00 00 88 3D 25 43 00 80 00 00`. The rest is 32-bit little-endian words. `FE40DEADh` occurs 93 times and looks like a NOP or filler. Words `03C0xxxxh` look like jumps to 16-bit targets. The word statistics do not fit i960, ARM or MIPS, so this is probably microcode for a module processor and not host CPU code.
  - Compressed image (chip 0x064894): `04 00 00 00 B4 B5 1C 00 2F 0D 03 00 8A 54 0A 00 30 53 3E 00 00 00 00 00 4A BE 11 00`, meaning 1,881,524 bytes packed into 677,002. The packed data has entropy 7.76 bits per byte, with no byte-aligned literals. zlib (raw, zlib and gzip framing), LZMA and Unix-compress LZW all fail at the start of the packed data. It is probably the main firmware, packed with a bit-oriented LZ/Huffman scheme.
  - `bmkr.bin` (chip 0x176AD4 and on): the name sits in the 16-byte field after the header. The data is a small table of u32 values (2, 2, 1, 0x200, 0x80, 0x240, …) and repeating 16-byte entries `01 00 00 00 06 00 10 00 …`, probably per-slot or per-bookmark configuration.
- **Module-ID table** (chip 0x010004): `61 10 02 00` (count or version), then 14-byte entries: PCI vendor (u16 LE), device (u16 LE), an 8-byte NUL-padded name and `00 31`. Vendor `1284h`, which pci.ids lists as Sahara Networks, maps to `oc3`, `ces`, `ds1e1`, `ds3e3`, `atm25`, `ima`, `j2` and `ospvideo`. DEC `1011:0009`, `1011:0021` and `1011:0024` (21140 Ethernet and the 21052/21152 PCI bridges) map to `enet`. Intel `8086:0960` (i960 RP) maps to `rvx`.
- **Forms library** (chip 0x000810 and on): Vermont Views form records. Each record is an s16 LE tag (`FFEB` = `FM_BEGIN:`, `FFEC` = `FM_END`, `FFF4` = label, …), a u32 LE record length that includes the tag, and strings with u16 length prefixes. The screens cover SONET/SDH path and line counters (`sntlCurCVs`, `sntsCurSEFs`, `Configure OC-3 / STM-1 Path (Advanced)`), DS1/E1 and DS3/E3 performance and faults (`dsx1CurLCVs`, `TS16 LOMF`, `ds3AlmLOS`), `ATM Port Statistics`, `Delete CES Connection`, `Processor Utilization`, MAP selection `[ATM...]`/`[NLI...]`/`[SLIP...]`, and system utilities (`Zmodem`, `[Exit to Shell]`, `DD-SSS-YYYY`).
- **Termcap** (chip 0x0176F5): a VT100 entry `d1|vt100|vt-100|vt100-80|pt100|pt-100|dec vt100:` with comments `by Vermont Views` and `Modified for the Designer`. An obsolete copy of a later sector (0x0676EC) holds a second entry with `<SHIFT-F4>` key labels.
- **Java applet archive.** A stored ZIP local header at 0x077B35 names `Poller.class` (1,427 bytes, CRC `D0274141`, DOS date 1998-03-23 09:27:26). Partial units at 0x037EFC and 0x047CF8 hold constant-pool strings such as `(Ljava/awt/Point;Ljava/lang/String;LHotSpot;I)V`, `_TEXTAREA`, `pollFactor`, `NORMAL_FACTOR` and `Ljava/awt/Frame;`. This is a Java AWT management GUI shipped on the device.
- **Byte order and bus.** The text and every structure read contiguously, so the chip was an 8-bit-wide part with no lane splitting and no bit swapping. All file system fields are little-endian.

## Device

**Sahara Networks multiservice ATM access concentrator, sold later under Cascade/Ascend. Confidence medium for the maker, low for the model.** The module table names Sahara's PCI vendor ID (`1284h`) for nearly every line card. The cards are OC-3/STM-1, DS3/E3, DS1/E1, J2, IMA, ATM25, circuit emulation, video and Ethernet, which matches Sahara's voice, video and data access over ATM. The menus match a carrier access box: TR-style performance counters, CES connections, slot/POD/port addressing, a VT100 craft interface built with Vermont Views and a Java applet GUI. The controller is probably an Intel i960 RP. Its PCI ID appears as module `rvx`, the flash sits at `FEC00000h` (the i960 Rx boot region at the top of memory), and the file system is little-endian. The chip is one of two AM29F016B parts making up a 4 MB flash file volume.

## Open questions

- **Missing three quarters of this chip.** A15 and A19 had no effect, probably because of a bad adapter contact or a damaged pin. Next: reseat the chip and re-read it, checking first that A15 and A19 toggle.
- **The other 2 MB chip.** Logical sectors 0–1, 3–6 and 0x0A–0x13 (most of the file records, with names if any) and the rest of every file are elsewhere. Next: find the partner chip, which has the same unit format and an `FF8x` header with the same date bytes.
- **Compression of the type-4 image.** Next: get the boot code, probably a separate boot ROM or the partner chip's top sectors near `FEFFFF30h`, and find the decompressor. Alternatively, try LZ77 variants with bit-packed flags, LZH, or PKWARE implode on the packed data from chip 0x0648B0.
- **What runs the `6.01b3` image.** It looks like 32-bit microcode with a NOP word `FE40DEADh`. Next: compare it against SAR and network-processor instruction sets of the period (for example the IBM or Maker ATM SARs) and work out the jump-target format.
- **The exact model.** Next: look for Sahara, Cascade or Ascend access-concentrator manuals that mention `ospvideo` or `rvx` modules.

## Method

Python 3 scripts for per-sector entropy, an address-bit mirror test (comparing byte pairs across each address bit), a parser for the 0x204-byte FTL units that rebuilds logical sectors by number, and decoders for the volume header, file records and file headers. Also `strings` and `xxd` for inspection, `binwalk` (no signatures found), Python zlib, LZMA and a hand-written LZW for decompression attempts, and the local `pci.ids` plus a web search to identify PCI vendor `1284h` and Sahara's ownership history. The unit map was drawn with Pillow.
