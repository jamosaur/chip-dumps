This chip is one of four 8-bit flashes on a 32-bit big-endian PowerPC bus. It holds the most significant byte (lane 0) of every 32-bit word. Each byte here is the CPU's byte at address `4 × offset`. In the code regions the byte values are almost all PowerPC primary-opcode bytes: `38` (addi), `7C` (opcode 31), `48`/`4B` (b/bl), `80`–`83` (lwz), `90`–`93` (stw), `40`/`41` (bc), `2C` (cmpwi), `3C` (lis) and `4E` (blr). Standard stack frames show up as the run `94 7C 93 93 93 90` (stwu, mflr, stw ×3, stw r0), and the matching epilogue is `80 7C 83 83 83 38 4E`. Several blocks are ARM code instead: nearly every byte has `E` as its high nibble (ARM condition "always"), and functions start with the APCS prologue `E1 E9 E2` (mov ip,sp; stmfd; sub fp). The used area is about 0x95000 bytes, or about 2.4 MB of CPU address space. It is split into 256 KB erase blocks (64 KB per chip), and each block starts with a 64-byte header beginning with `M`. The rest of the chip is erased.

## Findings

- **Stride 4, lane 0 (MSB).** The PowerPC opcode byte is the first byte of each big-endian instruction, and here every code byte is an opcode byte. The 6-byte prologue `94 7C 93 93 93 90` (for example at 0x0352F6 and 0x060040) only makes sense as six consecutive instructions. Testing permutations of address bits A0–A3 on the text at 0x090040 confirmed the identity order: strings run in normal order with stride 4 and no bit swaps.
- **Block headers.** Every used 64 KB sector (0x000000, 0x010000 … 0x090000) starts with a 64-byte header followed by 52 `FF` bytes. Byte 0 is `4D` (`M`), bytes 1–3 and 7 are `00`, and byte 8 is `80`. Bytes 4 and 5 are flags: `FF FF` in blocks 0 and 1, `FF 80` in block 2, `80 80` in blocks 3–8 and `80 FF` in block 9. This most likely means "continued from previous" and "continues into next", so blocks 2–9 hold one object. Byte 6 varies (`12 A5 2F 4A BA BB 9A A7 2E 1A`), and so does byte 0x3F (`20 1B 83 E8 78 77 97 8A 03 98`). These are probably checksums or sequence values. Code runs straight across the headers: the PowerPC code that fills up to 0x03FFFF carries on at 0x040040 with the epilogue `7F 38 4B 3F 63 7F 83 83 83 80 7C 38 4E`. So the stored objects skip the headers, which looks like a simple flash file store rather than a flat ROM image.
- **Reset stub.** The four bytes at 0x000040 (CPU 0x000100, the classic PowerPC system-reset vector) are `3C 38 7C 4E`. This is the usual load-address-and-jump sequence (lis, addi or ori, mtctr or mtlr, bctr or blr). No other exception vectors are populated. That suggests a 60x, 7xx, 82xx or 8xx-class core that boots at 0x100 or 0xFFF00100. It is not a 4xx core, which would have its reset branch at the top of flash; the end of this chip is erased.
- **Image headers.** The boot image at 0x000800 and the ARM image at 0x020080 both start with a 64-byte header whose first byte is `R` (`52`). The second byte is a type letter (`B` and `N`), the third is `00`, and lane-split name text follows: `MIes` and `MIDCocbg`. Without the other lanes neither the length fields nor the full names can be read.
- **Boot code** at 0x000840–0x0018F3 starts with the same startup sequence as the PowerPC program at 0x0340CA (`7C 7C 3C 38 3D 39 48`). It contains repeated `3C 38 7C 4C` groups (lis / addi / mtspr / isync), the usual pattern for setting up special registers. The boot code ends with a small table `80 00 00 00 00 01 01 01 01 01 01 01 01 01 01 00 …` at 0x0018DA.
- **Parameter table** at 0x008000: 63 records of 16 lane bytes (64 CPU bytes). Byte 0 is a group number (`01`–`17`), bytes 1–8 hold a name field and bytes 9–15 a value field. Visible name fragments are `Pem`, `Pern`, `Clem`, `SP iNe`, `I rds` and `I0eds`–`I6eds`. Value fragments are `PRA`, `D8XSX36`, `02:9e`, `M84`, `M86`, `M1S4`, `Iad`, `25` and `29`. Groups 08–17 each hold a pair of records with two-digit values, so this probably stores board inventory or per-port settings.
- **Sparse-bit block** at 0x010040–0x01D383 (CPU 0x040100–0x074E0C, about 211 KB). It is 52% non-`FF` bytes, mostly with a single bit clear (`7F FE FD BF F7 EF DF FB`), and has no row period that would make it an image. This is typical of an SRAM-FPGA configuration bitstream in which unused bits are 1. It is probably loaded into an FPGA by the boot code. The FPGA family is not determined.
- **ARM images.** The ARM blocks between 0x0200C0 and 0x03513F have their condition byte in the same lane as the PowerPC opcodes. So the ARM code is stored big-endian, or was written as big-endian 32-bit words. Format strings survive in fragments (`\r` followed by `%`, `%x`, `%d`). There are command-table-like strings at 0x02D980 (`[ pf …][ kf …]`) and a table of 4-character mnemonics at 0x021DC1 (`ACKCMCMSuLCM …`). Lane-split `PPC` appears at 0x02157D. These look like firmware for one or more ARM-based coprocessors that the PowerPC host loads.
- **Main application** at 0x035251. It starts with lane-split strings (`OUloe TaaSpe r e%`) and then PowerPC code at 0x0352F6, running to 0x07FFFF. After it comes a zero-filled area of about 250 KB (CPU), from 0x080040 to 0x08FA24.
- **Message table** from 0x08FA24: fixed 140-byte (CPU) records, 35 lane bytes each. Each holds a mnemonic beginning ` PX` (` PXMTLE`, ` PX_CTD`, ` PXTTC`, ` PXVCERD`) and a message beginning `Er` (Error) or `Wi` (Warning). `Wi:Tnnop`, `Erpf` and `Wi Phb ed` are typical fragments, and the message text includes `%x`, `%d` and `%o` format fragments.
- **Command table** from 0x09080C: 60-byte (CPU) records with lower-case command names beginning `px` (`pxtma`, `pxtmd`, `pxttk`, `pxtsra`, `pxgea`) and argument hints in angle brackets (`<g>`, `<I`, `alm>`). This is a debug or maintenance CLI.
- **End of object** at 0x094732: a short trailer `01 00 00 00 C0 00 00 C0 00 8D`, then zeros to 0x094777. The bank is erased from CPU 0x251DE0.
- No compressed streams were found (binwalk reports nothing), and the code is not compressed.

## Device

The device is probably telecom or networking equipment with a PowerPC host CPU (60x, 82xx or 8xx class, judging by the reset vector at 0x100) and four parallel Am29F016B chips forming an 8 MB, 32-bit boot and firmware bank. Next to the host CPU sat an FPGA loaded from flash and one or more ARM-based coprocessors whose firmware the host downloads. The `PX`-prefixed alarm and error mnemonics, the Error/Warning message table and the `px…` maintenance commands point to an embedded line card or controller rather than a consumer product. The make and model cannot be identified from this one lane. Confidence: high for the architecture and bus layout, low for the device type.

## Open questions

- **Full strings, names and versions.** The other three lanes hold the rest of every string. Interleave this chip with the partner chips (stride 4, this chip first) to read the message table, the command help, the image names in the `R` headers and any version or copyright string. There appears to be an `@(#)`-style string at 0x0945A6 (`@ yhc91 lecl pt`).
- **Block header format.** Only the high byte of each header word is here. The partners would show whether the varying words at header bytes 6 and 0x3F are checksums, erase counts or sequence numbers.
- **CPU model.** With the full 32-bit words, decode the mtspr/mfspr SPR numbers in the boot code at 0x000840. IMMR (SPR 638) would point to an MPC8xx or 82xx, and BAT or HID0 setup to a 60x or 7xx.
- **FPGA family.** With full words, check the start of the bitstream at CPU 0x040100 for a vendor preamble (Xilinx `AA 99 55 66` sync, or the Altera/Lattice headers).
- **ARM targets.** Full words would allow the ARM images to be disassembled and their load addresses found, which should identify the coprocessor chips.

## Method

I worked through the image with Python scripts (`python3 -I`), `xxd`, `strings` and `binwalk`. Steps: per-sector entropy and FF/00 maps; FF-run listing with CPU addresses (offset × 4); byte histograms per region to tell PowerPC primary-opcode bytes from ARM condition bytes; a brute-force test of A0–A3 address permutations against English bigrams on the message table; and a per-256-byte classifier used to draw the content map. I also tried lane-split string searches for common RTOS and vendor names (none matched) and an autocorrelation of the sparse-bit block (no row period). No disassembly was possible, because only one byte of each instruction is on this chip.
