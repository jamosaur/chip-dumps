This chip held one byte of every 32-bit word in a 4-chip, 8 MB flash bank on a big-endian PowerPC board. Every structure in it repeats at a stride of 4 CPU bytes per chip byte. The bytes that survive are bits 23–16 of each word (byte offset 1 in big-endian order). The clearest evidence is at chip offset `0x000040`, which is CPU offset `0x100`, the PowerPC system-reset vector. The bytes there are `60 63 68 80`. That is the bits-23–16 lane of `lis r3,hi` / `ori r3,r3,lo` / `mtlr r3` / `blr`, the usual jump out of the reset vector. Further on there are thousands of lane-split PowerPC prologues and epilogues, and two blocks of big-endian ARM code with APCS stack frames. A 256 KB-per-block chain carries the firmware, and the last sector holds an event log. All text is reduced to every fourth character, so it is unreadable without the other three chips.

## Findings

- **Stride 4, lane D23–D16.** At 0x000040 (CPU 0x100), `60 63 68 80` matches the bits-23–16 bytes of `3C60xxxx 6063xxxx 7C6803A6 4E800020`. PowerPC prologues show up as `21 08 81 a1 c1 e1 01`: `stwu r1` / `mflr r0` / `stw r28..r31,x(r1)` / `stw r0,x(r1)`. Epilogues show up as `01 08 21 80`: `lwz r0` / `mtlr r0` / `addi r1,r1` / `blr`. Between 0x0340C0 and 0x07F500 there are 2,936 `21 08` pairs, 2,594 `01 08 21 80` runs and 687 `81 a1 c1 e1` runs. Bytes 81/A1/C1/E1 for r28–r31 are only possible if this lane holds bits 23–16. Text decodes as plain ASCII, so the data bits are in normal order.
- **The boot loader and the main application use the same EABI start-up.** Both start with `63 63 40 42 a0 ad`, at 0x000840 and at 0x0340CC. That is the lane of loading r3 and then setting r2 (`_SDA2_BASE_`) and r13 (`_SDA_BASE_`) with `lis`/`addi`. This is the PowerPC EABI small-data set-up used by Diab, GCC and similar compilers.
- **ARM code is a separate, big-endian image type.** In 0x0200D1–0x02A380 the sequence `a0 2d 4c` appears 296 times, and 190 of those follow a `1b` byte within 8 bytes. These are bits 23–16 of `mov ip,sp` (E1A0C00D), `stmfd sp!,{…}` (E92D….) and `sub fp,ip,#4` (E24CB004), with `ldmdb fp,{…}` (E91B….) as the epilogue. This is the APCS frame convention of ARM SDT/armcc or GCC `-mapcs-frame`. These bytes land in the same lane as the PowerPC opcode fields, so the ARM image is stored big-endian. Image B (0x02B943, 177 prologues) shares some routines with image A but is a different build. Neither image starts with an ARM vector table, so they are probably images that the PowerPC host downloads into ARM co-processors or line cards.
- **Block headers.** Each non-empty 64 KB sector starts with a 0x40-byte (0x100 CPU byte) header. Byte 0 is `44`, bytes 1–3 are `00`, byte 4 points to the previous block, byte 5 to the next block, byte 6 varies (`ca 55 d9 96 93 0b 9b a9 f0 0c`, probably a checksum), byte 8 is the block's own address, byte 9 is `03` (or `00` on the last block of a chain, `ff` on block 0), and byte 10 is a sequence-like value (`80`, then `06 09 0d 11 15 19 1d 21`). Byte 0x3F also varies. The address bytes are bits 23–16 of bank offsets: block 2 says own `08` (0x080000), next `0c`. The chain runs 08→0c→10→14→18→1c→20→24 and ends with next `ff`. Block 1 (`04`) stands alone.
- **File header records.** At 0x000800 and 0x020080 the same record type appears: `01 44 00 xx` followed by the bytes `44 61 65 63 65 73` ("Daeces"). These are every fourth character of a name or description field that the other lanes complete. 0x020040 holds a type-`05` record. The two ARM fragments and the main PowerPC image after the holes have no header at all; the bytes in front of them are erased.
- **Erased holes inside the firmware chain** at 0x02A380–0x02B942, 0x030CC0–0x033CC9 and 0x033E10–0x0340C9. Code resumes right after each hole at a function prologue. This lane cannot show whether the holes are deliberate gaps, deleted files, or a rewrite that was interrupted.
- **Key/value table at 0x008000** (CPU 0x020000). Each record is 64 CPU bytes. Word 0 is an index (`01`–`0e`), words 1–8 are a 32-byte name field (`CN`, `CRs`, `CSaur`, `uCN`, `SU r`, `S rds` as seen in this lane), and words 9–15 are a 28-byte value field (`RES`, `M43`, `m107`, `nl`, `onl`, and two-digit numbers such as `91`/`30`). Groups like `CN/CRs/CSaur/CAO/CS/CD/CDDrl` repeat, and pairs like `SU r`/`SR` recur with changing values. This looks like an inventory or manufacturing record of cards and modules, or a history of their serial numbers and revisions.
- **Strings.** The boot loader strings (0x001160–0x0013A2) each start with `0d`, i.e. character 1 of each word-aligned string is CR, which fits `"\n\r…"`. They contain `%` format markers. In the main application, 0x039C00 onward has many short strings beginning `I`, ` `, `:` in this lane. 0x03D800 holds tables of short enum-like names. 0x08F800 holds command-line help text with argument placeholders (`d<g>`, `<r  >`, `alm>`, `<et>`), which suggests a router or telecom-style CLI.
- **Sparse-zero data in block 1** (0x010040–0x01CCDF). About 11 % of bits are 0, spread evenly across all eight bit positions. Rows of all-FF bytes appear at irregular intervals, and some parts show diagonal structure with a period of about 346 chip bytes. It is not code. It may be a lane of a mostly-white 1-bpp bitmap or some sparse table; this lane alone does not decode it.
- **Event log in the last block** (0x1F0000). After a distinct header, records from 0x1F001C are 4 chip bytes (16 CPU bytes) each, for example `2d 50 19 00`. Byte 0 is a slowly rising counter, probably bits 23–16 of a timestamp; it wraps from `ff` to `00` near 0x1F3264. Byte 1 is an event letter (`P`, `Y`, `B`, `S`, `D`, `E`, `K`, `N`, `W`, `I`). Byte 2 is mostly `19`, `0f` or `10`. Byte 3 is `00`. After about 0x1F4020 come counter-only records (`00 xx 00 00`, then `00 00 xx 00`), then `49 00 00 xx` records at 0x1FC000. A state area sits at 0x1FF760–0x1FF81F. The same `53 01 49 01 49 01 54 00 44 00` sequence appears at 0x1F0011 and in the application's data at 0x08E568, so it is probably a structure copied between RAM and the log.

## Device

The device is probably a telecom or network unit with a PowerPC main processor (MPC8xx/82xx class, booting from offset 0x100 of a 32-bit flash bank). It also carries ARM-based sub-processors or line cards, whose big-endian firmware the host stores in its own flash. Confidence that it is PowerPC with a 32-bit big-endian boot bank is high. The product class is low confidence. It rests on the CLI argument syntax, the alarm-like help strings, the card inventory table and the event log. The maker and model cannot be read from a single lane.

## Open questions

- What the file and record names say ("Daeces", the table names, the log letters). Next: interleave this lane with the other three chips of the bank (lanes 0, 2 and 3, same block headers at the same offsets).
- Whether the erased holes in the chain are intentional. Next: check whether the other lanes are erased at exactly the same word ranges, and decode the full file header.
- What the sparse-zero data in block 1 is. Next: render it from the full 32-bit interleave at 1 bpp, and try widths that are multiples of 32 pixels.
- Which RTOS and compiler built the PowerPC code (VxWorks/Diab is a guess from the EABI start-up). Next: run the interleaved image through a PowerPC disassembler and look for symbol tables or version banners.
- What the block-header checksum byte (offset 6) and the sequence byte (offset 10) are. Next: rebuild the full 32-bit header words from all lanes.

## Method

I worked with Python (`python3 -I`), `xxd`, `strings` and `binwalk` only. `binwalk` found no known signatures, which is expected for a single lane. I mapped sectors by entropy and erased/zero fill, hex-dumped every sector header, and decoded the linked block headers. I fixed the stride and lane by counting lane signatures of known instruction patterns: the PowerPC `stwu`/`mflr`/`stw r28..r31`/`blr` field bytes and the ARM APCS `mov ip,sp`/`stmfd`/`sub fp,ip,#4`/`ldmdb fp` bytes. The reset stub at CPU 0x100 confirmed both. I classified 1 KB chunks by these signatures to draw the content map, and parsed the log records in fixed 4-byte steps.
